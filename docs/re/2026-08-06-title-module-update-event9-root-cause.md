# Title 模块更新卡住：`event=9` 生命周期违约

## 触发条件

后台发布模块槽位 1（`mmTitleMstarWqvga.cbm`）后，标题启动阶段的 `WT 18/5`
协商返回更新位图，客户端开始连续请求 `WT 18/6` 分片。客户端在收到第六块后停止
推进，服务端最后看到的请求为 `start=24576`，没有继续请求 `start=28672`。

## 可重复证据

隔离自动化场景 `scene-teleport-stone-probe-v1` 使用独立端口、数据库、账号和
`JHOnlineData` 副本复现了同一链路：

- `18/6` 的前六个 4096 字节分片被原生 parser 消费；累计有符号字节和依次为
  `71084`、`149331`、`188917`、`233790`、`287920`、`334281`。
- 第六块触发客户端 20 KiB 缓冲刷写到 `MMORPGTempcbm`，随后构造下一请求
  `start=24576`；这证明文件大小、分片大小和累计校验和并非首次偏离点。
- 在第七块到达前，调度器投递了先前 `18/5` 响应附带的 `event=9`。客户端
  `handle_version_update_response`（入口 `江湖OL.CBE:0x01037472`，其非数据事件分支
  位于 `0x010375A0`）
  将更新状态从 `2` 设为 `5`；第七块随后抵达时不再进入分片消费路径。

对应自动化原始产物示例：
`artifacts/automation/scene-teleport-stone-probe-v1-20260806T051728597Z-45320/automation.log`。

## 根因

服务端传输层曾以“请求含 `version`、不含 `start` 且本地存在模块”为条件，给响应设置
自定义帧标志 `closeAfterData`。远程客户端将该标志翻译为 `event=9` 并投递到同一个
原生网络回调。这个关闭/失败事件不是 `18/5 → 18/6` 更新协商的一部分，而且其投递可以
落在后续分片之间，违反了客户端更新状态机的生命周期契约。

## 修复

删除服务端根据本地资源文件猜测并发送 `closeAfterData` 的逻辑。每个传输 socket 仍由
宿主端正常关闭，但不会把该宿主连接关闭伪装成客户端 `event=9`。因此 `18/5` 后只有
客户端实际的 `event=7` 更新响应，`18/6` 的后续分片可以按原生状态机继续处理。

运行独立副本。场景不发送任何标题界面输入，只等待真实启动更新状态机完成。
