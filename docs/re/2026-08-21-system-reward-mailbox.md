# 系统奖励邮箱调查与实现契约

## 触发与客户端链路

- NPC 点击使用已验证的 `WT 1/26/1 {type=1,id=actor}`。
- NPC 对话服务行使用已验证的 `WT 1/26/1 {type=2,id=value}`。
- `ParseNPCDialogData (JianghuOL.CBE:0x010380E8)` 读取 `1/26/1` 的主文本和 `action=1` 选项；现有技能、商店和副本服务都通过该 parser 完成后续选择。
- 本功能沿用普通 `action=1` 对话，不新增未知 WT kind/subtype。邮箱入口、邮件分页、邮件详情和领取结果都返回普通 `26/1` 对话对象。

## 服务值

`service_kind=9` 表示邮箱入口。其服务值使用独立的高字节命名空间：`0xf5000001` 打开邮箱、`0xf6000000 | mail_id` 查看邮件、`0xf7000000 | mail_id` 领取邮件。服务端再次校验当前账号的收件行和邮件状态，不信任客户端值。

## 持久化契约

- `server_global_reward_mails` 保存标题、正文、状态和审计时间。
- `server_global_reward_mail_items` 保存有序的多物品附件。
- `account_reward_mails` 保存奖励发放时的账号级收件行、领取状态和领取时间，主键为 `(mail_id, account_id)`；`recipient_count` 表示账号数。全服与指定账号两种模式共用该表，不需要复制附件或改变客户端领取协议。
- 发放在一个数据库事务中生成收件行。未填写指定账号时，读取当前 `account_roles`，按 `account_id` 去重并向全服所有已有角色的账号发放；填写指定账号时，仅为去重后的目标账号创建收件行。邮件是发放时的账号快照，新建角色不会重复获得历史邮件；撤回只允许未领取邮件，已领取物品不反向删除。
- 指定账号支持逗号、分号、空格或换行分隔，单次最多 64 个；账号格式与游戏注册账号一致（4–32 位字母、数字或下划线）。重复值在提交前去重。每个目标账号必须存在且至少拥有一个角色；任一个不满足时，邮件、附件和已插入的收件行全部回滚，不能留下部分发放。
- 同账号任一角色都读取同一封邮件。领取时仍保留当前 `role_id` 作为角色快照事务作用域，附件进入实际发起领取的角色背包；数据库对账号收件行加锁并只允许一次 `0 -> 1` 转换，因此其他角色不能重复领取。
- 领取在一个角色状态事务内预检完整附件的背包容量，全部物品加入成功后再标记账号邮件已领取；任一失败回滚角色状态和收件行。
- 已部署的 `account_role_reward_mails` 会按 `(mail_id, account_id)` 聚合导入：任一角色已领取则账号已领取，否则保留撤回状态；旧表不删除，作为历史迁移来源。

## 已排除假设

- 当前资源和代码没有发现独立客户端邮件模块或已知邮件 WT parser，因此不能凭空新增邮件专用包。
- 邮件附件不使用宝箱抽取模型；奖励是后台配置的有序多物品集合。

## 未知与限制

- 客户端原生对话最多显示有限行，服务端按现有分页上限生成选项。
- 撤回不会删除已领取物品，这是所有权已经可能发生变化后的唯一可审计语义。

## 验证记录

- `make -j2` 已通过；随后 `make server -j2` 实际重新编译并链接 `bin/jh-online-server.exe` 成功，邮箱实现和后台全服奖励页面均已纳入服务端目标。
- 后台历史邮件查询使用收件统计和附件摘要的独立相关子查询，避免收件行与附件行连接造成计数、摘要重复。
- 后台发放和历史统计均按账号计数；同账号多个角色只生成一个收件行。
- 后台“指定账号”留空即保持全服发放；非空时仅显示给、并写入目标账号的收件行。服务端不信任浏览器的范围提示，逐个校验目标账号及其角色后才提交事务。
- 后台 SPA 导航已包含“奖励邮件管理”入口；NPC 类型选择器和“可同时提供的对话功能”均包含邮箱。
- 尚未连接本机隔离 MySQL 自动化环境：当前会话未提供 `CBE_AUTOMATION_MYSQL_PASSWORD`，因此多附件领取、重复领取、背包不足回滚和撤回的运行时断言仍需在隔离数据库中执行。
