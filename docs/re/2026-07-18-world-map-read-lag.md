# 世界地图打开卡顿：数据表小读取开销

## 结论

卡顿不在地图选择协议。运行日志中的 `16/4` 地图确认由
`builtin-teleport-stone-map-confirm` 在约 1–2 ms 的正常请求处理区间内完成；
真正的同步重负载发生在世界地图界面初始化时的客户端本地数据表读取。

## 客户端与资源证据

- `JianghuOL.CBE:LoadItemDataSheets(0x01035C48)` 在地图缓存未就绪时依次调用
  `LoadMapDataSheet(0x0103581E, mode=0/1/4)`。
- `LoadMapDataSheet` 分别加载 `wMap.dsh`、`wMapLine.dsh` 和 `sMap.dsh`；子地图线
  页面还会加载 `sMapLine.dsh`。
- `LoadDataSheetFile(0x01045D28)` 读取 16 字节头和字段头；
  `SeekDataSheetRecord(0x01045C60)` 对每行先读取 4 字节行长，再读取最多
  `0x200` 字节行数据。
- 当前资源行数为：`wMap=27`、`sMap=135`、`wMapLine=26`、`sMapLine=102`。
  单次基础世界地图初始化至少产生约 376 次小文件读取，不含字段头和额外查找。

## 主机侧负开销

旧 `vm_cbfs_vm_file_read` 对每次读取都会：

1. 读取 PC、LR、R0、R1 四个 Unicorn 寄存器，但这些值从未使用；
2. 按本次大小执行 `SDL_malloc`；
3. `fread -> uc_mem_write` 后执行 `SDL_free`。

数百次 4–512 字节读取把寄存器桥接和堆分配固定成本集中到界面打开的一帧，
在子场景较多的世界区域尤其明显。

## 修正

- 删除文件读取热路径中的四次无用寄存器访问和空的 CBM 分支。
- `size <= 0x200` 使用 512 字节有界栈缓冲，覆盖客户端数据表的完整行上限。
- 大于 `0x200` 的资源读取仍使用原有 `SDL_malloc/SDL_free`，不改变大文件语义。
- 文件定位、读指针、返回字节数和 `uc_mem_write` 行为保持不变。

## 验证

- `make -j2` 通过。
- `git diff --check` 通过，仅输出仓库已有的 LF/CRLF 提示。
- mock service 重新监听 `127.0.0.1:19090`，启动 stderr 为 0。
- 该阶段没有新增或修改网络响应；客户端仍通过原生地图数据和既有 `16/4`
  确认链路工作。

## 2026-08-28：世界地图光标偶发约 2 秒延迟（调查中）

### 新症状与已知边界

用户报告世界地图已经打开后，方向键移动光标有时即时响应，有时约延迟 2 秒；这不是
“点击确认后等待 `16/4` 响应”的现象。此前的初始化本地数据表重负载仍是候选因素，
但尚无本轮运行证据证明它恰好发生在慢光标之前，不能将两者直接视为同一根因。

静态链路已确认：SDL UI 线程把按下和松开分别放入 `vm_event` 队列，模拟线程在屏幕
循环中每帧最多取出一个事件，帧节流为 `100 ms`。因此只要队列在一次按键前已有约
20 个待处理事件，光标事件就会出现约 2 秒的线性排队延迟。队列当前还以普通的
`vmIsLock` 标志在两个线程之间协作，而不是真正的互斥原语；这构成队列计数/顺序不稳定
的独立风险，尚未据此实施修复。

另一方面，事件出队后仍会依次执行现有 scheduler、CBE 的输入 logic、idle logic、
render、LCD 更新；其中任一阶段或地图本地表读取都可能占据同一帧，造成下一次按键在
队列中等待。网络 callback 不通过 `vm_event` 队列，但会在 scheduler 阶段运行，故也需
与队列延迟分开测量。

### 本轮取证（默认关闭）

`CBE_TRACE_WORLD_MAP_LATENCY=1` 时，客户端只向当前 profile 的
`logs/world-map-input-latency.log` 追加最多 2048 行。每行记录：

- 事件入队时间戳、出队时队列深度和 `queue_wait_ms`；
- 同一帧 `scheduler`、资源加载、输入 logic、idle logic、render、LCD 的耗时；
- 该帧本地文件读取次数/字节数，以及既有 screen/入口/最后 PC/SCE 标识。

事件时间戳和序号只存在于宿主 `vm_event` 结构；探针不写 CBE/CBM 内存、不改寄存器、
PC/LR、网络包、callback、屏幕生命周期或输入顺序。文件读取计数也只观察已发生的
`fread` 调用。复现时应只在世界地图界面进行少量、间隔清晰的方向键操作，并保留首次
慢响应前后的日志行。判定规则为：`queue_wait_ms` 接近 2000 且回调耗时正常，说明输入
积压；某个阶段单独接近 2000，说明该阶段是首次阻塞点；若同帧 `file_reads` 集中增长，
再回到 `wMap/sMap` 本地数据表路径取证。

为避免手动复现遗漏此开关，`bin/multiplayer/start-player-1.bat` 现在仅在变量未设置时将
它设为 `1`；需要关闭可在启动前显式设为 `0`。该开关不改变任何 CBE 输入或状态，只会在
按键事件或实际慢帧后追加一行宿主计时记录。

### 本轮根因确认（2026-08-28）

本轮手动复现后的 `player-1/logs/scene-battle-collision.log` 已有 43,712 行、
约 5.5 MB。最新原始行稳定成对交替：

```text
scene_battle_tick phase=gate-runtime-ready pc=01014d74 ...
scene_battle_tick phase=normal-tick         pc=01014d8a ...
```

`vm_trace_scene_runtime_tick_gate_pc()` 是 `hookBlockCallBack()` 对每个 CBE 执行
PC 都调用的旧场景战斗调查探针。它未检查 `CBE_TRACE_SCENE_BATTLE_COLLISION`，并且其
去重键包含当前 PC；正常帧固有地从 `0x01014D74` 进入 `0x01014D8A`，所以 PC 每次交替
都会绕过去重。每次命中都在模拟线程内同步执行 `fopen("logs/scene-battle-collision.log",
"ab") -> fprintf -> fclose`。

屏幕循环的方向键出队、CBE logic 和 render 与该 probe 共用同一模拟线程；因此这两次
每帧的磁盘打开/关闭一旦受缓存回写、杀毒扫描或文件系统调度影响，就会在输入处理前造成
可变、可达秒级的阻塞。`map-controller-forensics.log` 只保留首 32 次地图控制器 tick，
不是本次持续卡顿源。该无条件高频 I/O 于提交 `a9060f8`（2026-08-24）引入，是本轮
最早被违反的宿主取证契约；地图数据表读取和网络协议均不在首次偏离点。

修复已移除该无条件 scene-runtime tick probe，以及同一已完成崩溃调查的地图控制器
写入／格式化／tick probe；不再保留对 `Global_R9+0x9540` 的全局内存写观察或
`map-controller-forensics.log` 输出。仍在使用且由明确环境变量开启的场景／战斗探针不受
影响。移除不改变 CBE 的输入、screen、网络或地图状态。后续应在 player-1 世界地图重复
方向键，确认默认运行不再增长 `scene-battle-collision.log`，同时检查默认关闭的输入延迟
探针没有出现异常 `queue_wait_ms` 或单帧阶段耗时。

### 第二个首次偏离：重复的动态模块代码钩子（2026-08-28）

移除旧日志后，player-1 的新一次复现记录了 `screen=01053F60`（世界地图）中连续的
`render_ms=771/729/691/655/693/677/671/696`；相应 `queue_depth` 仅为 `1` 或 `2`，因此
秒级等待是前一帧 render 占用模拟线程的后果，不是输入队列本身失控。每个慢帧只有两次、
共 405 字节的本地读取，LCD 更新为 0–1 ms，也排除了文件 I/O 与最终 LCD 提交。

代码核对发现 `hookCodeCallBack` 已经以 `UC_HOOK_CODE` 覆盖全部客户机地址；此外
`add_manager_code_hooks()` 又在整个动态内存池重复注册了第二个 `UC_HOOK_CODE`。世界地图
的 `mmGame` render 每条动态指令都会进入它，重复调用仅用于已完成战斗调查的 PC 观察，并
执行一次 `uc_reg_read(R9)` 和 `vm_dl_note_sp_bf()`。`g_currentScreenModuleBase` 与动态模块
归属已经在 screen push/add/prepare 及 loader 生命周期记录，平台 API 分派另有精确地址钩子，
因此这条第二钩子没有产品语义。

修复移除了该整池重复代码钩子及其只读 callback；通用代码钩子、精确 manager API 钩子、
screen/module 生命周期记录、CBE 输入/渲染/网络 bytes 均保持不变。该修改只消除每条动态
客户机指令的一次宿主回调和寄存器读取。复测应仍在同一世界地图按方向键：预期
`render_ms` 不再持续处于数百毫秒，随后的 `queue_wait_ms` 也应恢复到一帧量级。

### 第三个首次偏离：通用代码钩子的历史取证扇出（2026-08-28）

移除动态池重复钩子后的新进程复现仍显示同一世界地图 render 连续为 645–696 ms，证明
前一项确实是冗余开销，但不是全部阻塞源。`hookCodeCallBack` 是覆盖全部客户机地址的
`UC_HOOK_CODE` 回调；在普通玩家会话中，它仍无条件顺序调用约 30 个已完成的背包、商城、
挂机战斗、场景 actor、付款与网络 parser 调查函数。即使每个函数最终因 PC 或状态不匹配而
返回，调用本身仍发生在每一条 `mmGame` render 指令上。

这些函数都只读日志/自动化证据，正常客户端的输入、资源、CBE render、screen、协议和
callback 不依赖它们。其逐指令扇出现在只在仓库自动化实际运行时启用；完成世界地图调查后，
不再保留可由普通启动器重新开启的 legacy runtime forensics 开关。必要的平台兼容
`vm_restore_main_r9_for_rom_code()` 和精确 manager API hooks 保留在热路径。世界地图延迟
计时器也已在结案后删除。

### 第四轮假设已否定：不能收窄通用代码钩子（2026-08-28）

第三轮新进程记录显示，进入世界地图后的正常 render 已降到 14–46 ms；按一次方向键后，
客户端自己的 `mmGame` 输入分支读取 1,526 次、约 40 KB 的地图/表数据，随后 render 稳定在
约 420–460 ms。该状态没有 scheduler、网络、LCD 或高频文件 I/O：每帧仅两次、405 字节读取。
这使全地址 `UC_HOOK_CODE` 成为合理的性能候选，但其覆盖范围不能仅以
`vm_restore_main_r9_for_rom_code()` 的 ROM 判断来推导。

实测收窄后，客户机跳至 `PC=0x0A100000`（`PROGRAM_EXIT_ADDR`）仍继续取指，首次异常为
未映射访问 `0x0A100000`；这证明通用 callback 还承担 `uc_emu_start()` 返回哨兵的停止语义，
单独地址注册在当前 Unicorn hook 组合中没有等价保留这一契约。该改动已立即回退为全地址
注册；历史 per-PC 取证扇出仍保持关闭。没有把该崩溃归因于地图、协议或 CBE 数据，也没有
修改 CBE/CBM 字节、寄存器、输入、网络响应、callback 或 screen 状态。

### 第五个热路径：无条件全局内存读取证（2026-08-28）

在普通 Windows 构建中，`hookRamCallBack()` 对 `UC_MEM_READ` 的唯一使用位于未启用的
`GDB_SERVER_SUPPORT` 分支；其余正常代码只观察有限地址的写入，用于已完成的诊断和自动化。
但初始化仍把它注册为整个地址空间的 `UC_HOOK_MEM_READ | UC_HOOK_MEM_WRITE`。世界地图在
`05039FDB` render 的慢状态每帧只发生两次文件读取，却会执行大量客户机内存 load；每次 load
都跨入空的宿主 read callback 是此前阶段计时没有单独显示的开销。

修复将非 GDB 构建的该 hook 缩为 `UC_HOOK_MEM_WRITE`；GDB 构建仍保留读/写 watchpoint。写入
观察、自动化断言和客户机内存内容都不变；该变更没有触碰 CBE 代码、寄存器、输入、网络或
screen 生命周期。

### 第六个热路径：无条件全局内存写入观察（2026-08-28）

第五轮新进程复现表明移除读回调后，地图慢状态已从约 420–460 ms 降为约 320–350 ms；队列
等待仍由这段 render 线性累积。`hookRamCallBack()` 的所有非 GDB 分支依然只是已完成调查的
写入日志/自动化 watch，未被输入、绘制、资源、网络或 screen 状态机读取。保留全地址
`UC_HOOK_MEM_WRITE` 仍让每一次客户机画面缓冲区/对象写入跨到宿主。

普通玩家会话现不注册该全局内存 hook；仓库自动化和 GDB 会保留原完整读/写观察。该范围
收缩只改变宿主取证，不改变任何客户机内存字节、指令、寄存器、输入、网络响应、callback
或生命周期。

### 第七个热路径：动态模块中的通用代码回调空转（2026-08-28）

第六轮的新进程记录把慢态 render 继续降至约 320–350 ms，证明全局内存 callback 的收缩
生效，但 `UC_HOOK_CODE` 的全地址 dispatch 仍会对动态模块的每条指令调用
`hookCodeCallBack()`。前一次把 hook 注册范围改为 ROM 加退出地址已证实不能替代全范围注册：
`PROGRAM_EXIT_ADDR` 的 fetch 仍需要通用 callback 停止。因此不能再改变 Unicorn 注册覆盖范围。

本轮保留原全地址注册与退出哨兵处理，但在普通玩家会话的 callback 开头识别动态内存池 PC
并立即返回。世界地图的动态模块只经精确 manager API hooks 调用宿主平台；而 R9 恢复只适用于
ROM 代码，历史取证又已显式关闭。此前的范围收窄试验能完成登录和地图操作，也交叉证明动态
模块不依赖该通用 callback 的其余产品分支。仓库自动化仍保留完整 callback，以维持其
声明的调查与断言。

此项只跳过动态客户机指令进入 callback 后的宿主空转，未改动 CBE/CBM 字节、客户机内存、
寄存器、PC/LR、输入事件、网络响应、callback 或 screen 生命周期。下一次复现须重新启动
player-1，并比较方向键后的 `render_ms` 与 `queue_wait_ms`；若仍有连续慢态，首次阻塞点将不再
是 callback 函数体，而需要分别量化 Unicorn 的 hook dispatch 和 CBE 原生 render 指令量。

### 第八个首次偏离：全局 `UC_HOOK_CODE` 的分派成本（2026-08-28）

第七轮后一次完整新进程复现仍记录 `render_ms=304–358`，并在连续按键时让
`queue_wait_ms` 线性累积至 2,663 ms。此时动态模块 PC 已在 callback 开头立即返回，日志的
`last_pc` 也由原先的 `05039FF0` 变为 ROM 中的 `0101829E`；因此残余慢态不是 callback 函数体、
文件读（每帧 2 次／405 字节）、LCD、scheduler 或输入分支，而是 Unicorn 仍对每条动态
客户机指令分派一次全地址 `UC_HOOK_CODE` 的成本。

前一轮曾将全局 hook 注册范围缩小并导致 `PROGRAM_EXIT_ADDR` 未停止而访问失败；本轮不再以
地址范围猜测退出语义。项目绑定的 Unicorn 2.1.4 头文件明确提供 `uc_ctl_exits_enable` 与
`uc_ctl_set_exits`：可由引擎在指定地址停止，且文档说明它比 hook 更适合此用途。普通玩家
会话现在将唯一退出地址配置为 `PROGRAM_EXIT_ADDR`，把通用代码 hook 限于主 ROM，并为
`VM_LOG_NOOP_ADDRESS` 保留精确 hook；动态 CBM 的平台 API 仍只经已有精确 manager hooks
进入宿主。若当前 Unicorn 构建拒绝该 exit 配置，会记录 warning 并自动回退到原全地址 hook，
不会以未受保护的退出地址继续执行。GDB、仓库自动化和显式 legacy 取证保持原全范围代码
hook，避免减少已声明的调查能力。

此为纯模拟器执行边界修复：没有修改 CBE/CBM 字节、客户机内存、寄存器、PC/LR、输入、网络
包、回调或 screen 生命周期。构建已通过；人工验收需要完整重启 player-1，确认能登录、进入
世界地图并持续按方向键，同时检查日志不再出现连续数百毫秒 render 或秒级 `queue_wait_ms`。

### 第九个首次偏离：LCD 精确代码钩子的跨边界分派（2026-08-28）

第八轮后的新进程仍有 `render_ms=244–300` 的连续慢帧，但新增加的有界平台 API 计时已排除
LCD 函数本体：每帧约 2,269–2,349 次 LCD API 调用，累计函数体仅 0–10 ms。按 manager 槽位
计数，稳定热点为槽 1（约 1,102 次，`vMGetCurrMainScreenImage`）、槽 25（约 750 次，
`vMDrawImageWithClipEx`）和槽 26（约 344 次，`vMDrawImageClipAndAlphaEx`）。因此首次偏离是
Unicorn 在每次精确 `UC_HOOK_CODE` 命中时切断动态 CBE 基本块并进入宿主，而不是图片像素拷贝、
文件读取、LCD 提交、网络或输入队列。

这三项的 ABI 已由现有固件管理器契约和运行时调用共同确认：普通 manager 初始化
`vm_configManagerTable()` 与 fixed-base 初始化器槽 2 的 `vm_configManagerTableCount(..., 95)` 都
把 LCD 函数表地址提供给 CBE；槽 1 仅返回固定的 `VM_screenImageStruct_ADDRESS`，槽 25/26 从
R0–R3 和调用方栈读取原图、裁剪和目标参数，原实现结束时均按 CBE 给出的 LR 返回。手工复现中
这三个槽正是全部慢帧的高频来源。

隔离 Unicorn 2.1.4 微基准以相同 ARM 调用/返回循环执行 48,000 次：精确代码钩子完成
48,000 次、耗时 3.211 ms；标准 `SVC` 中断入口同样完成 48,000 次、耗时 2.159 ms。由此采用
host-owned `VM_FUNC_HK_TABLE_ADDRESS` 内的 ARM 平台桩，而不修改任何 CBE/CBM 字节：槽 1 在
客户机 ARM 中加载原有屏幕对象地址并 `BX LR`；槽 25/26 触发各自 SVC，由现有宿主绘制函数处理
相同寄存器与栈参数，随后由客户机桩自己的 `BX LR` 返回。SVC 的 PC 被精确限定为这两个 host
stub 的下一条指令；其他 CPU 中断仍走既有 semihosting 处理。

这不是业务特判：函数表、实参、像素写入和返回地址完全沿用已有 LCD 平台 ABI，改变的只有
Unicorn 如何从客户机跨入同一宿主 API。世界地图 API 取证开关开启时，SVC 路径仍计入相同的
槽位和耗时统计，供下一轮人工复现验证；完成验证后应默认关闭该临时计时开关并移除其详细输出。

最新复现确认槽 1 已脱离精确代码钩子，但槽 25/26 经 SVC 仍分别约 760/344 次，慢帧仍为
约 240–280 ms。这否定了“只替换 hook 类型即可消除卡顿”的假设；每次图片绘制的宿主跨边界
仍是首个阻塞点。下一步仅在 API 计时开关开启时，为槽 25/26 各捕获最多 48 条既有 ABI 调用：
目标/源 `ImageHeader`、R2/R3 的源坐标、栈中的宽高/目标坐标。它在原绘制函数执行前只读参数，
写入独立 `world-map-lcd-blit-contract.log`，不改变图像、客户机寄存器、返回路径或调度；用来
证明客户机 ARM 平台例程可安全覆盖的正常调用集合，随后删除该临时取证。

采集结果为槽 25 的 36×36 图集上 12×12 不透明图块、槽 26 的 96×24 图集上 24×24 透明图块
及 70×38 图集上 35×19 透明图块；所有记录的目标均为 `VM_screenImageStruct_ADDRESS` 的
240×400 屏幕，源/目标坐标和宽高均在各自边界内。临时取证已移除。

基于这份契约，槽 25/26 现分别指向 host-owned 映射中的 ARM 例程：保存 R0–R12/LR，验证
主屏幕目标、非负坐标、正尺寸、源/目标边界和非空源像素指针后，在客户机内逐像素执行 RGB565
不透明／0 值透明拷贝，并 `BX LR` 返回；任一不满足的调用恢复原始寄存器和栈，再进入既有 SVC
宿主实现。主循环收尾 `vm_lcd_update_with_input_overlay()` 本来就从 CBE 的屏幕缓冲整帧读回
`Lcd_Cache_Buffer`，因此客户机内写入仍由同一 LCD 提交边界显示。

新增 `make world-map-lcd-native-blit-regression` 回归从同一 LCD manager 表读取槽 25/26 地址，
在隔离 Unicorn ARM 环境中验证：不透明矩形复制、透明像素保留目标值、R0–R12 不变，以及越界
矩形恢复 CBE 调用帧并由既有 SVC 裁剪。2026-08-28 的构建和该回归均通过；仍需用 player-1
世界地图确认连续方向键时 `render_ms` 和 `queue_wait_ms` 实际下降。

### 第十个首次偏离：平台 ARM 逐像素循环本身的执行量（2026-08-28）

新一次 player-1 手工复现已排除“槽 25/26 仍跨宿主”的假设：在慢帧中
`api_lcd` 已从约 2,300 降为 74–104，槽 25/26 不再出现在 API 热点；但相同帧的
`render_ms` 仍持续约 253–294 ms。也就是说，原来的精确 hook 和 SVC 已不在这条慢路径上；
将其替换成普通的客户机 ARM 半字循环，只是把阻塞转移为 Unicorn 对大量 load/store、计数和
分支指令的模拟。

已记录的地图调用形状可量化这个执行量：约 760 次 12×12 不透明块和 344 次 24×24 透明块，
仅像素数就约 307,000；原例程每个像素还执行地址更新、计数和分支，故一个 render 可进入约

修正仍限定为同一 LCD 平台 ABI 的实现优化：已通过参数和边界验证的 12 像素宽、不透明且源/

24 像素宽透明图集调用展开为每行 24 次 `LDRH/CMP/STRHNE`，逐项维持“源像素为 0 不写目标”的
原有规则，但去除内层指针、计数和回跳。35×19 和其它尺寸仍走已有的通用 ARM 循环，所有越界、
非主屏幕或异常参数仍恢复调用帧并进入原有 SVC 实现。为容纳展开后的平台例程，透明例程在同一
host-owned 映射中移至非重叠的 `VM_FUNC_HK_TABLE_ADDRESS + 0xF800`；没有修改任何 CBE/CBM
字节、客户机内存、寄存器、PC/LR、输入、网络包或 screen 生命周期。

回归扩展为从真实 LCD manager 表调用这两种常见尺寸：12×2 对齐不透明块验证每行六个字均被
正确复制；24×2 透明块验证首尾及中间的零像素均保留原目标值。通用尺寸、R0–R12 保留和越界
SVC 裁剪也继续验证。`make world-map-lcd-native-blit-regression` 已通过；下一步必须完整重启
player-1 后在世界地图连续方向键手工确认 `render_ms` 和 `queue_wait_ms`，再决定是否删除临时
延迟计时器。

### 第十二轮：player-1/player-3 的 render 分支对照（2026-08-28）

本轮对照复现否定了“player-1 的图片绘制量更大”这一假设。两个玩家使用同一个
`bin/JHOnlineData/mmGameMstarWqvga.cbm`（启动目录的 `CBE` 与 `JHOnlineData` 均为同一
共享目录 Junction），并且正常地图帧的 `clip_fast12` 都是 `6,264` 行，透明通用路径分别约
为 player-1 的 `3,766–3,800` 行与 player-3 的 `3,525–3,546` 行；平台 API 调用、文件读取
和最终 LCD 提交也处于同一量级。但 player-1 的 `screen=01053438, render=0501770f` 连续耗时
`250–291 ms`，player-3 的 `screen=01053f60, render=05039fdb` 仅 `35–47 ms`。

两边的 render 回调都属于已装载的 `mmGame` 代码，但动态装载基址与 screen 实例不同；这本身
不能证明哪个角色的数据或模块所有权有错，却把首次未决边界收窄为 render 回调内部的客户机
基本块执行量。不能再依据 LCD 分支比例继续改绘制实现。

初始实现把 `UC_HOOK_BLOCK` 常驻于整个模拟器、在非目标帧立即返回；新复现证明这仍会被 Unicorn
分派，player-3 因而从约 `35–47 ms` 扰动至约 `195–224 ms`，且最先 64 个动态 render 已在进入
地图前耗尽。这份样本不能作为地图计数证据，也不能继续保留该全局 hook。

静态 `+0x59c` 标注包含其前一函数的 `POP {r4,pc}`；首次全局采样的地图入口
`0501770e` 随后的 12 字节基本块，与已安装资源中 `mmGameMstarWqvga.cbm + 0x59e` 的
`C5 49 10 B5 49 44 0A 6B 01 2A 02 D1` 完全一致。故现有临时开关
`CBE_TRACE_WORLD_MAP_RENDER_BLOCKS=1` 改为以该 `+0x59e` 的 16 字节入口指纹只读匹配地图 render；仅在那一次
`vm_emu_start(screenRenderEntry, ...)` 前注册 `UC_HOOK_BLOCK`，返回后立即删除，整个进程最多
采集 8 个已匹配地图帧。回调只对基本块 PC、块长度和命中次数计入固定的 host-only 四路表，
渲染返回后才把总命中数、表冲突数、按命中排序的前三项和实际入口 R9 写入既有
`logs/world-map-input-latency.log`。它不读取角色/场景字段，不写 CBE/CBM 内存、寄存器、PC/LR、
输入、网络包、回调或像素。两个玩家的启动器暂时默认开启，下一次各自完整重启并在世界地图
移动光标即可直接比较同一字段；取得首个额外热块后应删除这项和已完成的 LCD 路径审计。

补充复现中，慢端仍为 `250–310 ms`、快端仍为 `35–47 ms`，但 `render_blocks=0`。这不能反证
渲染差异：它只证明静态文件指纹尚未等同于 loader 在实际入口映射出的首 16 字节。为固定首次
偏离条件，采样器现在仅在该开关开启且指纹不匹配时，对每个不同 render 入口最多记录一次、总数
不超过八条，向同一日志追加入口地址、loader 记录的 app/base/local 偏移、只读 R9 和 16 个指令
字节；它不安装 block hook，也不读取客户机业务状态。早先“最多两条”的版本只记录到进入地图前
的 `050177ae` loading screen，未等到地图回调，故改为按入口去重。下一次重启复现先据这些记录
收敛到“模块 + 本地 PC + 命中上限”的触发条件，再开始最多八帧的
基本块统计。

随后去重记录显示地图入口没有继续产生“不匹配”行，说明它确实命中了所设的静态指纹；但
`render_blocks` 仍为零。首次违反点因此从“入口选择”转为 block hook 的范围注册。Unicorn 的
全地址 hook 约定为 `begin=1,end=0`，而原采样器错误使用 `0..FFFFFFFF`；现已改为标准范围，
仍只在匹配的 map callback 前安装、返回后删除。同时 `render_blocks` 记录补充 `hook` 错误码，
使下一次复现可区分“未回调”和“安装失败”，不依赖控制台输出。

范围修正后，首个 map 入口记录到 `2` 个基本块（`0501770e` 与 `0501771a`），并且 `hook=0`，
证明 hook API 已正常工作；后续为零的原因是“最多八帧”在地图资源切换期间的短 setup render 已被
消耗，并非回调失效。采样器现改为先只读识别匹配入口、不安装 hook；仅在该入口完成的帧已超过
`200 ms` 时，才发放剩余最多八帧的采样预算。前一版还允许已出队的按键启动，实际证明它会在地图
初始化阶段提前消耗预算，故已删除该条件。这个决定发生在帧完成之后，只决定后续 read-only block
统计，绝不制造、延迟或改变输入、网络、screen 生命周期或 CBE 状态。先以此取得 player-1 的真实
慢帧热点；随后再以相同已确认 PC 对 player-3 做独立、短时的正常路径对照。

### 第十四个首次偏离：LCD 回调以外的 230ms（2026-08-28）

高精度复现排除了整数毫秒取整掩盖绘制时间的可能。player-1 慢帧中槽 25/26 分别累计约

额外约 230ms。故图片数据、CPU 拷贝、透明处理以及其 platform callback 实现均不是首次偏离。

下一项仅在同一帧内，把每次槽 25/26 回调结束到下一次槽 25/26 回调开始之间的高精度时间累加，
并记录间隔数量。它覆盖 callback 返回后的原有 CBE 指令和已有的 manager 调用，不插入客户机钩子，
不读取或写入客户机状态；每个 scheduler 帧开始前清零，避免空闲等待计入。若慢端的这项累计接近

### 第十五个首次偏离：回调间隙的客户机控制流（2026-08-28）

回调间隙累计已精确覆盖了慢帧：player-1 每帧约 1,103 个间隙累计 `236–284 ms`，几乎等于其
`render_ms=240–290 ms`；player-3 约 1,094 个间隙累计仅 `22–31 ms`，与其 `25–36 ms` render
一致。每次 player-1 间隙平均约 230 微秒，player-3 约 22 微秒。两端的图像 callback 本身、
调用量和请求像素量已被前一轮排除，因此首次偏离是 player-1 在既有 LCD platform callback
`BX LR` 返回之后、下一次图像 callback 之前的 CBE 控制流。

下一轮仍不改变该控制流：在每个已存在的槽 25/26 callback 入口只读 LR，把上一张图像 callback
的返回地址按相对当前 map render entry 的本地 PC 聚合，并累计其后到下一张图像 callback 的间隙。
固定 32 槽、前三项输出的统计只运行在当前帧，既不安装每指令 hook，也不写 CBE/CBM、客户内存、
寄存器、PC/LR、像素、输入、网络或生命周期。由此可把约 250ms 分配到具体静态 mmGame 本地调用点，
再用该调用点的 IDA/资源证据决定真正的修复层级。

### 第十五轮探针校正：逐图像 `uc_reg_read(LR)` 会改变被测时序（2026-08-28）

上述“按返回地址聚合”实现后，完整重启复现发现 player-3 原先的快路径也退化为约
`190–225 ms` render，且约 1,095 个 callback 间隙累计同样达到 `190–220 ms`。这项退化只在
每个槽 25/26 调用都执行一次 `uc_reg_read(LR)` 后出现；它本身说明 Unicorn 寄存器桥接不能被放进
每帧千余次的热路径。player-1 输出的相对地址还发生无符号下溢，证明该采样也没有建立有效的静态
调用点映射。

因此该返回地址表和 `lcd_gap_top` 输出已撤回，不能作为根因证据；原有的回调本体高精度总耗时和
回调间隙总耗时保留，因为它们没有额外逐调用寄存器访问，先前双端对照也由它们得出。此次撤回不
修改 CBE/CBM、客户机内存、寄存器、PC/LR、输入、网络包、callback 或生命周期。后续取证必须在
callback 热路径之外完成，例如由一次性、预声明的只读 PC 触发器对有限调用范围采样，并先验证该
触发器不会使 player-3 快路径的 `render_ms` 明显变化。

### 第十六轮探针撤回：普通会话没有动态 PC code hook（2026-08-28）

按上述设计完整重启复现后，`guest_instr` 始终为 0。检查实际 Unicorn 注册范围发现，这是正确的：
普通会话已用 `uc_ctl_set_exits(PROGRAM_EXIT_ADDR)` 保留退出语义，通用 `UC_HOOK_CODE` 只覆盖主
ROM 与 `VM_LOG_NOOP_ADDRESS`，不覆盖动态 CBM。先前“现有 hook 已取得动态 PC”的前提已过时；若为
抽样重新注册整池 code hook，又会重建已排除的高频宿主跨界，因此该抽样器和启动开关已撤回。

此次复现还显示 player-3 并非有效的同函数对照：其 `screenRenderEntry=05039FDB` 的 16 字节指纹
`F0B5864E051C4E44F06C00240128A5B0` 在 `mmBattleMstarWqvga.cbm` 原始偏移 `0x69B`，而 player-1 的
`screenRenderEntry=0501770F` 指纹 `C54910B549440A6B012A02D100200863` 在
`mmGameMstarWqvga.cbm` 原始偏移 `0x59E`。两个客户端虽然都进入用户可见的地图界面，但当前运行的
render module 与函数均不同，不能再以 player-3 的帧时间否定 player-1 的 mmGame 路径。

### 第十七轮取证校正：mmGame 入口的真实调用顺序（2026-08-28）

player-1 的 `mmGame +0x59E` 静态包装函数的运行时快照为
`owner=0500B210`、`owner+0x04=01014D31`、`owner+0x70=01018167`。随后以同版归档
`mmGameMstarWqvga.cbm` 反汇编该入口，并以主 CBE 的已有 IDA 结论交叉验证：它先调用
`scene_runtime_tick(0x01014D31)`，再调用 `FindEmptyActorSlot(0x01018167)`。
`0x01018167` 只是遍历 actor slot，不能称为 render delegate；先前文档的这一称呼已撤回。
取得这一次性地址证据后，`world_map_mmgame_delegate` 快照代码已删除，不会留在正常或后续取证路径中。

因此 1,100 次图片 callback 所在的正确分析边界是 `scene_runtime_tick`。最新复现也给出首次稳定
状态切换：资源完成后的首两帧仍为约 24–25 ms；同一 screen 的下一帧读取 1,552 次、41,007 字节后
开始稳定为约 240–270 ms，而图片 callback 自身仍仅约 3–4 ms。接下来应比较该 tick 在资源切换前后
的已证明状态分支，不能继续围绕 `FindEmptyActorSlot` 推测。

同时，启动器默认关闭世界地图的每帧、逐图片和 native-LCD 路径取证，先用完全无该类探针的手工复现
排除测量本身放大 player-1 时序。它们仍可由明确设置环境变量临时启用；未修改 CBE/CBM、客户内存、
寄存器、PC/LR、输入、网络包或 screen 生命周期。

### 第十八轮校正：直接读取绘制循环的槽数（待复现）

无上述逐帧、逐图片探针的完整重启后，用户仍可复现卡顿，故探针自身不是根因。前一组六条
`JianghuOL.CBE:0x01014E54` 快照均走 `scene_runtime_tick` 正常分支；除初始化/光标字节外，外层
状态稳定。静态复核 `0x01014456` 证实 `R9+0x5C64+0x60` 是该函数的绘制器对象，而不是此前错误
标注的 pending 根；其 `+0xDC` 是函数实际用于循环终止的绘制槽数。

同一受限开关现仍仅在外层 callback 匹配 `mmGame +0x59E` 的 16 字节静态指纹后，允许精确
`UC_HOOK_CODE` 在主 CBE `JianghuOL.CBE:0x01014460` 触发。该 PC 已位于 `0x01014456` 的
`R6=R9+0x5C64` 与 `R5=0xC80` 建立之后、首次解引用绘制器之前。触发器最多记录六次：二进制名、
规范化 PC、命中次数、外层入口、R9/R6/R5、状态指纹、绘制器、`draw_slots=R6+0xDC`、actor/
selector 表、scene/bounds 指针和绘制器 `+0xC68/+0xC80` 两项方法表。输出独立写入当前 profile 的
`logs/world-map-draw-loop-snapshot.log`。

它不在动态 CBM 的每条指令或图片 callback 中运行，不写 CBE/CBM、客户内存、寄存器、PC/LR、
输入、网络包、callback 或生命周期；六条后不再读取或写日志。该快照只用于比较资源切换前后的
实际绘制循环规模与方法表，在确定首个差异后必须删除；它不是性能修复，也不作为“客户端已正常”的证据。

### 最终根因与修复：主 ROM 的逐指令宿主回调（2026-08-29）

在 player-1 的完整复现中，资源完成后世界地图每次方向键都会执行主 CBE ROM 的
`0x01036247`。该方法按固定 25 项布局调用 `0x01005A7F`，最终进入纯 CBE RGB565 像素填充
`0x010048D8`；25 次调用累计稳定约 `0.80–0.90 s`。布局数量为正常值 25，并非角色、服务端
数据或网络包膨胀。该像素填充不写 R9。

首次被违反的平台契约是正常会话仍为整个主 ROM 注册 `UC_HOOK_CODE`，并在每一条指令中调用
`uc_reg_read(R9)` 以执行历史兼容检查。软件栅格化的内层像素循环因此反复跨越宿主边界。player-3
之所以此前流畅，是它的地图界面走动态内存池模块；普通会话的同一通用回调对内存池地址会立即返回，
不会承担这项逐指令开销。这是执行路径差异，不是客户端硬件或角色数据差异。

修复把正常会话的通用回调收缩为仅 `VM_LOG_NOOP_ADDRESS` 的精确平台入口：
`PROGRAM_EXIT_ADDR` 已由 Unicorn 的 native exit 机制处理，manager/platform 导出已有各自的精确
hook。显式自动化和遗留取证模式仍保留完整范围，以维持其被明确请求的观察能力。没有改写 CBE/CBM
字节、客户机内存、寄存器、PC/LR、输入、网络响应、callback 或 screen 生命周期。

用户已在 player-1 手工复测确认世界地图连续移动恢复流畅且无新增异常。构建 `make -j2` 与
`bin\\world-map-lcd-native-blit-regression.exe` 均通过。所有本问题的世界地图延迟、LCD、绘制块和
scene-tick 临时探针及 player-1 启动器开关已删除；历史章节仅保留取证过程，不再表示当前启用行为。
