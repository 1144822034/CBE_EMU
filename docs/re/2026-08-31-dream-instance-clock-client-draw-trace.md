# 梦境地图数字：客户端绘制链取证

日期：2026-08-31

状态：已排除固定 HUD 更新；等待一次带数字画面的只读 caller 记录

## 静态结论

`bin/CBE/江湖OL.cbe` 的 Thumb 代码段从文件偏移 `0x9A` 映射到
`0x01000000`。场景 UI 静态字符串表中可直接确认下列资源地址：

| 客户端地址 | 文件名 |
| --- | --- |
| `0x0104371C` | `map_kuang.gif` |
| `0x01043750` | `time_number.gif` |
| `0x01043A4C` | `-num.gif` |
| `0x01043A58` | `+num.gif` |
| `0x01043AF8` | `ui_timer.gif` |

`-num.gif` 与 `+num.gif` 紧邻 `handkuang.gif`、`numberexp.gif`；
`time_number.gif` 位于另一段场景 UI 名称表中。这只能说明 `-num` 和
`+num` 属于同一套数字资源，不能单靠名称判定截图的 `08:05` 是伤害数字或副本倒计时。

场景每帧路径在 `0x01015212` 依次调用：

```text
0x01015212 -> 0x0100E3E2
0x01015220 -> 0x0100E520
0x01015224 -> 0x0100E8E4
0x01015228 -> 0x01013A7A
```

其中 `0x0100E3E2` 只根据若干场景/角色状态写入固定 HUD 描述项及固定
图块编号 `0x35`、`0x36`、`0x37`、`0x38`、`0x5E`，在 `0x0100E468` 返回；
它不调用 LCD 绘制 API，也不含格式化秒数、递减值或 `-num`/`time_number`
的地址。因此截图中的地图右上角数字不由这条固定 HUD 更新链直接生成。

## caller 取证

新增默认关闭的 `CBE_TRACE_SCENE_NUMBERS=1`。它在既有的
`vM_DrawImageWithClipEx` 和透明版本入口处，仅在源图尺寸为
`110x16`、`77x7`、`17x17` 或 `13x16` 且目标位于上方地图区域时，追加一行：

```text
scene_number_draw ... caller=<CBE LR> ... atlas=<候选图集尺寸>
src=(...) dst=(...)
```

日志为 `bin/multiplayer-data/player-3/logs/scene-number-draw.log`。该探针只读取
绘制调用参数和寄存器 `LR/PC`；不写客户内存、寄存器、响应包、输入队列或屏幕像素。
`110x16` 仍标记为 `num-110x16`，因为该尺寸由 `-num` 与 `+num` 共享。

使用 `bin/multiplayer/trace-dream-clock-player-3.bat` 启动 player-3 后，正常进入
梦境并让数字出现至少一帧即可。拿到 caller 后，应围绕该地址反汇编其函数和上游调用者，检查：

1. 数字源裁剪格是否按 `mm:ss` 排列，及目标坐标是否恒定；
2. 数值来自本地 tick、场景对象字段还是一个解析后的会话对象；
3. 零值/到期分支是否切场景、发请求或仅隐藏该叠层。

在 caller 和它读取的状态字段确认前，不应在服务端或宿主侧添加“副本时长”字段或本地倒计时。

## 2026-08-31：真实绘制和计时对象

player-3 在正常的梦境 NPC 进入链中已产生下列只读记录：

```text
atlas=num-110x16
src=(0,0,11,16)  dst=(182,78)
src=(88,0,11,16) dst=(194,78)
src=(0,0,11,16)  dst=(214,78)
src=(55,0,11,16) dst=(226,78)
```

每帧均按此顺序透明绘制，分别为 `0`、`8`、`0`、`5`；所以截图中的
`08:05` 是真实 CBE 地图图层，而不是模拟器或宿主叠层。调用链从场景每帧入口
`0x01015212` 进入，经过场景 UI 分派和通用图集文本绘制器
`0x0100577A`，最终到 LCD 裁剪返回点 `0x01004222`。

真正维护数值的对象方法在 `0x0104C216`、`0x0104C252`、`0x0104C266`：

| 地址 | 已证实行为 |
| --- | --- |
| `0x0104C216` | 读取单调时钟；调用参数为 `0` 时，和对象 `+0x0C` 比较的阈值为 60,000 ms；参数为 `1` 时阈值为 1,000 ms。达到阈值后，若对象 `+0x10` 非零则将它减一，并更新 `+0x0C`。 |
| `0x0104C252` | 将调用方传入的 32 位值写入对象 `+0x10`，并保存当前单调时钟到 `+0x0C`。 |
| `0x0104C266` | 读取对象 `+0x10`，使用 `3600` 与 `60` 分解数值，再把选定的数字字段交给图集渲染器。 |

本次进场时，`0x0104C252` 对同一对象 `0x0500B57C` 调用了两次，传入值均为
`29285`，上游 return 地址为 `0x01010736`。`0x01010736` 位于从全局场景 UI
组件列表（项跨度 `0x58`）逐项装配控件的客户端循环中，经虚表调用进入该初始化器。
它不是 `30/1` 处理函数的直接读取点。

### 2026-09-01：定时节拍核对

`0x0104C216` 的 Thumb 指令直接给出两种节拍：`r1 == 0` 从只读常量池取
`0xEA60`（60,000 ms），`r1 == 1` 生成 `0x3E8`（1,000 ms）。二者都从场景
计时管理对象的 `+8` 方法取得单调毫秒值。模拟器该时间管理器的对应 ABI 槽位返回
`SDL_GetTicks()` 的相对毫秒，不使用 CPU 时间 `clock()`；因此宿主墙钟本身不慢。

为把本次梦境场景的实际调用模式固定为运行时证据，`CBE_TRACE_SCENE_NUMBERS=1` 时
新增只读、上限 128 条的 `scene_number_timer_process` 记录。它记录调用的 `mode`、
静态确定的阈值、对象当前值、CBE 锚点和同一时刻的宿主单调毫秒；不改寄存器、客户机
内存、网络包或调度。

首次运行已产生反证：梦境场景的可见数值在 `0x010104EE` 经 `0x0104C252` 被重置为
`60 → 59 → 58 → 57 → 56`，而没有命中 `0x0104C216`。因此新增同样只读的
`scene_number_timer_commit` 记录，直接在 `0x010104EE` 返回点读取 CBE 毫秒值、刚写入
的数值及同一时刻的宿主单调毫秒。该记录才是当前梦境场景后台字段单位与真实间隔的最终
取证边界。

同时抓到的正常副本入口包仍只有 `30/1 { scene, posinfo }` 及标准资源/场景
跟随包，未包含 `29285` 或可识别的时长字段。因此当前可以确认：

1. 右上角数值由客户端本地对象每秒递减，服务端不会逐帧推送或绘制它；
2. 图层可显示的字段由 UI 组件布局选择，截图不能单独证明它是简单 `mm:ss`；本次
   初始化值与可见四位之间还需在组件布局／数值转换处继续对应，不能擅自解释为“8 分 5 秒”；
3. 现有 dynamic-NPC `30/1` 入口没有提供该初始化值，给该表增加 `duration`、由宿主
   启动计时或伪造画面都不会走正确契约；
4. 正确的后台控制点只能是能够被客户端场景 UI 组件装配链自然解析，并最终把目标值作为
   `0x0104C252` 第二参数传入的原生数据／事件。其包型或资源字段尚未确认，仍为
   `unresolved`。

## 2026-08-31：`min` 字段与下一次只读验证

调用 `0x0104C252` 前的 `0x01010702..0x01010736` 不是通用布局分支，而是
处理类型 `4` 记录的专门分支。它以 CBE 内嵌字符串 `"min"`（地址
`0x01010A88`）调用记录 getter，并在非零时将返回值原样作为第二参数经
虚方法派发；该派发的 return address 正是先前记录到的 `0x01010736`。

已捕获的梦境进入跟随包中存在 `1/27/4`，且其对象确有 `min` 字段；最新样本
`dream-instance-capture-0000b8ed-010-downlink.wt` 的该字段编码为 `0`。这与同次
日志中最终初始化的 `29285` 不一致，因而目前不能把该样本直接认定为计时对象的来源：
它可能来自早于捕获起点的同类记录，也可能是该 getter 读取的另一份客户端保存记录。

为区分两种情况，`CBE_TRACE_SCENE_NUMBERS=1` 现额外在两个固定 PC 只读记录：

| PC | 记录内容 |
| --- | --- |
| `0x01010718` | `min` getter 返回值及源记录指针。 |
| `0x01010734` | 派发前的接收对象、`min` 值和实际方法地址。 |

两者都只读取寄存器并写入既有 `scene-number-draw.log`，每类最多 32 条；不修改
客户机内存、寄存器、包、callback 或事件顺序。下一次正常进场后，这些记录将给出
`29285` 是包字段原值还是客户端记录值的第一处可验证边界。

后续复现已经给出该边界：两条独立源记录（`0x05001668`、`0x050014B0`）的 getter
均返回 `min=29285`，而派发点的接收对象是计时对象 `0x0500B57C`，目标方法直接为
`0x0104C252`。也就是说 `29285` 没有在这条调用链中被重新计算、换算或兜底，它就是
记录 `min` 的原值。

已捕获的 NPC 后续 `1/27/4` 的 `min:u8=0` 仍不能解释这两个源记录，说明需要覆盖
NPC 请求前的连接阶段。为保持取证最小化，启用既有
`CBE_CAPTURE_DREAM_INSTANCE=1` 时，客户端现在从启动起只记录每个下行 `1/27/4` 的
`min` 字段值、原始编码宽度和投递序号到
`logs/dream-instance-min-field.tsv`（上限 64 条）；不保存其他前置包的原始字节。
这将把最早的非零 `min` 与网络事件序号对应起来，同时不改变任何传输或客户机状态。

为把运行时源记录对应回该事件，在同一 opt-in trace 下另增加了
`0x01010716` 的调用前记录（记录列表索引、`"min"` key 地址和 getter 指针），并在
`0x01010718` 读取该记录的前 16 个字节。二者仍为只读、每类最多 32 条。其目的是确定
两个 `min=29285` 记录的类型和 getter 实现，而不是改变或构造任何客户机状态。

本次启动阶段的 `dream-instance-min-field.tsv` 只观察到两条下行
`1/27/4.min:u8=0`。但 CBE getter 的实际源记录头是
`{major=1, kind=27, subtype=4}`，并且 `min=29285`；该 getter
`0x01033CF2` 只是在该记录的字段表中按名称找到值后读取四字节整数。故可以排除
“当前两条下行 `min=0` 被客户端换算成 29285”，但尚不能判定非零记录的构造来源。

下一步新增的固定 PC `0x01033D40` 只观察 `1/27/4` 且 field name 为 `min` 的字段创建，
记录其 CBE caller、record、key 和编码类型（最多 16 条）。它比全局写监视更窄，可直接
将保存 `29285` 的创建点归因到网络 parser、资源/本地构造器或其他 CBE 逻辑。

第一次运行没有命中该 helper 的“记录头已为 `1/27/4`”过滤条件。这不能说明没有经过
helper，因为字段创建可早于 record header 初始化；该探针已收窄为仅匹配字段名 `min` 并
同时记录当时的三字 header 和 caller，仍维持 16 条上限。下一次运行由 caller 判定实际
构造路径。

放宽后仍未命中，故这两个对象没有走 `0x01033D40` 的字段创建 helper。当前探针改为在
`0x01010716` 读取 `0x01010594` 保存的调用栈：该函数的入口保存 LR 后固定分配
`0x444` 字节局部变量，因此此时 `SP+0x454` 是它保存的调用者。记录四个返回地址可以追到
装入／反序列化 `1/27/4 {min=29285}` 的调度链，而不监视全局堆写入。

## 2026-08-31：已定位 CBE 数据事件入口，待确认原始字段

校正后的保存 LR 为 `0x01012F7C`，它紧随 `0x01012E4C` 的中央数据事件分派函数中
`0x01010594` 的调用之后。静态反汇编显示 `0x01012E4C` 在第四参数等于 `7` 时，将第一

`(response, arg1, arg2, eventType)` 原样调用该 CBE callback；在这次链中第四参数就是
`7`。因此 `29285` 所在的 `1/27/4` 记录已可归属为 CBE 的数据事件解析结果，而不是
绘制函数或宿主合成的值。

现有远端下行观察仍只看见两条 `min:u8=0`，和 CBE 已使用的 `min=29285` 不一致。为把

探针：仅当 CBE 正在处理事件 `7`、响应缓冲区是结构完整的 WT 帧且其中有 `1/27/4` 时，
才记录该对象的 `min`、编码宽度、包长和对象序号（最多 16 条）。它不写入客户机内存、
寄存器、原始包、callback 或调度队列。下次同样的正常进场将判定非零值是否直接位于进入
CBE 的原始响应帧，或是更早事件保存后由当前事件重新装配。

## 2026-08-31：根因确认——`min` 的编码宽度错误

本次完整抓包与 CBE 入口探针给出了同一时刻的两份结果：

```text
事件 7，544 字节，1/27/4（对象序号 7）：min:u8 = 0
事件 7，114 字节，1/27/4（对象序号 2）：min:u8 = 0
随后 CBE 0x01033CF2 读取两条记录的 min：29285 (0x00007265)
```

这不是服务端给出 `0` 后被客户端换算成 `29285`。`0x01033B9A` 会按 WT
字段声明的长度逐字节复制字段内容；对当前包，`min` 的原始字段为：

```text
03 6D 69 6E 00 03 00 01 00
^  "min"     ^^^^^^^^--- 字段内容长度 3：00 01 00（u8 的 0）
```

而计时器专用 getter `0x01033CF2` 固定读取字段内容指针的 `+2,+3,+4,+5` 四个
字节，按大端组成 32 位值。三字节字段只有 `+2` 在其分配范围内，后面三个字节越界；
本次正好读到了相邻堆内容 `00 72 65`，于是得到 `0x00007265 = 29285`。这就是画面
显示 `08:05` 的直接原因，而非一个有意义的副本时限。

仓库后端中对应的构造点已经找到：
`src/server/mock_server_social.c` 的
`vm_net_mock_append_fb_target_result4_object()` 目前以
`vm_net_mock_put_object_u8(..., "min", 0)` 生成上述错误字段。CBE 对该字段的实际
契约是 32 位大端整数；后台应改为：

```c
vm_net_mock_put_object_u32(out, outCap, pos, "min", remainingSeconds)
```

例如 `remainingSeconds = 29285` 时，字段主体应为
`00 04 00 00 72 65`，完整 `min` 字段为
`03 6D 69 6E 00 06 00 04 00 00 72 65`。CBE 将该值原样写入计时对象 `+0x10`，
然后本地每约 1000 ms 减一；该对象到零时仅保持零值，本身不负责踢出副本、切场景或向
服务器发送到期通知。

因此后台控制方式已经确定：在进入/刷新梦境时所返回的 `1/27/4` 对象中，以 **u32**
编码 `min` 为希望客户端本地倒计时的秒数；传 `0` 则可靠地关闭/归零该计时值。不得继续
用 u8 编码该字段，也不应通过宿主侧改写客户机内存或另行绘制数字。

## 2026-08-31：当前模拟后台接入

当前模拟后台已经把 `min` 改由 `vm_net_mock_put_object_u32` 写出，即使为零也保持 u32
格式。计时秒数不再是进程环境变量，而是副本引导 NPC 的持久化配置：后台在“游戏内容
管理”编辑该 NPC，在“副本目标场景”同一区域填写“副本倒计时（秒）”。允许范围为
`0` 至 `86400`；`0` 时客户端正常显示 `00:00`，例如 `3605` 在入场时显示 `01:00:05`。

在 NPC 已确认副本传送、服务端写出 `WT 30/1` 的同一个入场路径中，后台将配置值复制到
该玩家的瞬态副本会话并记录服务端开始时刻。后续共享 `1/27/4` 构造器只对这个活动会话
计算 `max(0, configured_seconds - elapsed_seconds)`；普通场景、其他玩家和已离开副本的
会话固定发送 `u32(0)`。旧数据库会自动增加 `server_dynamic_npc_instances.timer_seconds`
列，默认值为零。

该设置目前控制客户端显示以及服务端返回的剩余值；CBE 的计时器归零后只保持零值，不会
自动离开副本。若要实施到期离场、结算或失败，仍需在该会话的权威副本状态机增加独立的
到期处理，不能依赖客户端归零。

`1/27/4` 是共享的 fb-target 结果对象，但其 `min` 现在从活动副本会话读取，因此后台可以
为不同的副本引导 NPC 分别配置不同秒数。player-3 当前的本地服务需要重启到这份构建后
才会出现后台表单的配置；修改本地工作区不会改变远端进程。

`fb-target-timer-field-regression` 回归目标覆盖无副本计时的零值、会话内的非零配置和经过
秒数，并验证出包的 `min` 按目标的大端 `u32` 解码。

运行时复现补充：player-3 切换到本地服务后进入梦境场景，右上角从原先远端服务的错误
`08:05` 变为 `00:00`。这证明客户端接收到了边界正确的零秒 `u32`；显示零值是 CBE 绘制
路径的正常行为，不表示后台仍在发送原来的伪倒计时。

## 2026-08-31：动态 NPC 保存崩溃的后台根因

首次将计时配置接入动态 NPC 后，后台保存暴露了两项先于客户端协议的服务端契约错误：

1. 多任务绑定查询必须以 `task_bindings` 聚合子查询产生一行 NPC 记录。加入
   `timer_seconds` 后，该 SELECT 的列数为 21；行解析器也必须在索引 20 读取计时秒数。
   错误的 22 列约束会把所有记录记为 `skipped`，启动日志表现为
   `dynamic_npc_db_load rows=0 skipped=...`。
2. `dynamic_npc_save` 的日志必须含有 `task_count`、`primary_task` 和
   `repeat_policy` 三个 `%u` 占位符。缺少其中一个会使后续的 `y` 坐标被当作
   `instance=%s` 的指针传给 `printf`，在保存已提交后造成服务端访问冲突。

修复只恢复数据库加载/日志格式的既有后台契约；没有修改 WT 包、CBE 内存、寄存器或

## 2026-09-01：归零后的处理边界

用户在本地 player-3 中观察到右上角倒计时达到 `00:00` 后没有任何后续反应。对实际
梦境更新函数 `JianghuOL.CBE:0x010104A2` 的 Thumb 反汇编给出直接结论：

```text
0x010104CE  r2 = [scene_state + 0x3C]       # 当前 min
0x010104D0  if (r2 != 0) --r2
0x010104D8  r1 = [scene_state + 0x3C]
0x010104EC  call timer_component.set(r1)    # 0x0104C252
0x010104EE  继续通用场景帧/计数逻辑
```

当 `r2 == 0` 时唯一的分支目标是 `0x010104D8`：仍以 `0` 调用计时组件，随后执行与
计时值无关的场景帧 bookkeeping。函数中没有针对零值的网络发送、场景传送、战斗结算、
弹窗或副本会话清理调用。因此 `1/27/4.min` 是**客户端显示用的本地分钟计数**，不是
“到期事件”；只下发它不能触发原生的副本结束流程。

本地成功进图的捕获还显示，归零期间持续出现的 `WT 2/1 { moveinfo }` 是十帧移动上传，
其已证实响应仅是同身份的空 `1/2/1` 确认。它不携带到期语义；把 `30/1`、未请求的
`27/4` 或猜测的结算对象塞进这个高频 ACK，会违反既有场景 callback/资源生命周期契约，
不能作为实现手段。

若产品需要“倒计时结束即离开、失败或结算”，后续处理必须新增为**服务端权威的副本到期
契约**，并先反向确认一个客户端已接受的触发响应：服务端以会话开始时刻和配置分钟数判定
到期；客户端在下一条已存在的请求边界上接收一个已证实可消费的到期/场景变更对象；其 parser
再自然发出离场或结算后的跟随请求。当前尚未捕获到这样的原版对象或 parser 分支，因此不能
在 `2/1` ACK、宿主定时器或客户端内存中强行触发。下一次取证应以 1 分钟实例运行至零为场景，
同时保留归零前后的 `scene_number_timer_commit`、原始 `2/1` 上下行和任何随后用户触发的
离场/结算请求，先确定原版可接受的到期协议。

### 已有的受控场景切换下行通道

这里的“主动”不能理解为服务端反向连接 player-3 并任意写入 WT 包：当前短连接传输始终由
客户端发起 `CBMS`，并只会通过 CBE 已登记的 callback/context 投递 event `7`。但已有
scene-sync poll 是经过运行验证的等价下行通道；客户端发起 poll 后，服务端可以返回非空
WT 数据。

地图石确认后的场景进入已经采用这个契约：确认包只保存目标，至少一个后续帧的
scene-sync poll 才返回 `30/1 {scene,posinfo}`。构造器
`vm_net_mock_build_teleport_stone_deferred_enter_response()` 调用既有的
`vm_net_mock_build_scene_channel_enter_combo_for_target()`；客户端随后自然发出目标场景的
`2/3`、资源和 `6/1` 跟随请求。这证明服务端可在下一次 poll 决定并下发场景进入，而不是
依赖未经验证的宿主事件注入。

因此，到期离场可采用同一模式：服务端会话达到 deadline 后标记一次性的
`pending expiry exit`；下一次 scene-sync poll 返回已经证实的 `30/1 {scene,posinfo}`；
再由目标场景的正常资源链完成切换。它仍不能混入 `2/1` ACK，也不能由计时显示归零时直接
调用 callback。实现前必须明确离场目标场景/落点，并补充梦境加载、战斗中与断线重连时
一次性状态的权威归属和清理规则。

### 已实现：到期后经 poll 返回进入前的世界锚点

本次将上述已证实的场景进入通道用于服务端权威到期处理，且没有为客户端增加反向连接、
宿主业务事件或客户端内存写入。动态副本会话在进入时冻结该角色的持久世界场景及坐标为
`transientInstanceReturnScene/X/Y`；副本自身仍是临时可见场景，持久角色锚点不会被进入副本
的 `30/1` 覆盖。于是当前到期的明确产品语义是：**回到进入副本前的位置**。

### 战斗中的到期边界

随后真实复现显示，到期点位于两次 `WT 4/2` 战斗回合之间。旧实现此时已发送 `30/1`；客户端能
回到目标世界场景，却没有可见 NPC。服务端的同一 `WT 6/1` 已记录 4 个 NPC 的非空 `27/11`，
因此不是目录缺失；首次偏离是场景切换跨越了仍由 battle screen 持有的 actor 生命周期。该生命周期
只会在原生战斗结果的 `25/5` 边界释放。

到期构造器现在检查当前会话的 `g_mockBattleSceneMonsterStartActive`。若战斗仍活动，仅记录一次
`transient_instance_timer_expired_wait_battle_close` 并保留已经归零的临时会话；不会下发 `30/1`。
战斗按既有 `25/5` 正常回到场景后，下一次 scene-sync poll 才发送一次退出 `30/1`，并继续既有
`2/3 -> 6/1` 的完整收尾与 NPC 种子链。该延后保持“时间已到”的服务端判定，但不把场景进入对象
错误注入到战斗 callback 中。

### 到期返回后的 NPC 二次请求

战斗延后后，客户端仍报告返回场景没有 NPC。现有捕获给出更早且可重复的协议边界：完整退出
`WT 6/1` 后，客户端主动发送 `WT 25/5`，其中包含显式的 `1/27/11` 与 `1/27/4`；之前服务端因为
全局“目录已播种”标记，对这次请求返回了空 `27/11`。这使第一次随 `6/1` 尾包到达的目录没有可供
重播的机会。

现在仅对“副本到期返回”会话，在 `6/1` 完整收尾后保存一次性目标场景标记。客户端的该次
`WT 25/5 + 27/11` 请求会得到返回场景的非空 `27/11 {npcnum,npcinfo}`，随后立即清除标记；普通
场景、普通重复请求和下一次传送仍维持空确认或原有目录生命周期。该操作响应客户端实际请求，且
目录仍由既有 `vm_net_mock_build_scene_npcinfo_blob()` 从场景配置生成。

## 2026-09-02：副本入口的合并移动上传

一次重新进入梦境空间的本地运行，在 NPC 服务回复 `WT 30/1` 后没有到达原先捕获的独立
`WT 2/3`。服务端记录的第一处偏离是一个 102 字节的复合 `WT 2/1`：

```text
1/2/1 { moveinfo } + 1/2/3 { maptype,mapID,exitID } + 1/27/11 + 1/7/42
```

原分发器只接受单独的 `2/1` 移动上传，或从 `2/3` 开始的场景进入请求，因此把整个复合帧记为
`unhandled` 并回空包；客户端随即停在场景加载，尚未发出资源完成的 `6/1`。这说明首次违反的是
请求边界的合包处理，而不是副本目标、计时字段、资源文件或到期退出逻辑。

`vm_net_mock_build_scene_enter_moveinfo_combo_response()` 只匹配上述精确四对象序列。它将前置
`2/1` 交给既有的 pending-scene 移动确认路径（不保存过期源场景坐标），并将后三个对象按既有
`2/3 + 27/11 + 7/42` 场景进入构造器处理；两段既有响应对象以原请求顺序拼回同一个 WT 响应。
未知对象、不同顺序、额外对象或普通移动帧仍不匹配，不会被泛化拆包。修复后日志应出现
`mock_scene_enter_moveinfo_combo`，其后客户端应自然进入资源 `WT 6/1` 跟随链。

本次修改已执行 `make -j2` 并成功生成客户端和服务端二进制；仍需以 player-3 重启后的真实入口
验证该精确日志及后续 `6/1`，不能仅凭构建成功认定加载链已完成。
