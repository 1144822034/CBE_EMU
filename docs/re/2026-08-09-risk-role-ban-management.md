# 风险角色管理：快速进入战斗审计与账号封禁

## 触发条件与原始证据

`vm_net_mock_role_record_rapid_battle_entry` 是挑战战斗和场景挂机战斗共用的
入口审计。它在 MySQL 事务中读取同一 `account_id + role_id` 上一次进入战斗的
数据库时间；当相邻间隔不大于
`VM_NET_MOCK_RAPID_BATTLE_ENTRY_WINDOW_MS`（3000 ms）时，才写入
`account_role_rapid_battle_entry_audit`。

因此后台“风险角色管理”直接读取这张审计表，而不从移动包、动画包、请求数量或客户端
本地时间推断风险。列表包含审计时间、账号、角色、相邻间隔、战斗入口、场景和怪物。

## 最早契约与处理方式

审计只是取证，原有设计明确要求不能改变合法战斗的响应、掉落或客户端战斗状态机。
封禁也不能写入 `accounts.password_value` 或角色快照：密码认证、角色状态和账号访问权是
三个不同的权威层。

新增 `account_access_bans`：

- 以 `account_id` 为主键，外键到 `accounts`；账号删除时随之删除；
- 保存封禁时间和固定原因 `risk:rapid-battle-entry-within-3s`；
- 封禁提交成功后才调用既有 `vm_mock_service_session_mark_offline` 清理队伍、交易、
  决斗、场景可见性、挂机与缓存；随后清空会话的 `accountId`，防止空凭据的标题登录
  重用旧会话；
- 同时注销该账号的用户中心 HTTP 会话；
- 原生登录认证和用户中心登录都会查该访问表。访问状态查询失败时拒绝登录，避免 MySQL
  异常期间意外放行已封禁账号。

服务端的游戏连接为逐请求传输，并没有可由后台向客户端发送的长期 socket。这里的“立即
断开”按真实服务生命周期实现为立即下线并作废账号绑定：之后的场景轮询和普通请求成为
无绑定请求，下一次凭据登录则被认证层拒绝。

- 静态链路核对：挑战和挂机入口均调用快速进入战斗审计；风险页只查询
  `interval_ms <= 3000` 的审计记录；封禁先执行 MySQL `INSERT ... ON DUPLICATE KEY
