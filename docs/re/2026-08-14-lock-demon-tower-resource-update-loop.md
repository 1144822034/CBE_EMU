# 锁妖塔资源更新循环

日期：2026-08-14

状态：修复已构建；待使用新启动的客户端复测。

## 触发条件

从传送石进入 `16锁妖塔_01.sce`。客户端在“更新资源文件”界面停留，且持续重复请求同一资源。

## 运行时证据

本次复现的服务端日志显示，以下资源均只请求一次且服务端完整返回：

```text
16锁妖塔_01.sce  413 bytes
b_16锁妖塔.sce   50 bytes
b_16锁妖塔.map   342 bytes
m_cave02.gif     3544 bytes
```

之后客户端反复从 `start=0` 请求：

```text
WT 18/7 name="16锁妖塔_01 .map"
totalsize=926, chunk=926, crc=4294959664, version=1
```

服务端每次都能从权威资源目录读取该文件，并没有 `mock_update_chunk_missing`。当前玩家缓存中也已出现前四个资源，唯独 `JHOnlineData/16锁妖塔_01 .map` 始终未落盘。因此资源内容不是缺失或损坏，首个偏离发生在客户端接收该名称后的本地文件路径解码阶段。

## 客户端和模拟器链路

| 层级 | 证据 | 语义 |
| --- | --- | --- |
| `江湖OL.CBE` `handle_update_chunk_response` (`0x0103741A`) | 读取 `totalsize`、`crc`、`version`、`type`、`name`、`data`，校验累积有符号字节和后调用写入 | WT 18/7 的响应字段及校验均由客户端消费 |
| `江湖OL.CBE` `WriteResBinToTempFile` (`0x01037000`) | 完整下载后调用 `LoadGameDataFromTemp("MMORPGTempbin", name, 0, 0)` | 使用响应的 `name` 安装资源到 `JHOnlineData` |
| `江湖OL.CBE` `LoadGameDataFromTemp` (`0x010368CA`) | 将目标构造为 UCS-2 路径 `\\JHOnlineData\\%s` | 名称以 UCS-2 形式交给宿主文件回调 |
| `src/vmFunc.c` `vm_path_looks_like_ucs2_le` | UCS-2 ASCII 白名单未允许 `0x20` 空格 | `16锁妖塔_01 .map` 被错误判定为非 UCS-2，随后回退到字节字符串读取，路径在第一个 UCS-2 NUL 截断 |

## 根因

锁妖塔第一层地图的权威文件名确实包含 `.map` 前的一个 ASCII 空格：

```text
16锁妖塔_01 .map
```

该名称由 CBE 正确放入 WT 18/7 请求与下载完成后的 UCS-2 目标路径。模拟器的 UCS-2 路径判定却不接受合法的路径字符空格，导致写入回调无法得到完整路径。文件未安装，下一次资源访问再次触发相同下载，形成更新界面循环。

## 已排除

- 不是服务端资源不存在：服务端每次成功读取并返回 926 字节。
- 不是资源内容与既有副本不同：历史隔离缓存中的同名地图与权威资源 SHA-256 一致。
- 不是场景目标或传送坐标错误：目标严格解析为 `16锁妖塔_01.sce`，落点为 `(221,336)`。
- 不应通过服务端重命名、删空格、伪造成功或停止响应来掩盖问题；客户端原始场景资源要求的文件名包含该空格。

## 修复点

仅在 `vm_path_looks_like_ucs2_le` 的 ASCII 路径字符集合加入空格。该修改位于真正拥有“CBE UCS-2 路径 → 宿主路径”契约的客户端模拟器层，保留原始资源名和原始 WT 18/7 协议。

## 验证计划

1. 构建后清除仅该客户端缓存中的 `16锁妖塔_01 .map`，避免把已有文件当作下载成功。
2. 进入锁妖塔，确认一次 18/7 响应后该文件以 926 字节落盘。
3. 确认不再重复请求该文件，资源更新界面退出并进入场景。
4. 复测不含空格的锁妖塔背景资源，确认路径判定未改变既有行为。

## 构建结果

`make -j2` 已通过，同时重建 `bin/main.exe` 与
`bin/jh-online-server.exe`。正在卡住的旧客户端进程已经加载旧代码；需重新启动客户端后才会使用该修复。
