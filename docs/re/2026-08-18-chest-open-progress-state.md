# 黄金宝箱开启进度状态

Date: 2026-08-18  
Status: 原生 `7/15` 奖励/提示响应已实现；客户端运行时复测待完成

## 触发与最新运行时证据

在背包中开启黄金宝箱（`524`）后，宝箱、钥匙和奖励状态均已下发，但界面仍被一个
无法自动消失的层阻塞。最新复现时服务端明确输出：

```text
mock_chest_open ... response=7/4-complete+7/11+7/11+7/7-type1+7/37
```

这证明带 `7/4` 的响应已经到达真实客户端；`7/37` 仍会在 mmGame 奖励增量之后建立
阻塞层。旧进程、旧二进制和传输层对象顺序已排除，剩余偏离点位于 mmGame 的完成时序。

## 客户端契约与第一次偏离

- `JianghuOL.CBE:HandleItemOperationResponse(0x01033544)` 的 subtype `4`
  分支负责结束本次物品操作等待，不创建成功消息框。
- `JianghuOL.CBE:HandleItemAcquire(0x0101191A)` 先复制 `msg`，再无条件调用
  `(*manager + 140)(msg, 0, 0, 20)`，之后才读取 `result`；只有 `result=0` 才继续
  插入物品。
- manager 方法 `+140` 对应 `ui_show_message_box(0x010103F4)`。它把
  `Global_R9 + 23876` 置为活动，并把第四参数写入 `Global_R9 + 23912`。函数中没有
  倒计时清除分支，因此 `20` 是模式参数，不是显示帧数。
- 所以 `7/37 result=1` 只能阻止重复入包，不能阻止消息框建立。此前响应先由 `7/4`
  正确结束等待，随后又被 `7/37` 建立的阻塞框覆盖；这解释了去掉 `7/37` 后仍需继续
  追踪 mmGame 等待状态的原因。
- `mmGameMstarWqvga.cbm:sub_11CE(0x11CE)` 将 `7/7` 交给
`sub_D04(0x0D04)`；奖励继续使用 `type=1` 单次增量。宝箱使用按序号的 `7/11`，避免
`type=2` 在 category 15 管理器中泄漏物理槽；钥匙由 `7/15 {box,key}` 原生路径扣一次，
不能再附加钥匙 `7/11`。

此前的第一次偏离发生在奖励增量对象：`sub_D04` 在 `0x1094` 将共享网络状态重新置
为等待中。`sub_D04` 的 `type=3` 分支位于 `0x116C-0x1190`，会执行模块完成回调并
清除该状态；它必须排在奖励 `type=1` 之后。该分支仍先读取 `iteminfo`，所以零行终结
对象使用合法的单字节流 `0x00`，而不是省略字段或发送空 blob。

## 修复

`7/7 type=1 + type=3` 修复了进度状态，但用户随后复测确认奖励文字只进入聊天列表，
背包界面没有即时提示。继续检查主固件后发现，原调查只看了
`HandleItemOperationResponse(0x01033544)`，遗漏了
`HandleShopBuyItem(0x01025AE6)` 的原生 `7/15` 宝箱成功分支。该分支自行插入奖励，
并使用固件模板“获得%d个%s”显示本次结果。

`vm_net_mock_build_chest_open_response()` 的当前成功包严格为：

```text
1/7/4   result=1                 结束操作等待
1/7/11  chest sequence/count     更新或删除所选宝箱行
1/7/15  result=1,total=1          单次加入抽中奖励并显示固件原生提示；钥匙在原生路径中扣一次
```

`7/15 iteminfo` 每行是 `itemId:u32, seq:i16, count:u32, common extra`，没有
`7/7` blob 的前置行数。它替换原 `7/7 type=1`，因此奖励不会重复；同时也不再进入
mmGame `sub_D04` 的等待置位分支，所以删除了仅为该路径准备的 `type=3` 终结对象。
系统聊天奖励绕行已移除。成功包继续拒绝 `7/1`、`16/2`、`18/1`、`20/1`、
`25/11`、`7/37` 和消费项 `7/7 type=2`。修复没有写客户端内存、寄存器、PC/LR、
screen 状态或输入队列。
