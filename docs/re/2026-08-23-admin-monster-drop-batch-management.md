# 后台怪物掉落批量管理

## 目标

怪物管理页原先把“智能分配装备掉落”的三个概率字段直接放在目录侧栏，且只能通过逐只编辑掉落来调整指定物品。本次将该功能收敛到“怪物掉落管理”弹窗，并在同一弹窗增加指定物品的批量增删配置。

## UI 与请求契约

- 目录侧栏只保留“打开掉落批量管理”按钮。
- 弹窗的“智能分配装备掉落”沿用 `assign-monster-equipment-drops`，原有品质 0、1、2 的概率字段保持不变。
- “批量增加或删除指定掉落”提交 `batch-configure-monster-drops`：
  - `drop_batch_mode`: `add` 或 `remove`；
  - `drop_batch_family`: `all`、`boss`、`nonboss`；
  - `drop_batch_level_min` / `drop_batch_level_max`: 1 到 255 的闭区间；
  - `drop_batch_item_ids`: 1 到 12 个去重的物品 ID；
  - `drop_batch_rate`: 仅增加时使用，范围 0.01 到 100，最多两位小数。

物品选择器直接使用后台已有的可显示物品目录；前端限制至 12 项，服务端仍会重新解析、去重和校验目录存在性。

## 持久化与边界

服务端先读取全部有效怪物行，再按类型和等级范围在内存中规划本次操作。增加不会重复加入已存在的物品；每只怪物超过 12 个掉落槽时，无法放入的条目会被计入结果并跳过。删除只移除明确选中的 ID，包括管理员明确选择的任务材料。

`server_scene_battle_monsters` 中引用的场景战斗怪拥有独立作者配置，智能分配与本批量操作都会将其排除。操作日志和回显会给出命中、更新、增加/删除、已存在、槽位不足和被保护场景战斗怪的数量。

所有受影响怪物的 `server_monsters` 与 `server_monster_drops` 更新在一个 MySQL 事务中完成；只有 `COMMIT` 成功后才发布内存覆盖，失败则回滚，避免部分掉落配置进入运行中战斗状态。

## 回归边界

`scripts/admin-request-length-regression.c` 检查共享后台脚本包含弹窗、操作模式、首领筛选和物品选择字段，并以无数据库夹具验证首领/非首领与等级闭区间匹配。完整构建使用 `make -j2`。
