# 交易限制物品：固件与服务端调查

## 结论

- 固件资源确实给 `item.dsh` 和 `equip.dsh` 定义了 `绑定属性` 列；但现有
  数据中其取值和物品类型并不构成足以确认的“不可交易”清单，不能把该列直接
  自动迁移为交易禁令。
- `JianghuOL.CBE` 的交易报价请求只上传背包 `seq` 和交易数量，不上传绑定/
  可交易标记。因此可交易性必须由服务端按实际背包物品 ID 判定，不能信任
  客户端筛选。
- 可以安全增加一张显式的 MySQL 配置表，并在后台维护。规则应同时应用于报价
  和最终成交，避免物品在报价后变为禁交易时仍可被成交。

## 固件证据

### 资源表

`bin/JHOnlineData/item.dsh` 的 33 列中第 8 列（零基列 7）是 `绑定属性`；
`bin/JHOnlineData/equip.dsh` 的第 5 列（零基列 4）也是 `绑定属性`。

当前 item 表的该列只有 `0` 与 `1` 两种值，但值为 `1` 的条目同时包含各类
回复药和普通材料；equip 表几乎都是 `0`。这只证明它是资源元数据，不足以证明
`0` 或 `1` 哪一值等同于交易禁令。

### 交易请求与结果

`JianghuOL.CBE:0x01022D4E`（`SendTradeSellReq`）构造 `WT 1/21/5`：

```
num        : 已选格子数量（最多 10）
trademoney : 铜钱
iteminfo   : 重复 { backpack_seq, count }
```

没有发送 item ID、绑定位或可交易位。`JianghuOL.CBE:0x01025AE6` 处理
`1/21/5` 的 `result`，而 `0x01027726` 继续处理 `1/21/7`、`1/21/8` 的交易
确认/结算结果。客户端已原生处理 `1/21/5 result=3` 的失败分支，因此服务端
应复用该既有失败结果，不发明新的字段或伪造成功响应。

## 服务端证据

- `src/server/mock_server_guild.c::vm_net_mock_trade_validate_offer` 已按
  背包序号解析真实物品 ID、数量和装备实例数据。
- 该函数既在初始报价 `1/21/5` 使用，也在
  `vm_mock_service_trade_commit` 前再次使用。这是唯一合适的强制点。
- `src/web_admin_server.c` 已有公共物品选择弹窗和 DSH 目录，可直接复用，
  不需要从客户端传入物品属性。

## 最小实施方案

1. 增加 `server_trade_restricted_items(item_id PRIMARY KEY, created_at,
   updated_at)`；表中存在即禁止交易，删除即恢复可交易。
2. 在物品目录模块缓存此表，并为后台保存/删除立即更新缓存。
3. 在 `vm_net_mock_trade_validate_offer` 中拒绝表内物品；由于最终成交复用此
   验证，规则会覆盖报价与成交两阶段。
4. 在“商品管理”中增加“交易限制”页面：使用现有物品搜索选择器添加条目，并
   显示当前列表及来源表的 `绑定属性` 原始值作为参考，不自动解释或启用它。

## 验证

1. 将一个背包中的普通物品加入限制清单，报价时应得到原生 `1/21/5 result=3`，
   且对方不收到报价。
2. 删除规则后，用同一物品重新报价，应正常进入双方确认流程。
3. 在已报价后再加入限制，最终确认应被第二次验证拦截，不发生背包或金钱变动。
