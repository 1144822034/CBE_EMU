## 重要更正

原 `docs/re/2026-07-11-nearby-player-actions.md` 把 `4/14` 标注为「切磋请求」。
对二进制 `江湖OL.CBE` 的静态取证证明：客户端内部文案统一使用**「决斗」**，
不是「切磋」。相关字符串（GB2312）：

- `0x102e850` 区域 → "斗请求已发送"（发起成功提示）
- `0x102e838` → "城市中不允许决斗!"
- `0x102e85c` → "你不能与自己决斗!"（"务器限制使用决斗!" 实际为 "服务器限制使用决斗!"）
- `0x102e888` → "地图不能决斗!"
- `0x102e8a8` → "该玩家是队员"
- `0x102e89a` → "对方已发送"

因此 `4/14` = **玩家间决斗（PK / duel）请求**，文档命名应改为「决斗」。

## 请求侧（已确证）

发送器函数：`江湖OL.CBE:0x0102E624`（二级玩家操作菜单的决斗项）。
统一网络发送器：`0x010103F4`（设置 `[r4,#0x60]=1` 等待响应标志，调用 `[r4,#0x64]` 发送函数，走真实 TCP 通道）。

构造请求对象（见 `0x0102E6F6` 起）：

- `major = 1`
- `kind = 4`        （`movs r2, #4`）
- `subtype = 14`    （`movs r3, #0xe`）
- 字段 `id`         （`adr r1, #0x114` → "id" 字符串，`r2 = 目标角色 id`）

即 WT `4/14 { id }`，与 mock-server 检测器 `vm_net_mock_is_challenge_interaction_request`
（`src/mock-server.c:22609`，要求 `object.kind==4 && object.subtype==14 && 有 id 字段`）完全吻合。

发送前的本地前置校验（顺序，见 `0x0102E624` 全函数）：

1. `0x0102E636` 比较某状态 `==1` → 可能弹提示后返回（已在决斗中？）
2. `0x0102E64e` 比较 `0x47*16` 处状态 `==1` → 弹确认框
3. `0x0102E66e` 比较 `0x4f*16+0xe` 处状态 `==4`（`beq 0x102e686`）→ 调用 manager 传字符串"斗"，
   这是**决斗状态机**的一个分支（状态值 4 可能代表「已收到对方决斗邀请 / 等待接受」）
4. 检查目标在线（`blx [base+0x81]+0x30` 返回 0 → 离线）、是否队员、是否自己
5. `0x0102E6F6` 构造并发送 `4/14`

## 响应侧（待动态 IDA 取证）

`0x0102E624` 发送后客户端置「等待响应」(`[r4,#0x60]=1`)。但顶层 WT 响应分派器
`0x01014B14`（按 **外层 kind** 分派：kind=1 / 14 / 20 / 21 / 2 / 15 / 0x11...）
**不含 kind=4**，其内部 kind=14 分支处理的是「挂机状态」(字符串 "你处于挂机状态")，
kind=15 分支处理的是 NPC 对话 ("好，请问需要什么帮助?") —— 均非决斗。

推论：决斗响应与交易 `21/1`、组队 `5/1` 同构，应是**服务端经 event-7 场景同步轮询
向目标端投递一条「决斗邀请」下行**，目标端弹确认框 → 回 `接受/拒绝` → 发起端收到结果。
但以下 WT 头尚未从二进制静态定位（函数含 jump table，Capstone 线性反汇编失同步）：

- 目标端收到的「决斗邀请」下行 WT 头（疑似 `4/13` 或 `4/15`，需与 `21/2`/`5/2` 对称验证）
- 目标端「接受/拒绝」回包（`id` + `result:u8`）
- 发起端收到的「接受/拒绝结果」下行（疑似 `4/15` 或 `4/13`）
- 双方进入同一场战斗的开场包（复用怪物战斗 `1/4/5` 或独立 `4/x`？）
