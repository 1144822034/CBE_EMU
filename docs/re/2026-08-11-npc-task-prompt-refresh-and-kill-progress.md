# NPC 任务图标与击杀目标状态同步

Date: 2026-08-11

## 触发

欧冶子可成功发放“挑战小猴子”任务，但接取后头顶没有灰色问号；击败小猴子后
没有可提交标识，重新对话也没有“提交任务”。

## 首个偏离

`JianghuOL.CBE:sub_104726C(0x0104726C)` 的 case 11 只消费接取结果和单条
`taskinfo`，不会重建活动任务表或调用 `scene_refresh_interact_prompt_types`。相反：

- case 1 逐条反序列化完整活动任务记录，依据进度把任务状态归为进行中/已完成，并对
  每条调用 `scene_refresh_interact_prompt_types`；
- case 14 重建可接任务候选，再调用同一刷新路径。

服务端此前在接取成功后仅下发 `6/11`，因此原有感叹号被对话流清除后，不会转换成
进行中的灰色问号。

更早的权威状态错误发生在战斗结算：
`vm_net_mock_task_progress_after_battle()` 仅在某件战利品实际进入背包时才被调用。
小猴子没有掉落，或本次掉落未命中时，击杀任务永远停在 `task_state=1`、进度 0；因此
服务端正确地不会生成提交项。若一场战斗有多个掉落，该旧位置还会把同一击杀重复计数。

## 修复

1. 接取成功的 `6/11` 后，追加客户端既有 `6/1` 活动任务表和 `6/14` 候选任务表，顺序为
   `6/11 -> 6/1 -> 6/14`。没有伪造客户端状态。
2. 每次首次成功结算的战斗胜利，独立调用一次任务击杀进度；每个实际掉落仅更新物品
   条件，不再重复累计击杀条件。
3. 任务从进行中变为已完成后，给当前可见场景的下一次正常 service poll 置位既有
   `taskPromptRefreshPending`，由该 poll 下发 `6/1 + 6/14`。场景已变更时既有逻辑会取消
   该刷新，不会把旧场景标识写进新场景。

提交操作仍严格依据 `task.receiver == 当前场景 NPC displayName` 授权；服务端不会因为
任务从欧冶子接取就允许其他 NPC 提交。

## 本次配置修正

运行时记录显示小猴子战斗已经胜利，而随后欧冶子的对话仍为
`task_options=0`。核对 `server_tasks.task_id=100001` 发现该任务的 `giver` 和
`receiver` 都是旧测试 NPC 名称“测试”，与绑定该任务的 `actor_id=20020`（欧冶子）
不一致。这不是客户端图标或对话包的问题，而是任务交接配置违反了上述严格匹配契约。

已将该任务的发放人与提交人都更正为 GBK 编码的“欧冶子”。任务目录在服务端进程中
缓存；通过后台任务管理保存会立即 reload，直接修正数据库后则需要下一次服务端启动才会
装入新配置。既有角色的完成状态不需要重置。

## 验证

构建后人工路径：欧冶子接取任务，确认灰色问号；击败小猴子，确认任务状态为完成、
欧冶子显示完成问号；与欧冶子对话应出现“提交<任务名>”。服务端应依次记录
`mock_task_accept_prompt_refresh`、`mock_task_battle_progress ... state=2` 和
`task_prompt_refresh_deliver`。
