# 好友删除的页面刷新契约（2026-08-21）

## 卡点与首次偏离

在好友列表确认删除后，客户端永久显示进度条。当前服务日志记录的同一个上行 WT 包为：

```text
unhandled wt=10/9 len=53 objects=1 first=1/10/9:11,1/10/1:28
```

其中第一个对象是 `1/10/9 { id:u32 }`，11 字节 payload 与既有 `id` 的 tagged-u32 编码精确一致；第二个对象是正常的 `1/10/1 { index:u32, pageSize:u8 }` 好友页刷新（其独立请求长度为 37）。此前 dispatcher 没有处理这个有顺序依赖的双对象事务，直接零回复；这是等待层未被清除的首次偏离，而不是进度条绘制问题。

## 客户端取证

本地 `江湖OL.CBE` 的 `net_business_response_dispatch(0x01012E4C)` 将 kind 10 交给
`0x010114FC`。该函数对 subtype 3、4、5、6、25、26 有显式分支，**没有** subtype 9 的下行分支。因此不能臆造 `10/9 { result }` 来作为删除完成回包。

好友页面的已确认回调 `HandleFriendInfoResponse(0x0102FF54)` 则消费 `10/1` 的
`allpgs:u8` 和 `friendinfo` 行流。删除点击随即组合发送 `10/1`，表明客户端要求用这条原生页面结果完成页面更新与等待生命周期。

## 服务端契约与修改

服务端只接受恰好两个对象、且顺序为：

```text
1/10/9 { id }
1/10/1 { index, pageSize }
```

它先以当前 `(account_id, role_id)` 和目标 `role_id` 查找已有好友关系；歧义 role id、非好友或持久化失败均不修改数据。有效删除在一个 MySQL 事务中同时删除正反两条 `friendships` 记录，提交成功后才替换内存好友快照。随后无论动作是否获授权，均以当前权威快照构造**唯一**的 `1/10/1 { allpgs, friendinfo }` 页面结果：成功时列表已移除该行；拒绝或持久化失败时列表保持不变。这不是伪造成功，而是该页面查询真实读取到的状态。

未向客户端内存、寄存器、PC/LR 或 CBE/CBM 指令写入任何数据。

## 验证清单

1. 构建后，以至少一名好友的角色点击删除并确认：日志为 `builtin-friend-remove`、`mock_friend_remove ... response=10/1`，进度条自然消失，目标行消失。
2. 重新登录删除方和被删除方：双方好友页均不再显示此关系，证明双向持久化。
3. 对不存在的行或重复点击：页面仍由 `10/1` 自然刷新，日志 `removed=0`，不删除其他好友，也不出现未处理 `10/9`。
