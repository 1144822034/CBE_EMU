# NPC 玄晶合成服务（2026-08-27）

## 结论

已新增后台可选的 NPC 服务 `11: 玄晶合成`。管理员可在原生或动态 NPC 的“可选服务”中勾选它；这不会自动修改已有铁匠 NPC 的配置或玩家背包。

服务规则是：`900`（玄晶碎片）消耗 10 个得到 `901`（一级玄晶）；`901`（一级）至 `915`（十五级）各消耗 3 个同级玄晶，得到下一级。输出恒为输入 ID 加一，因此可得到 `901` 至 `916`（十六级）；十六级玄晶不能继续合成。

`10:1` 碎片配方和 `3:1` 同级配方均是本次需求指定的服务规则，而不是声称已从原版固件还原出的配方数量。`bin/JHOnlineData/item.dsh` 的直接资源证据仅为：

- `900` 的描述为“玄晶的碎片，可在铁匠处合成玄晶”。
- `901` 至 `916` 的描述为“可在铁匠处合成高级玄晶”。

在发现原版合成请求、配方表或运行时抓包前，不能将这个数量或碎片到一级的比例标注为固件事实。

## 客户端与服务端契约

客户端沿用已验证的 NPC 对话流程：首次选择和后续选择均为 `WT 26/1`、对象 `1/26/1`、字段 `{type=2,id=...}`。客户端 `ParseNPCDialogData` 已处理普通 `action=1` 行；本服务只在服务端私有的 `id` 高字节命名空间中增加了两个值：

- `0xf8000000 | page`：打开玄晶列表；
- `0xf9000000 | sourceItemId`：选择一种输入玄晶并进入数量列表；
- `0xf9000000 | (quantity << 16) | sourceItemId`：选择 `1..10` 份并进入确认。

确认和取消复用已有的 `0xf0000001` / `0xf1000001` 一次性事务动作。确认上下文绑定角色、NPC、场景、该 NPC 当次实际展示的服务掩码、输入物品、选择数量与总材料数；确认读取即清除，不能重放，也不能跨 NPC 或跨场景使用。

`2026-08-27` 的实际服务端日志证明了原先“预约下一次背包查询”的假设不成立：成功的 `26/1` 响应记录为 `objects=1 inventory_sync=not-applicable`，虽然随后记录了 `mock_backpack_role_list_pending source=npc-crystal-synthesis`，但紧接着没有原生 `17/1` 或 `7/42` 背包查询来消费该标记。因此角色数据已经保存，客户端背包画面却保留旧值；第一次偏离是在成功响应没有携带可由固件立即解析的背包增量。

用户在 `901 → 902` 的真实路径上进一步验证：输入一级玄晶每次都减少 3，说明输入 `7/11` 已生效；二级玄晶的显示数量却未变化，说明只用 `7/15` 奖励增量不能可靠地替换一个已存在的客户端堆叠。成功响应因此改为：`1/26/1` 完成对话，`1/7/11` 用输入序列更新或删除材料堆叠，`1/7/15` 以选定的输出数量创建/通知输出玄晶，最后再以输出物品的序列发送 `1/7/11` 及其持久化后的最终数量。最后一个对象只更新已存在的行，不是第二次奖励；它使二级及更高玄晶的可见堆叠与已保存数量一致。

它明确不发送 `7/7`：`JianghuOL.CBE:0x01033544` 已证实 `7/11` 按序列更新正数数量、零数量走删除路径；`JianghuOL.CBE:HandleShopBuyItem(0x01025AE6)` 已证实 `7/15` 是增量获得通道。该四对象的组合是基于这些 parser 契约、原先“无后续查询”的运行时证据以及上述真实客户端负证据的服务端修正；回归测试锁定字段和顺序，但仍须在隔离客户端路径上继续验收固件实际画面刷新。

## 事务边界和失败条件

合成先在角色背包的内存快照中消耗该输入对应的 `10 × quantity` 或 `3 × quantity` 个材料，再尝试加入 `quantity` 个固定输出。任一步失败（材料不足、背包空间/堆叠限制、序列分配失败）都会恢复完整快照，不会丢失材料。成功后只持久化一次最终角色快照；持久化后还会校验输出物品和序列，不满足时保存恢复快照并返回失败。

管理员配置继续经过既有 `server_npc_services` 验证：服务种类必须在 `1..VM_NET_MOCK_NPC_KIND_MAX` 内，不能由后台提交任意客户端 action 或 opcode。新增种类后，原有的通用服务多选表单、权限掩码、动态 NPC 与原生 NPC 覆盖流程会共同覆盖它，无需数据库迁移。

## 回归覆盖

`scripts/npc-crystal-synthesis-regression.c` 覆盖：后台服务默认投影、私有 opcode 白名单、首层从“合成一级”到“合成十六级”的列表与分页、`1..10` 数量边界及编码、`900→901` 的 10:1 配方、`901→902` 的 3:1 配方、确认上下文一次性消费、输入材料不足或数量越界不修改背包、`916` 不可继续合成，以及成功响应严格为 `26/1 → 7/11(输入最终数量) → 7/15(输出增量) → 7/11(输出最终数量)`。回归中的 `901×9 + 902×4` 场景断言选择数量 `2` 后分别为 `901×3 + 902×6`，包括两个序列、批量奖励和最终数量。它不连接 MySQL、不启动监听器、不运行或修改客户端二进制。
