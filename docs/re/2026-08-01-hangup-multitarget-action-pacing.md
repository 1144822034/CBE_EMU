# 场景挂机多目标战斗：首个死亡动作重复

## 触发条件

2026-08-01 的手工复现中，在场景挂机自动战斗开始后的三怪战斗中，玩家击杀第一只怪物后，客户端持续播放该怪物的死亡动画，未继续播放其余怪物反击或推进下一次自动出招。

客户端操作与验收由用户执行；本调查只读取了该次运行留下的 `bin/server_out.txt`。

## 链路与证据

1. 场景挂机以 `2/10` 启动战斗；日志证明本次初始化为 `enemies=3`，并下发战斗开始响应。
2. 自动开关的 `4/11 type=1` 只切换客户端原生自动 UI。`mmBattleMstarWqvga.cbm` 的 `BattleMenu_SelectOption(0x5F78)`、`BattleScene_HandleInput(0x6258)` 及 `HandleServerBattleCmd(0x7BD0)` 显示：客户端不会为每个物理攻击发送一个新的 `4/2`；服务端必须在异步轮询中发送下一份 `4/6`。
3. `HandleBattleActionMsg(0x6EB0)` 把 `4/6.actionnum` 的每条 `actioninfo` 分别写入固定动作队列；`DrawBattleSceneBg(0x4BE8)` 逐条消费，其中 type 3（死亡）进入独立的死亡动画回调。因此 `actionnum` 是多个顺序动作，不是可以整体按一个动画周期处理的元数据。
4. 首次自动动作的服务端日志为 `actions=4`：玩家攻击 slot 0、slot 0 的死亡 type 3、另外两个存活怪物的反击。该条是在 tick 121 投递；旧调度器在 tick 131（仅 10 ticks / 1000 ms）又发送下一条 `4/6`。第一次四条动作尚未全部由客户端消费，第二份动作列表已经进入 parser。这是首次偏离点。
5. `HandleServerBattleCmd(0x7BD0)` case 6 只把 `4/6` 交给 `HandleBattleActionMsg` 并切换战斗阶段；动作队列清空时没有客户端上行确认。因此不能等待一个不存在的 ACK，也不能固定按“每包一秒”推进。

已排除：

- 敌人槽位映射错误。该轮日志的敌人 HP 槽依次为 `20/20/0`，死亡 actor 为 wire 0；下一轮为 `0/20/0`，与 N=3 的客户端槽位映射一致。
- 把死亡动作改为伪造的普通伤害动作。type 3 有单独的客户端 parser/回调契约，不是可互换字段。

## 根因

自动战斗调度器把一份 `4/6` 视作一个一秒的原子动画，而客户端把其中 `actionnum` 条记录视作顺序动作队列。多目标击杀包同时含攻击、死亡和多个反击记录时，下一份 `4/6` 在前一份队列消费完毕前抵达，造成死亡动画状态被后续动作覆盖/重入。

## 修复

`vm_net_mock_append_battle_action6_object_ex` 在完成主 `4/6` 时记录本次实际写入的 `actionnum`。自动调度器在同一次内部 `4/2` 构建返回后立即读取该值，并将下一次到期 tick 设为：

`max(actionnum, 1) * 1000 ms`

该观察值仅在同一请求构建栈内使用，不跨角色或网络事件保存。0 条的合法 no-op `4/6` 保持原有一秒节拍。日志新增 `actionnum` 与 `delay_ticks`，供手工复现直接核对；每个动作阶段后还保留一个 100 ms 调度帧，使网络事件不会恰好与最后一个动画完成回调处于同一帧。例如四条动作应显示 `actionnum=4 delay_ticks=41`（调度帧为 100 ms）。

本修复不改变死亡动作与存活怪物反击在同一 `4/6` 中的既有顺序，因为目前客户端和已实现协议只证明它们分别是队列条目，尚无证据证明应调整顺序。

## 手工验证范围

1. 开启挂机，遇到三只怪物；击杀第一只后，死亡动画只播放一次，随后继续其余怪物动作并进入下一次自动出招。
2. 检查服务端日志：含首个击杀的 `mock_battle_auto_action` 应有 `actionnum=4 delay_ticks=41`，下一次自动动作不得在该到期 tick 前下发。
3. 覆盖单怪、未击杀、多怪全部击杀、手动取消自动战斗以及一场战斗结束后进入下一场，确认不会引入自动退出或加载停滞。

仍未知的风险：若某个特定资源的死亡动画实际超过一个原生自动阶段，日志已可证明输入间隔；下一步应保留该次原始 tick/包并按客户端该资源的动作回调继续取证，而不是再任意增加全局延迟。
