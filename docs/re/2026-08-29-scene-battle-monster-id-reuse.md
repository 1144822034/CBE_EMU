# 场景战斗怪：复用怪物 ID 与多坐标

日期：2026-08-29

## 触发条件与首个偏离

后台“场景战斗怪”表已经以 `(scene, monster_id, pos_x, pos_y)` 作为唯一
位置键，原始 SCE2 kind-3 编译器也会逐条保留 actor ID 与 X/Y。然而管理页面
新增草稿时总是用参考怪物生成新 ID，已保存草稿的 ID 又被渲染为只读。因此同一
怪物不能由管理员明确地配置到第二个坐标，且无法调整已保存条目的 ID；首个偏离
在后台表单和保存分支，而不在 CBE 客户端或 SCE2 格式。

客户端普通碰撞的 `4/1` 请求包含实时 scene-node `index`、`posx` 和 `posy`。
服务端保留该元组启动 subtype-5 场景战斗；不会按同 ID 的首个 SCE 节点替换它。
因此相同 actor ID 的不同坐标在客户端和正常碰撞战斗路径中具有独立身份。

## 修复契约

- 新增草稿可选择已有“复用怪物 ID”；该选择与“参考怪物”互斥。复用只写入新的
  场景坐标条目，绝不复制或改写既有怪物属性、掉落或其他草稿。
- 若未选择复用 ID，则保留原有参考模板流程：分配新 ID，并复制模板属性与掉落。
- 已保存草稿的怪物 ID 使用可编辑选择器，但只能改为当前怪物目录已知的 ID。这避免
  把缺少属性、掉落与任务匹配契约的裸 ID 写入 SCE2。
- 保存与更新都会把数据库唯一键冲突转为明确提示；只有相同场景、相同 ID、相同
  坐标会失败。相同 ID、不同坐标是有效配置。

## 验证

- `scene-battle-monster-field18-regression` 在同一基础 SCE 内编译两条相同 ID、
  不同坐标的草稿，检查两条 kind-3 记录都存在，并验证重新从基础资源构建的字节
  完全一致。
- `admin-scene-battle-monster-layout-regression` 检查页面同时输出复用 ID、参考
  怪物、可编辑 ID 与多坐标说明；该回归在关闭的本地 MySQL 端口下运行，不读取或
  迁移用户的数据库。

本改动只调整服务端管理数据、SCE2 部署和后台校验；客户端 CBE/CBM、客户内存、
寄存器及网络包投递均未修改。
