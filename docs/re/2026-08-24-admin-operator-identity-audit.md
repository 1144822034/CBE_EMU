# 后台多账号登录与操作人审计

状态：已实现，待部署时执行 MySQL 迁移并进行人工后台验收。

## 触发条件与首个违反的契约

旧版后台只从 `server_admin_config(config_id=1)` 读取一份共享密码，并把所有成功登录
浏览器视为同一个进程级 `cbe_admin` Cookie。多个工作人员同时操作时，登录身份没有
独立归属；`server_admin_operation_logs` 也只有目标账号，无法证明一条人工变更由谁发起。
这不是日志展示缺字段，而是认证会话在最早处没有携带操作人身份。

## 修复契约

- 新增独立于玩家 `accounts` 的 `server_admin_users`。每行保存后台账号、密码、失败次数
  和锁定状态；账号格式限制为 ASCII 字母、数字、`. _ - @`，避免把不受控文本作为审计
  身份。
- 后台账号由可信数据库管理终端显式创建。服务端不会读取 `server_admin_config`，也不会在
  登录或重启时补建默认 `admin`。
- 登录同时验证账号和密码；失败次数及五次锁定按后台账号隔离。成功登录签发独立会话，
  Cookie 反查出的账号被显式传入账号/角色管理动作，不能由 POST 字段伪造。
- `server_admin_operation_logs.operator_account_id` 保存该会话账号。游戏内交易、装备操作和
  W 币消费没有后台操作人，写空值并在页面显示“游戏内”；升级前的人工行保留空值并显示
  “历史未记录”，不伪造历史身份。
- 所有后台编辑入口都创建线程隔离的待审计上下文；最终成功重定向时统一追加
  `admin-edit` 行，说明中带原始动作代码。原本已有精细审计的账号/角色编辑会复用其详细
  行并抑制通用行，避免重复。失败或未提交的编辑不写成功审计。

## 数据库升级与验证边界

运行 `server/mysql/migrate_admin_users.sql` 会创建账号表，并以 MySQL 5.x 兼容的条件
`ALTER` 为旧日志表增加操作人列；它不会迁入或生成默认 `admin`。服务端首次登录/访问
日志页会执行相同的非破坏性表准备，但账号仍须显式创建。

本次回归将覆盖：后台账号格式校验、两个独立后台会话各自反查账号、登出只清理当前会话、
登录页显式选择后仅在浏览器本地保存账号和密码，以及日志行解码/页面中“操作人”列的保留。构建和回归结果追加到本
文档的交付记录中。
