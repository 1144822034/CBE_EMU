# 装备回收 NPC：一键回收品质 0 装备

日期：2026-08-27  
状态：已实现，待客户端手工体验验收

## 需求与最早改动点

装备回收 NPC 原先只提供按背包序号逐件回收的选项；没有“按品质批量筛选”的服务端动作。
客户端已有普通 NPC 对话和二次确认的完整解析链，因此不新增客户端回调、宿主行为或输入自动化。
最早改动点是服务端现有 `WT 1/26/1 {type=2,id=value}` 装备回收菜单：在其首页增加一个受
NPC 会话上下文约束的私有动作值。

## 协议与数据契约

- 首次点击值为 `0xfa000001`，仍由 `task_hall_activate_selected_entry`
  （`江湖OL.CBE:0x010492B0`）发送为普通 `26/1` action=1 请求；
  `ParseNPCDialogData`（`0x010380E8`）继续按既有对话格式处理响应。
- 新值仅在 `VM_NET_MOCK_NPC_KIND_EQUIPMENT_BUYER` 已登记的会话上下文中可达，并且必须取得
  既有的 `0xf0` 确认上下文。确认或取消都会消费上下文；直接伪造确认、跨 NPC/场景/角色重放均被拒绝。
- 候选必须是背包中的独立装备实例，且其 `equip.dsh` 权威目录记录 `quality == 0`。不通过物品
  ID 区间猜测品质。已装备物品不在背包候选集中；品质 1 及以上装备不会被选中。
- 强化等级不改变品质，也不参与回收定价，因此强化过的品质 0 背包装备仍包含在该操作内。确认页
  明示件数和总铜钱。

## 结算与失败边界

首次点击只保存候选件数、总报价、角色/NPC/场景/服务掩码和列表页，不修改角色。确认时重新计算
品质 0 候选与总价；任一数值变化即拒绝，并保持角色状态不变。通过复核后，先在内存投影中收集所有
背包序号，再删除每个实例并增加铜钱，最后仅调用一次既有角色保存事务。保存失败会完整恢复内存角色。

定价继续复用既有规则：每件获得 `ceil(基础价 × 10 / 100)`；不读取 NPC 专属售卖价，也不引入
强化附加价。

## 客户端刷新与成功提示（2026-08-27 修正）

player-3 实际确认五件装备后的服务端记录固定了首个偏离：

```text
mock_role_db_mysql_save ... reason=npc-equipment-sell-quality-zero
mock_backpack_role_list_pending source=npc-equipment-sell-quality-zero
mock_npc_service action=equipment-sell-quality-zero ... result=1 options=0
  money=6835->6870 objects=1 inventory_sync=not-applicable
```

因此结算和持久化本身已经成功；问题不在候选筛选或事务。旧成功响应只有 `1/26/1`，并且只把
全量 `17/1` 背包快照标记为“下次查询时返回”。本次 action=1 返回后固件并未发出该查询，所以
背包保留旧行；只有无选项的对话正文，也不足以提供稳定的完成提示。

`JianghuOL.CBE:0x01033544` 已证实 `1/7/11` 按背包序号更新既有行，数量为零时走物品管理器
自己的删除路径；`10/26` 是场景铜钱 HUD 的既有更新对象。

第二次 player-3 复现确认服务端已经送出完整的五对象旧响应：

```text
mock_npc_service action=equipment-sell-quality-zero ... result=1 options=0
  objects=5 resp=237 inventory_sync=dialog+deleted-rows+wallet+notice
```

因此“仍立刻显示没有可回收装备”不是丢包或未构建 `7/11`。首个违反的 UI 契约是：成功的
`26/1` 对话仍然有 `options=0`。固件重建当前 NPC screen 后会走无选项的空列表展示分支，将
成功正文替换为“没有可回收装备”；末尾的通用 `25/11` 也不是可返回的 NPC 对话，不能修复该
生命周期。

成功响应现改为严格的：

```text
26/1（“一键回收成功…”且包含“返回装备列表”动作）
-> 每件已回收装备各一个 7/11 {seq, count=0}
-> 10/26（提交后的铜钱）
```

这不是完整 `17/1` 快照或 `7/7` 装备安装包：二者不属于 `26/1` 回调，且此前会造成物品管理器
状态错位。`25/11` 不再附加，避免与成功对话竞争展示所有权。用户点击返回后才按既有的普通
`26/1` 装备列表路径继续；服务端仍保留“下一次原生背包查询返回权威列表”的标记，供用户随后打开
背包时进行完整重建。

## 宿主边界

本改动没有修改客户端宿主的网络、定时器、回调或 screen 生命周期。宿主仍只将不透明响应字节按
CBE 已登记的 callback/context 投递；筛选、确认、背包变更和后续 UI 均由已有固件 parser 与
服务端协议完成。

## 验证

```text
make -j2
make npc-quality-zero-equipment-recycle-regression
obj\\server\\npc-quality-zero-equipment-recycle-regression.exe
```

该隔离回归不启动监听器、不连接 MySQL、不运行客户端，也不读写账号或角色数据。它构造一件已装备
品质 0 装备、两件背包品质 0 装备（其中一件强化 +5）和一件背包品质 1 装备，断言：白名单接受
该对话操作、首次点击不修改角色、确认上下文只能消费一次、报价改变会在变更前被拒绝，以及成功
结算只删除两件品质 0 背包装备并增加正确铜钱；还断言成功包严格含有带返回动作的
`26/1 + 7/11(seq=9,count=0) + 7/11(seq=11,count=0) + 10/26`。
