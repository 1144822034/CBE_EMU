# 战斗击杀任务进度主动提示

Date: 2026-08-14

## 目标

角色已接取要求击败指定怪物数量或收集指定物品数量的任务后，一场战斗首次成功
结算并确实增加任一条件进度时，主动向该角色提示新的进度。重复结算和已达上限的
条件均不应产生提示。

## 客户端协议边界

本次按 `binary_name == 江湖OL.CBE` 选择 IDA 实例并核对以下真实处理：

- `UpdateTaskProgress`：`0x01047ACE`。这是客户端在战斗本地状态变化后发送的
  `6/3 taskinfo` 上报；不是服务端可下发的进度窗口。
- `net_handle_task_response_dispatch`：`0x0104726C` case 2 只读取 `result`，因此
  服务端对 `6/3` 的正确回应是 `1/6/2 result`，不能附带未定义的进度字段。
- 同一分发器的 case 6 接收 `taskstate == 2`，只用于任务完成后的原生完成提示；
  `1/6/4` 是提交任务的奖励结果，不能复用于战斗中间进度。

对 CBE 静态区检索 GBK 的“任务进度”和“任务完成”字串均无匹配，未发现可由服务端
携带任意动态文字的原生任务中间进度弹窗协议。因此不能伪造 `6/*` 对象来强行弹窗，
否则会让客户端按错误的任务流程解析。

## 正确投递方式

服务端已有经客户端验证的系统消息队列：
`vm_mock_service_session_enqueue_system_message()`，由后续正常 scene-sync poll
作为系统频道消息送达。它不进入战斗结算包，也不重载任务/场景状态，适合承载
“任务进度：<任务名> 击杀/收集 <当前>/<目标>”的主动提示。

任务完成时仍保留既有的 `taskPromptRefreshPending` 机制，由客户端原生 `6/1 + 6/14`
刷新 NPC 的可提交标识；本次提示不会冒充完成或奖励结果。

## 服务端判定

战斗结算调用 `vm_net_mock_task_progress_after_battle(enemyId, enemyCount, 0, 0)` 一次。
该函数现在保存每个条件更新前后的值：

- 怪物条件（`requirementType == 2`）和物品条件（`requirementType == 1`）都以
  `min(旧值 + 本次增量, 目标) != 旧值` 判断是否真实增加；
- 只有数据库 `UPDATE ... task_state=1` 成功后，才排入系统提示；
- 同一任务的两个条件若同场战斗均增加，合并为一条提示，并分别标识击杀或收集；
- 已满进度和重复的战斗结算不提示。

## 验证

人工路径：接取一个 N 次击杀任务或 N 个物品收集任务，完成一次会使目标条件增加的
战斗。战斗结束后下一次场景轮询应显示一条系统消息，内容为任务名、条件类型和新的
计数；再次结算但已达到目标时不应再出现该提示。服务端日志应包含
`mock_task_battle_progress ... progress_notice=1`；零增量应为 `progress_notice=0`。
