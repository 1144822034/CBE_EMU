# 怪物管理：批量重置战斗四项属性与局部提交

## 触发与原有行为

怪物管理原先只能在单个怪物编辑区执行“重置战斗四项属性”。保存属性和该重置
都会走服务端 `303` 跳转，使浏览器重新载入整个管理页，丢失左侧目录的滚动位置和
当前筛选。批量场景若以浏览器端循环提交单个请求实现，则会在中途失败时留下部分
怪物已重置、部分未重置的持久化状态。

## 契约与修正

1. 左侧怪物目录为每一项提供勾选框，可全选当前筛选结果、清除选择，并提交以逗号
   分隔的 `monster_ids`。
2. 服务端先完整校验所有 ID（非零、目录存在、无重复），再在一个 MySQL 事务内更新
   每个已有覆盖项的 `HP/MP/攻击/防御`。任一 SQL 语句或提交失败即回滚；内存中的
   覆盖值只会在 `COMMIT` 成功后更新。
3. 未建立覆盖项的怪物本就直接使用按当前等级、类型计算的服务端基线，因此不额外
   写入冗余行，并在结果中计为“原本已使用服务端公式”。
4. 重置只改变四项战斗属性，保留等级、类型、经验、金钱、掉落与其他怪物配置。
5. 保存属性、单个“四项属性重置”与批量重置都使用同一局部提交路径：请求仍是正常
   `/action` 表单并遵循服务端重定向，但前端只替换 `#monster-list` 和
   `[data-admin-detail]`，保留目录滚动位置和筛选输入；网络失败只在编辑区显示错误。
   未启用 JavaScript 时仍可遵循原有整页表单跳转，服务端契约不变。

构建通过。未启动或操作用户正在使用的服务端及 MySQL 数据库；实际管理页交互可在
隔离测试账号上验证以下边界：多个已覆盖怪物、混合已覆盖/默认怪物、重复 ID 和
MySQL 写入失败回滚。
