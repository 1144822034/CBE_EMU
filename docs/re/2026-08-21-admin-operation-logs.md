# 后台账号操作日志

状态：已实现；等待在目标 MySQL 实例执行迁移或由后台首次访问自动建表。

## 目标与边界

后台对账号和角色的人工变更、以及玩家已提交的经济与装备操作都需要可追溯记录。日志覆盖：

- 创建账号、修改密码（不记录密码内容）；
- 修改角色名称、等级和位置；
- 增加普通钱币或 W 币；
- 发放物品或装备；
- 从风险角色页封禁账号。
- 游戏内商城购买商品；
- 进入配置了 W 币门票的副本。
- 玩家交易：双方各写一条记录，说明交易对象、双方转出/收到的铜钱与物品数量；
- 丢弃装备：只记录已写入角色背包事务的装备实例删除，保留物品 ID、背包序号、强化等级、数量和剩余数量；
- NPC 装备回收：记录已删除的装备实例、回收铜钱与角色铜钱余额变化。

内容配置、怪物、任务、场景战斗怪、Actor、商城、宝箱、登录服务器、内容更新、DSH 行编辑、
全服奖励及 GIF/DSH 上传现在也纳入审计。它们统一以 `admin-edit` 写入，说明列保留实际
动作代码（例如 `save-npc`、`batch-configure-monster-drops`、`upload-gif`）；没有玩家目标
的配置写入以 `admin-config` 作为目标标识。

## 持久化契约

`server_admin_operation_logs` 是追加式表，记录操作代码、后台操作者账号、目标账号/
角色、物品/数量、金额、UTF-8 说明和毫秒时间。`operator_account_id` 来自当前已认证的
`server_admin_users` 会话；表没有账号或角色外键，因此后续的角色迁移、角色删除、后台
账号停用或账号状态变更都不会改写历史证据。

业务服务先完成自身的权威持久化，再插入审计行。账号/角色的精细审计写入失败时，后台
页面会明确提示“操作已完成，但操作日志写入失败”；统一配置编辑审计写入失败会在服务端
输出动作、操作人和 MySQL 错误。游戏内则记录服务端错误但仍返回已提交的消费结果，不会
把已扣除的 W 币伪装为失败或回滚到不一致状态。

所有 `POST /action` 编辑和 GIF/DSH 上传在同一后台工作线程中创建待审计上下文；只有
最终重定向的 `status=ok` 才会追加统一编辑行。账号/角色动作原有的精细审计行（含金额、
物品、角色等）会标记该上下文已写入，因此不会同时再生成一条笼统的 `admin-edit` 重复行。
失败、校验拒绝或未提交的请求不会伪造为成功审计记录。

玩家交易的两条审计行只会在双角色背包/铜钱事务提交后写入；丢弃装备则先确认角色保存
成功，保存失败会还原内存状态并返回丢弃失败，不会产生审计行或成功响应。装备回收同样在
“删除装备 + 增加铜钱”的同一角色保存提交后才写入。审计写入自身失败时，上述已提交操作
保持成功，并在服务端输出明确错误，避免把历史写入失败误报为业务回滚。

新增类型分别为 `player-trade`、`discard-equipment`、`recycle-equipment`。交易行的“金额”
表示该角色本次付出的铜钱，完整收支在说明列中；回收行的“金额”是实际获得的铜钱。

已有数据库执行后台多账号迁移：

```powershell
mysql -h 127.0.0.1 -P 3306 -u root -p jh_online < server/mysql/migrate_admin_users.sql
```

后台首次写入或访问“操作日志”页也会执行等价的建表与列升级；后台首次登录会自动建立
`server_admin_users` 并将旧版共享密码迁入默认 `admin` 账号。

## 查看与验证

后台导航新增“操作日志”。页面按 `log_id DESC` 分页，可按精确账号过滤，并可同时勾选
多个日志类型；翻页会保留所有已选类型。记录显示时间、操作、操作人、目标账号、角色、
金额或物品和说明。后台成功操作显示实际 `server_admin_users.account_id`；游戏内提交
行为显示“游戏内”；升级前的人工历史行没有伪造操作者，显示“历史未记录”。

- `make -j2`：源文件编译成功；正式服务可执行文件被运行中的服务占用，未强制覆盖。
- 独立临时服务可执行文件：链接成功。
- `scripts/admin-request-length-regression.c`：覆盖操作日志导航、交易/丢弃/回收与 W 币消费
  类型、多类型 SQL 筛选和翻页参数保持；该测试不连接 MySQL，因此不会向用户数据库写入
  审计行。
