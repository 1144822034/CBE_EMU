# 宝箱开启等待：背包堆叠上限契约

## 触发步骤

1. 登录账号 `21642502`，选择角色“武林盟主”。
2. 在后台依次给予黄金宝箱（`524`）99 个、22 个，再给予黄金钥匙（`815`）。
3. 在客户端使用黄金宝箱并选择钥匙。

客户端持续显示等待提示。

## 原始运行证据

`bin/server_out.txt` 记录的两次后台给予已经显示了第一次偏离：

```text
account_item_grant ... role=... id=10036 item=524 count=99 seq=78 stack=0/99
account_item_grant ... role=... id=10036 item=524 count=22 seq=78 stack=99/121
account_item_grant ... role=... id=10036 item=815 count=11 seq=41 stack=1/12
```

随后真实客户端仍发送原生单对象请求，服务端也没有落入未处理分支。下面是修复前的历史
回包，保留它用于解释当时的等待/隐形模态框现象：

```text
mock_chest_open request=7/15 chest=524 key=815 chest_seq=78 key_seq=41 ...
  response=7/1+2x(7/7-type2+7/11)+7/7-type1
```

这说明请求的 `box` / `key` 字段仍是序列号、奖池抽取和角色事务均已执行；等待不是
“没有收到开箱请求”或“奖池未配置”。

只读查询该角色当前的关系表也确认，已经执行过一次被卡住的开箱事务后，`seq=78` 仍以
单行 `524 x120` 持久化；角色背包容量为 100、当前仅 51 行，因此有充足空间迁移为
`99 + 21`，不存在“为分拆而丢弃物品”的容量问题。

## 客户端和资源取证

直接解析客户端资源 `bin/JHOnlineData/item.dsh` 的 33 列记录得到：

| 物品 | ID | `堆叠数` |
| --- | ---: | ---: |
| 青铜宝箱 | 522 | 99 |
| 白银宝箱 | 523 | 99 |
| 黄金宝箱 | 524 | 99 |
| 青铜钥匙 | 813 | 99 |
| 白银钥匙 | 814 | 99 |
| 黄金钥匙 | 815 | 99 |

`江湖OL.CBE:0x01033544`（`HandleItemOperationResponse`）在通用成功
`1/7/1 { result, type, id }` 确认上清除待处理操作；同一函数处理 `7/11` 数量流后也会
清除这项 pending 状态。背包模型消费 `7/7 type=2` 和 `7/11` 的选中行更新。
`mmGameMstarWqvga.cbm:0x000011CE`
按复合响应中的对象顺序派发 `7/7`，`0x00000D04` 再把 `iteminfo` 写入该模型。

历史开箱 builder 曾首先发送 `1/7/1 result=1`，且没有使用旧的重复 `7/37` 获取包；该确认
后来被固件取证证明会创建无法自动关闭的成功模态框。当前 builder 已移除这个对象，改由
两组 `7/7 type=2 + 7/11` 清理 pending 操作，再发送奖励 `7/7 type=1` 和 `25/11`
横幅。堆叠问题仍发生在回包之前：
客户端登录和背包模型已被服务端给予路径构造为资源不允许的 `524 x121` 单实例；开箱
又把这一实例下发为 `x120`。

## 根因

`vm_net_mock_role_add_backpack_item_to_role_in_memory()` 对非装备、非壶、非天书物品采用了
“找到同 ID 即无上限累加”的规则，完全忽略了已加载的 `item.dsh` 第 11 列 `堆叠数`。

这违反的不是传输整数位宽（`7/11` 可承载更大的数），而是客户端物品资源定义的**单背包
实例上限**。99 与 22 本应形成两个有不同 sequence 的背包行；错误合并使原生 `7/15`
开箱的选中 sequence 指向非法堆叠，后续的完成确认没有可依赖的合法背包状态，表现为等待
无法结束。

## 修复计划

1. 将普通物品的合并规则改为从 `item.dsh` 的 `堆叠数` 读取单格上限：先填充同 ID 的未满
   行，再按上限创建新行；容量不足时不改变角色状态。
2. 在角色背包规范化阶段迁移已有的超上限普通堆叠为多个 sequence。若背包容量不足，保留
   原数据并记录明确的 `unresolved` 日志，不截断、不丢物品。
3. 添加纯服务端回归：`524 x121` 规范化为 `99 + 22`，下一次开箱只把被选择行改为 `98`，
   而钥匙和奖励仍保持各自的实例/堆叠规则。
4. 不修改 CBE/CBM、客户端内存或请求字节；成功回包遵循当前已验证的
   `7/7,7/11,7/7,7/11,7/7,18/1` 顺序。

## 回归

`scripts/chest-stack-limit-regression.c` 是不连接 MySQL、不启动监听器的纯服务端回归。它
加载真实 `item.dsh`，构造历史行 `{ item=524, seq=78, count=121 }`，验证规范化为
`{78,99}` 与新 sequence 的 `{...,22}`；再模拟扣除选中行及一把钥匙，验证选中行仅变为
98、另一格保持 22，所有受 DSH 约束的普通行均不超过其上限。

## 已排除的假设

- 非 `WT 7/15` 未处理：服务端日志已经证明 detector、奖池和事务进入成功路径。
- 非“`box`/`key` 被当作 item ID”：日志中的 `chest_seq=78`、`key_seq=41` 与原生 parser
  的 sequence 语义一致。
- 非请求未处理：历史 builder 已进入成功事务；当前回包不再发送会创建模态框的
  `1/7/1`，而由 `7/11` 数量流清理 `0x01033544` 的 pending 状态。
- 不以更宽整数作为修复：字段能表示 120 不代表该值可作为 `堆叠数=99` 的一个客户端背包行。
