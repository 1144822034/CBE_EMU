# 黄金宝箱超 99 堆叠迁移未持久化（2026-08-08）

## 触发与取证

此前修复把客户端资源 `item.dsh` 的普通物品单格上限应用到背包规范化：黄金宝箱
`524` 的上限为 99，因此历史 `524 x120` 应拆成两条带不同 `item_seq` 的记录。

对 `21642502` 的只读 MySQL 查询确认，当前权威数据不是“箱子被删除”：角色 `10036`
容量为 100、背包持久化行数为 51，仍存在：

| slot | item | seq | count |
| ---: | ---: | ---: | ---: |
| 49 | 524（黄金宝箱） | 78 | 120 |
| 50 | 814（白银钥匙） | 79 | 1 |

因此首次错误状态是 `account_role_backpack` 中仍持久化着违反客户端资源约束的
`524 x120`。客户端背包模型不能把这条非法单实例可靠显示为正常宝箱，而不是 MySQL
已经删除了该物品。

## 根因

`vm_net_mock_role_normalize_backpack()` 确实会在内存中把该行分成 `99 + 21`，但
`vm_net_mock_role_db_load()` 没有把“规范化导致背包变化”纳入 `needsSave`。结果是该
迁移只停留在本次进程内存，关系表保持 `x120`，下次登录又从非法原始行开始。

这违反的是服务端持久化生命周期，而非 `WT 7/15` 开箱请求或客户端回包字段；不应通过
补发箱子、忽略资源上限或修改客户端状态处理。

## 修复

1. 背包规范化函数返回是否改变了持久化表示。
2. 角色关系表加载时比较规范化前后的角色状态；任何变化都设置 `needsSave`。
3. 既有 `vm_net_mock_role_db_save_relational(..., full_snapshot=true)` 在一个 MySQL
   事务中替换该账号的背包行，所以会原子地把 `524 x120` 写为 `524 x99` 和 `524 x21`，
   不存在先删后不补的中间提交。
4. 若空间不足，原规范化器仍保留原行并记录 `backpack_stack_limit_unresolved`，不会截断
   箱子；本例 51 行/100 格有足够空间。

## 验证

- `scripts/chest-stack-limit-regression.c` 现断言历史 `524 x121` 的规范化明确报告持久化
  表示已改变，并继续验证拆分、选中格扣除以及钥匙/奖励的正常行为。
- `make -j2` 用于服务端构建验证。
- 部署后该角色首次加载应记录
  `backpack_normalize_persist ... source=role-load-relational`，随后数据库应保留两个
  黄金宝箱行，总数量仍为 120（99 + 21）。
