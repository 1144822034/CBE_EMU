# 黄金宝箱钥匙重复扣减

## 触发与首次偏离

在背包开启一只黄金宝箱（`524`）时，用户观察黄金钥匙（`815`）从开箱前数量减少两把；
服务端角色事务本身只调用一次 `vm_net_mock_role_consume_backpack_item(... key ..., 1)`，因此
重复不在持久化扣除，而在下行背包同步。

当前运行的 `mock_chest_open` 记录了原生请求 `WT 7/15 {box,key}`（黄金宝箱 seq `238`、
黄金钥匙 seq `258`）及旧成功回包：

```text
7/4 + 7/11(chest sequence/count) + 7/11(key sequence/count) + 7/15(reward)
```

`JianghuOL.CBE:HandleShopBuyItem(0x01025AE6)` 的 `7/15` 成功分支是此原生开箱操作的拥有者，
请求中的 `box/key` 为客户端所选实例。实际界面结果证明它已经对钥匙完成一次本地消耗；随后再把
同一钥匙序号的剩余数量写入 `7/11`，便造成第二次可见扣减。宝箱行没有这个客户端侧钥匙消耗，仍
需要 `7/11` 按序号更新或删除。

## 修复契约

成功响应改为严格三个对象：

```text
1/7/4   result=1                    结束物品操作等待
1/7/11  chest sequence/count         同步或删除宝箱行
1/7/15  result=1,total=1,iteminfo    原生奖励与提示；钥匙仅由该原生开箱路径扣一次
```

服务端仍在同一预提交副本中各消耗一只宝箱和一把钥匙，并在保存失败时整体回滚。删除的只是会让
客户端第二次修改钥匙行的下行 `7/11`，没有改变奖池、随机抽取或持久化数量。日志会记录
`key_remaining`，但标明 `key_count=client-native-once`，便于与持久化状态交叉核对。

## 验证

`scripts/chest-open-reward-notice-regression.c` 现在断言成功包只有 `7/4, 7/11, 7/15` 三个对象，
没有钥匙 `7/11`。手工验证应检查：每开一只黄金宝箱，宝箱、钥匙和服务器持久化记录均恰好减一，
奖励只新增一次；重新登录后钥匙数量仍与开箱前减一一致。
