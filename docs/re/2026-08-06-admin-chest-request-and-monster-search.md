# 后台宝箱奖池保存与怪物筛选修复（2026-08-06）

## 触发条件

1. 在“宝箱管理”中编辑较多奖励行并提交；后台返回“请求长度无效”。
2. 在“怪物管理”的“按 ID、名称或场景筛选”输入内容；目录不发生筛选。

## 首个偏离与根因

`vm_mock_admin_handle_client` 将 HTTP 请求头和请求体一同放入固定的
`VM_MOCK_ADMIN_REQUEST_MAX=8192` 字节栈缓冲。解析到 `Content-Length` 后，
它在进入 `/action` 的 `save-chest-rewards` 分支前以
`contentLength > 8192 - headerLen` 返回“请求长度无效”。因此问题不在宝箱
奖励解析、奖励行上限或 MySQL 保存，而在 HTTP 接收层错误地把头部缓冲上限当作
表单大小上限。

怪物页的筛选初始化是页面尾部独立的内联脚本，而后台的选择、局部刷新和列表状态
都由 `/admin.js` 的统一生命周期管理。该筛选没有使用这一初始化入口，也没有避免
重复绑定；在后台页面的装配/局部导航组合下，筛选监听器不具备稳定的所有权。

## 修复

- 保留 8 KiB 的请求头上限；在得到完整头部和合法 `Content-Length` 后按实际总长度
  分配请求缓冲并继续读取 body。常规编辑表单不再受 8 KiB 限制。
- 设置 1 MiB 的全局 HTTP body 资源保护阈值，只用于避免单个连接无限制占用进程内存；
  它不是宝箱、物品或奖励行的业务限制。
- 把请求分成“接收/拥有缓冲区”和“分发请求”两层，保证所有既有分发分支返回时由外层
  统一释放动态缓冲区。
- 把怪物筛选移入 `/admin.js` 的 `DOMContentLoaded` 初始化，并以数据标记保证每次完整
  页面装配只绑定一次。筛选按怪物行 `data-key`（ID、名称、首个场景）匹配。

## 验证边界

- `scripts/admin-request-length-regression.c` 验证 24 KiB 的标准表单 body 能通过请求
  长度计算（旧的 8 KiB 接收契约会拒绝），并锁定怪物筛选统一初始化的存在。
- 完整 `make -j2` 先完成了源码编译；链接 `bin/jh-online-server.exe` 时因用户正在运行的
  同名服务持有该文件而被操作系统拒绝。随后以同一组对象成功链接独立候选文件
  `tmp/jh-online-server-web-admin-candidate.exe`，证明当前服务端完整链接通过；未终止或
  替换用户进程。
- 浏览器自动化连接尝试受当前浏览器运行时初始化错误阻塞（`process` 属性已存在），因此
  未执行任何后台写操作；待用户正在运行的服务替换为本次构建后，可在怪物页输入 ID/名称/
  场景并提交多行宝箱奖励进行人工验收。
