# 比武擂台：入口与大厅协议

状态：可实现（大厅、开设、房间查看与加入）；擂台战斗的独立回合/奖励协议仍需在真实流程中继续取证。

## 入口位置

- `sMap.dsh` 的地图行 104：`c14蜀山_01.sce`，显示名为“蜀山南门”。
- 主程序 `江湖OL.CBE` 在 `0x0105082F` 包含活动文案：`擂台宗主广邀天下英雄共赴蜀山南，踢台夺金。`
- 原始 `c14蜀山_01.sce` 只含清微、苍古、传送石等内置 NPC，并没有擂台宗主。因此该入口应作为服务端动态 NPC/原生 NPC 覆盖服务提供，不能把它误当作漏加载的 SCE 记录。

## 客户端已确认的状态机

`net_business_response_dispatch(0x01012F4E)` 将业务 26 交给 `net_open_task_hall_response(0x01010C34)`；其中 `result=1` 会打开擂台/任务大厅专用界面。

场景通道 `1/30/*` 在 `net_handle_scene_channel_dispatch(0x01039B8A)` 中分流：

| 响应 | 已确认字段 | 客户端状态 |
|---|---|---|
| `1/30/3` | `curpage`、`pagenum`、`roomnum`、`roomlist` | 27，擂台房间列表 |
| `1/30/4` | `turnvity`、`minaward`、`minaward2`、`minaward3`、`maxaward`、`maxturn` | 28，开设擂台参数 |
| `1/30/7` | `roomid`、`rolenum`、`rolesinfo` | 31，房内角色列表 |
| `1/30/9` | `isleader`、`challenge` | 原生“是否挑战”确认框 |

`SendGameEvent(0x01037C02)` 的客户端请求字段已确定：

| 请求 | 字段 | 调用点 |
|---|---|---|
| `1/30/7` | `roomid:u32` | `task_hall_room_list_dispatch(0x01049878)` |
| `1/30/8` | `roomid:u32` | `task_hall_enter_current_room_dispatch(0x01049740)` |
| `1/30/10` | `agree:u8` | `HandleResConfirmCb(0x01039566)` |
| `1/30/11` | `type:u8`、`award:u16`、`turns:u8` | `task_hall_accept_current_task_dispatch(0x01049764)` |

`task_hall_room_list_dispatch(0x01049878)` 还会用 `1/30/3 { page }` 请求房间列表翻页；服务端即使当前仅有一页，也必须以 `1/30/3` 回答。对开设页的参数刷新只使用已确认的 `1/30/4` 配置响应。

`1/30/4` 和 `1/30/3` 不能作为一次“打开擂台”响应连续下发：两个处理器都会写入同一个大厅模式，后面的 `1/30/3` 会把 `1/30/4` 刚打开的模式 28（开设擂台参数页）覆盖为模式 27（房间列表）。因此服务端在苍古的 NPC 对话中使用两个独立的 action-1 服务行：

- **开设擂台**：`1/26/1 { type=2, id=0xef000001 }` → `1/26/1 {result=1}` + `1/30/4`，最终为模式 28；
- **挑战擂台**：`1/26/1 { type=2, id=0xef000002 }` → `1/26/1 {result=1}` + `1/30/3`，最终为模式 27。

两项绝不能合并为同一个选项或同一复合响应；`30/3` 仅用于“挑战擂台”入口、创建成功后，或客户端明确请求的列表翻页。

`task_hall_screen_dispatch_input(0x010498F6)` 进一步确认了该结论：模式 27 只进入 `task_hall_room_list_dispatch`（翻页/查看房间）；模式 28 才进入 `task_hall_accept_current_task_dispatch`，并由此发送 `1/30/11 { type, award, turns }`。因此“首包最终落在列表状态”会使创建操作不可达，而不是客户端未实现创建按钮。

房间列表的 `roomlist` 行由 `roomid:u32` 加三段长度前缀字符串组成。客户端将前置 `roomid` 作为第一列显示，所以 `colnames` 必须给四个本地化表头：`编号`、`擂台`、`擂主`、`状态`；不能下发英语占位列名。角色列表同理使用 `姓名`、`职业`、`等级`、`状态`。

## 2026-08-12：蜀山苍古入口问题修正

现象：通过苍古打开比武擂台后进入“比武类型列表”，表头为英文，且不能创建。

原因：服务端首包错误地把 `30/4` 配置页和 `30/3` 房间列表混在同一复合响应内，最终由 `30/3` 覆盖为模式 27；同时列表列名使用了调试英语 `id/room/scene/state`。这不是缺少创建接口，创建请求 `1/30/11` 已有客户端调用证据，只是 UI 从未保留在能够发起该请求的模式 28。

修正：入口只下发打开结果和 `30/4`；`30/11` 成功后才下发 `30/3`。所有擂台列表字段用 GBK 中文编码，并保留现有 raw 字段顺序。

## 2026-08-12：开设参数与活力消耗

`ParseArenaRewardData(0x0103965A)` 将 `30/4` 的参数分别保存为：
`minaward`（初始加幅）、`minaward2`、`minaward3`（另外两档加幅）、
`maxaward`（赏金上限）、`maxturn`（次数上限）和 `turnvity`（每次消耗的活力）。
该页的固定中文标签位于 `0x0104CD74`：模式、加幅、赏金、次数、消耗活力。

客户端的计算方式已由 `DrawCalcMulValue(0x0104CA74)`、
`DrawCalcTotalValue(0x0104CA0E)` 和创建请求 `SendGameEvent(0x01037C02)` 确认：

- 加幅在三档 `minaward/minaward2/minaward3` 间选择；
- 赏金是当前加幅的正整数倍，写入 `30/11.award`；
- 次数最小为 1，写入 `30/11.turns`；
- 消耗活力固定为 `次数 × turnvity`；客户端不会在请求中另传一个活力字段。

字段编码必须与其读取器严格一致：`turnvity`、三档 `minaward*` 和
`maxaward` 由 `LookupItemIntField(0x01033CF2)` 读取，值必须是
`00 04 + BE32`；`maxturn` 由 `LookupItemByteField(0x01033C6C)` 读取，
值必须是 `00 01 + byte`。不能按存储目标的 16 位宽度写入：读取器总是
从 value 的第 2 字节开始取数，短字段会把紧随其后的下一个字段名的字节
误当为数值（例如界面中的 28009 / `0x6D69`）。

旧实现把首档 `minaward` 误填为 0，导致客户端的加幅、赏金初始值和可选范围均失真；服务端又把所有创建失败一律回成 `30/3`，造成“确认后回到空列表”。修正后的约定为：首档加幅 100、其余档位 500/1000、最高赏金 10000、最多 20 次、每次消耗 5 活力。服务端以同一组固定约束复算 `30/11`，通过后用 MySQL 中权威的 `(account_id, role_id)` 活力行原子扣除；参数非法或活力不足时仅回 `30/4`，让客户端保留在原生创建页。

## 2026-08-12：加入房间后的挑战与战斗

`task_hall_enter_current_room_dispatch(0x01049740)` 证明 `30/8` 不是只会
加入一次的请求：在房内角色列表（模式 31）按确认会再次发送同一个
`1/30/8 {roomid}`。服务端因此按房间成员状态区分两个阶段：

1. 请求者尚未在房内时，`30/8` 执行加入并回 `30/7` 刷新成员列表；
2. 请求者已经在一个双人房内时，下一次 `30/8` 是挑战入口。回复必须是
   同一 WT 包中有序的 `1/26/0 {}` 后接
   `1/30/9 {isleader=0, challenge=...}`。运行时曾只下发 57 字节的
   `30/9`，客户端没有再发送 `30/10`，且取数进度层持续存在。
   `HandleChallengeResponse(0x010395AA)` 只注册确认回调；
   `DispatchItemEvent(0x01039C28)` 才会在处理 kind-26 对象后清除该
   进度层。因此 `26/0` 是无业务副作用但必须先到的确认对象；
3. `HandleResConfirmCb(0x01039566)` 发出严格的 20 字节
   `1/30/10 {agree}`。`agree` 是该回调写入的原生确认状态，不能由服务端
   擅自反推其数值含义；只有尚未过期、成员仍完整的同一角色可以消费该确认。
   静态核对 `30/10` 的分发目标 `0x01039528` 后确认：`result=0` 只会清除
   网络等待标记，**不会**关闭 task-hall；`result=1` 则读取 `failnotify` 并
   通过 `0x01038E00 -> CleanupTaskHall(0x010491AE)` 返回场景。故双方确认均
   回独立的 `1/30/10 {result=1,failnotify}`。运行时记录已确认：双方都从后续
   场景轮询收到了 `4/10`，但客户端没有进入战斗。因此不能将两个启动都延后为
   轮询投递；轮询次数、延迟和场景重入都不是正确的就绪条件。
   首个 `30/9` 已是擂台的远端应战确认；不得再额外复用普通切磋的
   `4/15 -> 4/16 + 4/9` 模态链。被挑战者回 `30/10` 后，服务端创建共享擂台
   对局。被挑战者的本次 `30/10` 响应按已验证的普通切磋接受方模式，有序复合
   一个 `4/10`；挑战者则在它自己的大厅关闭完成后的下一次场景轮询收到 `4/10`。
   这不是定时延迟，也不需要场景重入。拒绝或超时只释放当前挑战租约，不影响房间。
   不得使用带 `posinfo` 的 `30/2` 强制场景重入：后者会导致双方无条件重新加载
   场景，却不是擂台大厅的正常关闭路径。
4. `4/10` 复用已经验证的双人战斗 wire 格式：观察端的本地角色在右侧、
   对手在左侧，后续 `4/6` 行动与 `4/11 + 4/9` 结束包由同一共享会话同步。

擂台和“附近玩家切磋”复用战斗包及行动会话，但不复用切磋的请求入口。切磋
创建会话时必须同场景；擂台只以同一房间的在线双方为准，允许双方停留在不同
场景。两者均以临时 HP/MP 承载战斗，结束后不把 PvP 伤害或 MP 消耗写入角色
持久状态。

`turns` 是该房间可完成的对战局数。正在对战时房间保持“对战中”；一局的双方
终局包均发出后才可开始下一局，达到次数后房间关闭。`award` 的战后货币结算
协议尚无客户端证据，本阶段只使用它作为已展示、已校验的创建参数，不伪造
扣款、转账或奖励包。

## 实现边界

1. 新服务类型只在确认过的 `1/26/1` NPC 服务上下文中接受，避免将任意 `1/30/*` 包误判为擂台操作。
2. 房间是在线活动状态，不持久化为角色档案；创建者下线即时关闭、挑战者下线即时移出。角色、货币和战斗结果仍由既有权威存储负责。
3. 擂台仅接受精确的大厅上下文、`30/8` 的成员状态转换与同一角色未过期的 `30/10 {agree}`；不得把任意 `30/10` 或普通切磋请求升级为擂台战斗。

## 2026-08-13：是否需要进入专用擂台场景？

结论：**没有固件证据表明擂台会进入一张专用 `.sce` 场景。** 该功能使用的是
任务大厅 screen，而非世界场景切换：

- 固件中的 `擂台列表`、`开设擂台`、`房间信息`、`挑战`均位于任务大厅 UI 文本区；
  本地 `JHOnlineData` 中也没有可识别为擂台的场景资源名。
- `task_hall_screen_dispatch_input(0x010498F6)` 的擂台模式 27/28/31 只分别分派
  `30/3`、`30/11`、`30/8`；`task_hall_enter_current_room_dispatch(0x01049740)`
  只发送 `30/8`。
- `30/10` 的处理器 `0x01039528` 在 `result=1` 时调用
  `0x01038E00 -> CleanupTaskHall(0x010491AE)`。后者仅释放/复位任务大厅状态，
  没有调用 `EnterSceneByMapName(0x01018150)`，也没有构造 `30/1`、`30/2`。
- 场景通道分派器 `0x01039B8A` 中，只有 `30/1` 进入
  `scene_handle_enter_with_scene_pos(0x010396D6)`；擂台已经确认使用的
  `30/3`、`30/4`、`30/7`、`30/9`、`30/10`、`30/11` 都不走该分支。

因此不得用场景跳转或伪造擂台 `.sce` 来解决“确认后无反应”。首个尚未闭合的
契约在**原生 PvP 建战序列**，不是场景生命周期。

普通切磋的 `4/14 -> 4/15 -> 4/16 + 4/9 -> 4/17/4/10` 只适用于从场景玩家
操作发起的切磋。擂台已有独立的 `30/9 -> 30/10` 应战链，先前为擂台叠加
`4/15` 是未经证实的临时假设，造成用户看到第二个“请求切磋”确认，且将
`4/10` 置于该回调尚未返回的错误时机；现已移除。

## 2026-08-13：场景所属的擂台确认链

进一步对照已经能启动战斗的副本挑战链后，确认此前擂台双方虽然都收到
`4/10`，但它们各自的 `30/9` 所属 UI 不一致：发起者在任务大厅内接收，而被挑战者
少了挑战链固有的 `1/26/0` 前置对象。二者都会让 `30/10` 只完成界面确认，而不会让
场景回调进入可消费 `4/10` 的建战状态。

服务端现统一采用已验证的场景确认次序：

1. 发起者第二次 `30/8` 只收到 `1/26/0 + 1/30/10 {result=1, failnotify}`，
   正常关闭任务大厅；
2. 下一次**场景**轮询向发起者下发 `1/26/0 + 1/30/9`，再严格绑定其 `30/10`；
3. 被挑战者同样由场景轮询收到 `1/26/0 + 1/30/9`，并严格绑定其 `30/10`；
4. 两端确认均为 `1/30/10 {result=0}`，只有第二端接受后创建决斗，再按既有会话
   下发 `4/10`。

这不是额外延时或兜底包，而是复用已有实例挑战的“清除大厅请求层后，由场景接管确认
回调”的实际生命周期。后续测试应观察 `arena_initiator_challenge_notice_deliver`、
`arena_challenge_notice_deliver` 和双方 `30/10` 是否按该顺序出现；若仍不能进入
战斗，则继续从该完整链的客户端回传和模块状态取证，而不是修改 `4/10` 字段。
