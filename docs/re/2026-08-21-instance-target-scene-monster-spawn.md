# 副本目标场景指定怪物刷新

## 业务链路与根因

副本 NPC 的进入动作仍走原生 `30/1` 场景切换。客户端加载目标 SCE 后，只会从
SCE2 kind-3 记录创建可见、可碰撞且可发起战斗的 type-2 场景节点。动态 NPC 包、
`4/10` 自动战斗或传送后的临时对象都不能替代该资源契约。

原有 `challenge_enemy_id` 属于来源场景的“守关怪挑战”，点击服务后直接进入战斗，
并不表示目标场景应出现哪个怪物。复用该字段会混淆场景归属和行为，所以新增独立的
`spawn_enemy_id`，只绑定副本目标场景。

## 实现契约

- `server_dynamic_npc_instances.spawn_enemy_id` 保存目标怪物 ID，0 表示不指定。
- 保存时要求目标场景存在同 ID、已启用的 `server_scene_battle_monsters` 行。
- 同时重新解析当前服务端 SCE，确认所有已启用草稿都已部署，且指定 ID 的 kind-3
  记录确实存在。未部署或资源陈旧时拒绝保存。
- 运行时发送 `30/1` 前再次执行相同检查。配置失效时不伪造怪物、不自动战斗，也不
  发送错误场景成功包。
- 传送包本身不增加任何怪物对象；怪物来源日志固定记录为 `SCE2-kind3`。

## 内容更新边界

场景战斗怪草稿必须先在后台部署到目标 SCE。部署通过现有内容更新链路发布
`WT18/9 -> WT18/8 -> WT18/7`。客户端首次进入副本时如果先建立场景壳、后完成同名 SCE
的 `WT18/7` 安装，服务端会在严格匹配最近完成目标的条件下允许一次原生场景重入；若客户端
没有进入该更新回调路径，仍需完整退出并重新启动后再进入副本。

这项配置不是每次传送动态生成一只新怪物；它声明该副本目标场景必须包含哪个已部署
的 kind-3 怪物。若需要同一 SCE 在不同副本入口显示不同怪物，必须使用不同的目标
SCE 资源或先扩展经过客户端协议证据确认的实例化场景资源机制。

## 验证边界

纯代码回归检查：未部署的 `spawn_enemy_id` 会阻止传送；清空该字段后仍只生成一个
`1/30/1` 场景进入对象，且不会生成动态 NPC 怪物包或 `4/10` 自动战斗。
