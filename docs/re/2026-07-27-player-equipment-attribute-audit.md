# 人物与装备属性链路核对（2026-07-27）

## 范围

本次只核对当前实现的属性来源、客户端显示、装备实例状态和战斗结算；不在
尚未取得原服数值证据时修改公式。

## 已确认的资源与客户端契约

`bin/JHOnlineData/equip.dsh` 有 1485 行、26 列。与角色数值有关的列为：

| 零基列 | 字段 |
| --- | --- |
| 3 | 等级 |
| 7 | 类别 |
| 8--18 | 护甲、攻击、生命、法力、力量、敏捷、智力、爆击、命中、躲闪、抗性变化 |
| 19 | 耐久 |

例如 `1001 木制宽剑` 的资源值为：等级 `1`、类别 `7`、攻击 `30`、力量
`15`、耐久 `50`。

客户端不是只显示服务端计算后的最终装备属性：

1. `JianghuOL.CBE:HandleItemOperationResponse(0x01033544)` 在 `1/7/8`
   穿戴或脱下成功后调用 `scene_rebuild_status_meter_node(1)`；
2. `scene_rebuild_status_meter_node(0x0100FED8)` 遍历当前装备，跳过当前
   耐久为零的条目，并读取装备本地字段；
3. 该函数调用 `AddActorStatBonus(0x0100FE2C)` 累加生命、法力、经验与多项
   属性，又调用 `CalcEquipStatBonus(0x01028B34)` 计算装备/强化带来的附加值；
4. `CalcEquipStatBonus` 读取客户端自身的强化表和装备强化等级。因此客户端
   具备基于本地资源重算装备显示属性的逻辑。

这证明 `actorinfo` 的基础属性与客户端本地装备重算是两个必须严格分工的
输入，而不是可以同时下发“已含装备”的同一数值来源。

## 审计开始时的服务端链路

| 项目 | 当前实现 | 状态 |
| --- | --- | --- |
| 装备目录 | `mock_server_catalog.c` 读取 `equip.dsh` 的 3、7--19 列 | 已与资源对齐 |
| 装备槽位与等级限制 | 类别 0--9 映射八槽；穿戴时验证等级 | 已生效 |
| 力量/敏捷/智力、生命/法力、攻击/护甲 | `vm_net_mock_role_build_player_stats()` 汇总已穿戴装备 | 服务端战斗使用，但与客户端本地重算重叠 |
| 普通攻击/受击 | 使用汇总的攻击、防御及软减伤公式 | 已生效，但公式是 mock 设计 |
| 技能伤害/治疗 | 使用力量、敏捷、智慧与 `skill.dsh` 系数 | 已生效 |

## 首次偏离与证据

### 1. 服务端和客户端同时叠加装备基础词条

`vm_net_mock_role_build_player_stats()` 已将装备词条加入主属性和 HP/MP，且
`vm_net_mock_build_actor_info()` 将这些已汇总的值写入 `actorinfo`。而客户端
在装备同步完成后会按前述 `scene_rebuild_status_meter_node()` 再次从本地
`equip.dsh` 叠加同一装备。

这不是一个可通过调整 `攻击 / 3` 或 `护甲 / 5` 修复的数值问题，而是属性
归属不唯一。需要用同一角色的“裸装登录 / 单件装备登录 / 穿上后重登”运行时
快照确认最终 UI 的实际差值；当前没有保留该组 trace，因此不能把重复的准确
倍率写死为结论。

### 2. 强化实例在穿戴边界被丢弃

背包实例结构含 `enhanceLevel`，但角色装备状态仅保存
`equippedItemIds[8]`。`vm_net_mock_role_equip_backpack_item()` 消费背包实例
后只写入 item id；`vm_net_mock_build_equipment_login_iteminfo_blob()` 又固定
下发强化等级 `0`。换装时旧装备也被固定写回 `enhanceLevel = 0`。

因此强化成功后即使背包中显示等级，穿上、换装或重新登录后强化等级也无法作为
该装备实例继续存在；服务端的属性收集函数当然也不可能将其纳入战斗。该偏离可
由静态状态结构和三条持久化/下发路径直接复现，不依赖猜测公式。

### 3. 四项战斗属性没有消费者

全服务器检索显示 `hit`、`dodge`、`crit`、`resist` 仅被目录解析、派生属性
构造和临时 buff 重算写入；普通攻击、技能伤害、怪物反击、切磋均未读取它们。
故装备的命中、躲闪、爆击、抗性词条现在不会改变命中结果、闪避结果、暴击伤害或
抗性减伤。

### 4. 耐久为零仍有装备属性

客户端重算明确跳过当前耐久为零的装备。服务端
`vm_net_mock_role_collect_equipment_bonus()` 只检查 item id、槽位和等级，未读取
`account_role_equipment_durability` 的当前值。因此耐久归零时，客户端显示层和
服务端战斗层会对该装备是否生效得出不同结论。

“每场扣 1、死亡/逃跑是否扣”的规则也只是当前 mock 玩法策略；
`docs/re/2026-07-22-battle-equipment-durability.md` 已记录它没有原服战斗包
证据，不能标作原版规则。

## 数值公式的证据边界

当前基础职业表、HP/MP、攻击、防御、命中等派生公式，以及
`attack * 100 / (100 + defense)` 均来自 2026-06-28 的 mock 玩法模型。提交记录
和 `docs/re/2026-06-28-player-attribute-model.md` 明确其目标是“让早期装备有
意义且保持 UI 可读”，而非从原服或客户端恢复出的公式。

客户端能证明字段布局、装备本地叠加和强化表的存在；它不能证明原始服务端在
战斗中采用哪一个最终伤害、命中、暴击、抗性公式。因此当前实现不能称为“完全
符合原游戏逻辑”。

## 后续正确修复方向

1. 先固定属性所有权：`actorinfo` 仅提供客户端期待的基础/权威字段，客户端
   本地负责已确认的装备显示重算；服务端战斗维护同一份服务器侧有效属性，不能
   依赖客户端显示缓存。
2. 将已穿戴装备改为实例状态（至少 `itemId`、强化等级、当前/最大耐久、稳定
   序号），并在背包、装备槽、换装、交易、登录同步之间原样迁移。不得由 item id
   推测实例属性。
3. 恢复数值规则前采集原服或可信旧服务端的最小对照：裸装、单件 1001、同件
   `+1`、耐久为 0 的登录属性和普通攻击/技能伤害；另采集命中、闪避、暴击、抗性
   各一组战斗结果。以这些包和客户端 parser 确定服务器公式，不能凭当前 `/3`、
   `/5` 系数继续调参。
4. 回归必须同时验证：角色属性页、场景 HP/MP 条、普通攻击、技能、切磋、
   强化后穿脱/换装/重登/交易，以及耐久为 0 的显示与战斗一致性。

## 第一阶段修正（2026-07-27）

### 可检验根因陈述

触发条件是角色携带任一装备后登录、穿脱/替换装备、交易装备或完成一场会扣耐久
的战斗。被违反的契约有两个：

1. `actorinfo` 的 HP/MP 和属性槽应是客户端装备重算之前的基础层，但服务端把
   已含装备的派生值写入其中；客户端随后在 `0x0100FED8` 又读取 `1/7/7` 的本地
   装备数据并叠加一次。首个错误状态是客户端场景节点拿到“已含装备的 base max”。
2. 装备是有强化和当前耐久的实例，旧持久化却把背包实例拆成
   `backpack.enhanceLevel`、装备槽 `itemId`、独立耐久表三份状态。首个错误状态是
   穿戴时背包行被消费、槽位只留下 `itemId`，强化/耐久不再有共同归属；交易路径
   还会在跨账号 SQL 写回时遗漏耐久字段。

客户端 `HandleItemOperationResponse(0x01033544)` 对 `type=3/4/9` 直接替换完整
`324` 字节物品对象，而非仅替换物品 ID。这与上述实例契约相互印证：服务端的
穿戴、卸下和替换不能各自重建强化或耐久。

### 已落地的修改

- 角色数据库版本提升到 `6`。装备槽改为
  `{itemId, enhanceLevel, durability, durabilityMax}`；背包行也保存当前/最大耐久。
  旧 v1--v5 文件和旧 payload 备份仅在读取时迁移，迁移后以 v6 关系表为唯一
  运行时来源。
- `account_role_equipment` 新增强化、当前耐久和最大耐久；
  `account_role_backpack` 新增当前/最大耐久。旧
  `account_role_equipment_durability` 只在首次迁移时、且 **role/slot/itemId 都相同**
  时作为来源，避免把旧槽位中另一件装备的耐久套到新装备上。
- 穿戴、卸下、`1/7/9` 替换、NPC 修理、战斗扣耐久、登录 `1/7/7` 与交易都迁移
  同一实例状态。装备不再按 item id 堆叠；背包中的装备一件一行、一件一个序号。
  事务写回也包含强化与当前/最大耐久。
- 服务端收集装备词条时与客户端 `0x0100FED8` 一致：当前耐久为 `0` 的装备不再
  参与服务器侧战斗属性。
- 场景登录 `actorinfo` 改为调用无装备的基础属性构造器；服务器战斗仍使用完整的
  装备实例状态。当前 HP/MP 保留耐久的服务器总上限，让客户端在本地叠加装备最大
  值后自行裁剪，而不在网络基线处错误截断。
- HP/MP 的职业升级增量不再沿用旧 mock 公式。它们直接使用
  `scene_apply_levelup_status_growth(0x01017F1C)` 的已确认值：

| 职业 / `visualVariant` | 每级 HP | 每级 MP |
| --- | ---: | ---: |
| 1 / 0 | 25 | 15 |
| 2 / 1 | 20 | 20 |
| 3 / 2 | 15 | 25 |

  以 1 级的 `120 HP / 100 MP` 为基数；装备生命/法力仍由 `equip.dsh` 词条叠加。

### 验证

- `make -j2` 已重新编译包含所有修改的 `obj/server/main.o`。最终覆盖
  `bin/jh-online-server.exe` 被正在运行的服务进程占用而失败（`Permission denied`）；
  使用完全相同的链接对象和选项输出到临时校验可执行文件，链接成功。
- `tmp/trade-equipment-instance-regression.c` 已重新编译并运行通过：
  `trade equipment instance regression passed item=1001`。该夹具覆盖同 ID 装备不合并、
  强化等级和当前/最大耐久随交易实例保留，以及 `WT21/6` 强化预览字段。
- `php -l scripts/equipment-durability-max-regression.php` 通过。该脚本已改为断言
  v6 `account_role_equipment` 中的实例耐久，而非旧的独立耐久表。
- 尚未对运行中的生产 MySQL 做写入式迁移夹具，因为它会创建/删除测试账号；待服务
  重启并在隔离端口运行后，应执行该脚本的 setup/run/cleanup 三段回归。

### 仍待取证，未伪造实现

- 力量、敏捷、智慧、体质、魅力的初始值和完整成长映射尚未从客户端/原服恢复；
  旧职业表仍明确标记为 mock 基线。
- 攻击/防御的装备**基础词条**已确认由客户端完整相加；角色自身的派生底数、强化
  的服务器侧追加值、技能伤害、命中、躲闪、暴击、抗性的服务器公式，尚无足以确定
  原版的包或反编译证据。客户端不能由本地展示加成反推原服战斗随机和最终伤害公式。
- 因此本阶段修复的是已确认的协议、实例归属、耐久失效和 HP/MP 成长契约；后续每一
  项战斗公式必须先以最小对照包/运行时记录证明，不能把旧 `/3`、`/5` 和软减伤公式
  误称为原版逻辑。
- 本次查询到的 IDA 实例只有 `MT6252_CH.bin`，没有打开 `江湖OL.CBE`；故没有把
  固件实例误当作江湖客户端来取证。以上客户端结论来自项目中已保存的江湖 OL
  反编译导出，后续若打开正确二进制，应按 `binary_name=江湖OL.CBE` 重新核验。

## 第二阶段：攻击/护甲的已证实基础词条（2026-07-27）

### 首次偏离、证据与修改

触发条件是角色穿戴任一带攻击或护甲的装备进入普通攻击、技能伤害、怪物反击或
切磋结算。此前服务器在 `vm_net_mock_role_build_player_stats_impl()` 中将装备攻击
按 `/3`、护甲按 `/5` 折算后才参与战斗；这两个除数来自早期 mock 的平衡曲线，
不是协议字段或资源定义。

首个错误状态发生在服务器汇总已穿戴装备词条时：`equip.dsh` 已给出完整基础值，
但汇总层在没有客户端或原服契约支持的情况下修改了它。静态证据如下：

1. `equip.dsh` 第 8、9 列的列名分别为“护甲”“攻击”；木制宽剑（1001）的攻击字段
   为 `30`，而不是需再缩放的内部量纲。
2. `CalcEquipStatBonus(0x01028B34)` 先将传入的装备基础值 `a3` 原样加入目标属性，
   随后才按每级强化表计算额外百分比值。
3. `scene_rebuild_status_meter_node(0x0100FED8)` 对当前耐久大于零的武器传入其攻击
   字段、对防具传入护甲字段。因此客户端展示层的基础装备词条没有 `/3` 或 `/5`
   的换算步骤。

据此，服务器战斗侧现在完整累加有效装备的攻击、护甲基础词条；该修改位于拥有
服务器有效属性契约的汇总层，而非网络包或客户端兼容层。

### 明确未扩大范围

本次没有根据上述展示逻辑猜测或改写以下内容：角色自身攻击/防御成长、强化在服务器
战斗中的追加规则、最终减伤曲线、技能系数，以及命中/躲闪/暴击/抗性随机结算。战斗
动作包由服务端下发最终目标结果；目前保存的客户端反编译只能证明它消费这些结果，
不能反推原服公式。后续需要裸装/单装备/不同强化等级的同目标战斗对照包后才可继续。

## 第三阶段：爆击、躲闪等直接装备词条（2026-07-27）

### 首次偏离、证据与修改

触发条件是角色装备带“爆击变化”或“躲闪变化”的有效装备，服务器随后读取完整
`vm_net_mock_player_stats`（战斗、临时属性修改或后续功能均会走该构造器）。此前
`crit` 和 `dodge` 分别只加入 `equip.dsh` 词条的一半；这两个 `/2` 同样来自 2026-06-28
的 mock 平衡模型。

这次的客户端证据比旧模型更直接：`scene_rebuild_status_meter_node(0x0100FED8)` 将
已装备物品的字段送入 `AddActorStatBonus(0x0100FE2C)`；该函数对每个输入字段均为
直接加法，不存在折半路径。服务端目录的列 15--18 已分别读取为 `crit`、`hit`、
`dodge`、`resist`，且列 16、18 原本已是直接相加。因此首个错误状态是服务器聚合层
对同一 DSH 基础词条作了只存在于 mock 的缩放。

`vm_net_mock_role_build_player_stats_impl()` 现对爆击和躲闪也完整累加有效装备的基础
词条。没有在此阶段创建命中判定、闪避随机或暴击倍率：它们目前在现有战斗结算中仍
没有消费者，且客户端动作包只消费服务端给出的最终结果，不能作为原服概率公式的
证据。

### 定向回归

新增 `tmp/equipment-stat-bonus-regression.c`：它从实际 `equip.dsh` 目录为生命、法力、
攻击、护甲、力量、敏捷、智慧、爆击、命中、躲闪、抗性各挑选一个非零词条装备，
以正耐久的装备实例构造完整服务器属性，并断言相对裸装的增量**恰好**等于目录基础值。
这覆盖了本阶段移除 `/2` 的爆击/躲闪，也防止已修正的攻击/护甲或其他直接词条被再次
缩放。

2026-07-27 实际运行结果：目录共加载 1485 条装备；11 个字段的取样（木制宽剑 1001
的攻击 30、普通衣服 3001 的护甲 45 等）均通过，输出为
`equipment direct-stat regression passed`。同一源对象也已成功链接为
`bin/jh-online-server-attribute-verify.exe`；常规 `make -j2` 的唯一失败点仍是正在运行的
`bin/jh-online-server.exe` 被 Windows 进程锁定，非编译或链接错误。

### 仍未恢复的战斗契约

继续搜索项目中的网络记录、历史提交和战斗反编译后，未发现原服的战斗动作对照包；现有
记录均为 mock 服务产生的动作结果。`HandleBattleActionMsg` 只读取服务端给出的目标和
数值，不能反推出命中、躲闪、爆击、抗性概率或最终伤害公式。`CalcEquipStatBonus` 虽能
证明强化是在基础词条之上追加百分比，但其强化表的权威数据源尚未定位。因此服务器暂不
把强化等级伪造为额外战斗加成，也不把已存的 mock 随机规则标记为原版逻辑。后续需要从
正确的 `江湖OL.CBE` IDA 实例或裸装/单装备/逐级强化的原服战斗记录恢复该契约。

## 第四阶段：ActorInfo 属性槽与职业三维成长（2026-07-27）

### 触发条件、首次偏离与根因

触发条件为角色登录或重新进入场景，服务端构造 `actorinfo`，客户端随后解析角色基础
状态并在本地叠加 `1/7/7` 装备词条。预期是力量、敏捷、智慧、命中、防御、抗性各写入
客户端对应的状态槽，未确认的速度保持为零。

实际旧实现把“六个属性词”按 `力量/敏捷/智慧/体质/魅力/防御` 顺序写入，同时把魅力
写到六词之前的标量。首次偏离位于服务端
`vm_net_mock_build_actor_info()` 的序列化所有权：客户端把该标量解释为力量，并把随后的
六个字依次存到完全不同的槽位，所以力量会落到敏捷、敏捷会落到智慧、智慧会落到命中，
而防御会落到抗性。它不是属性页排版或客户端刷新时序问题。

### 取证链

1. `parse_actorinfo_playerinfo_blob(0x0100FA88)` 解析 HP/MP 后，把下一个标量存入
   `actor+132`，再将六个词依次存入 `actor+290`、`+292`、`+298`、`+294`、`+306`、`+300`。
2. `scene_rebuild_status_meter_node(0x0100FED8)` 与
   `AddActorStatBonus(0x0100FE2C)` 对装备本地词条的写入证明这些已确认槽分别对应力量、
   敏捷、智慧、命中、防御、抗性；中间的 `+294` 是速度槽。
3. 直接读取 `bin/JHOnlineData/equip.dsh` 的 26 列标题并用客户端资源读取代码交叉核对：
   它含力量、敏捷、智慧、爆击、命中、躲闪、抗性，却没有“速度变化”列。因此速度没有
   可下发的 DSH 基线，写零而非把体质/魅力塞入该槽。
4. `scene_apply_levelup_status_growth(0x01017F1C)` 的三套职业增量直接写入力量、敏捷、
   智慧目标槽。登录 `job 1..3` 对应 `visualVariant 0..2`，故每级三维增量严格为：

| 职业 | 力量 | 敏捷 | 智慧 |
| --- | ---: | ---: | ---: |
| 1 / `visualVariant=0` | 12 | 4 | 6 |
| 2 / `visualVariant=1` | 6 | 10 | 3 |
| 3 / `visualVariant=2` | 3 | 6 | 12 |

当前打开的 IDA 实例只有 `MT6252_CH.bin`，未把它误用为江湖客户端；上述取证使用项目
保存的江湖反编译导出和 `江湖OL.cbe` 的离线资源/代码交叉检查。若后续打开正确目标，
必须按 `binary_name=江湖OL.CBE` 选实例后再作二进制级复核。

### 修改点与验证

- 增加 `vm_net_mock_build_actorinfo_status_fields()`，唯一拥有 fresh ActorInfo 的
  `actor+132` 与六词顺序。`endurance`、`charm` 不再错占该协议段；它们仍保留在服务器
  内部的未恢复 mock 模型中。
- `CBE_ACTOR_ATTR_STRENGTH`、`AGILITY`、`WISDOM` 继续作为明确的调试覆盖；旧的
  `ENDURANCE`、`CHARM`、`RESERVE` 覆盖不再冒充客户端定义的槽，改为
  `HIT`、`SPEED`、`DEFENSE` 三个与 wire slot 一一对应的名称。无语义的
  `CBE_ACTOR_EXTRA132` 覆盖已删除；`RESIST` 覆盖也已删除，避免它绕开由装备

### 仍未知的边界

该阶段没有把速度、体质、魅力的网络字段或成长凭空补出，也没有将攻击、防御、命中、

## 第五阶段调查：强化等级的基础词条加成（2026-07-27）

### 已确认的客户端算法

`CalcEquipStatBonus(0x01028BCE；旧导出中函数起点被标为 0x01028B34)` 是场景状态重建
和强化界面共用的计算器。对每件正耐久装备，它先将攻击或护甲基础值 `a3` 直接加入
目标字段；再对 `0 .. enhanceLevel-1` 的每一档读取一条 4 字节规则，并累计：

```text
bonus += rule[i].flat_u8 + (rule[i].percent_i16 * base_stat) / 100
final = base_stat + sum(bonus)
```

`scene_rebuild_status_meter_node(0x0100FED8)` 对武器传入装备 `+250` 的攻击字段、对
防具传入 `+248` 的护甲字段，并以 `+286` 的强化等级作为循环上限；它随后再处理可选
的装备附加属性列表。因此服务端若要让战斗侧纳入强化，必须使用同一张“每级固定值 +
百分比”规则表，而不是使用强化界面显示的成功率、玄晶等级、费用或一个猜测的线性倍率。

### 已排除的数据源

客户端资源字符串和本地文件核对表明，可见数据表只有 `item.dsh`、`equip.dsh`、
`skill.dsh`、`eidolon.dsh`、`sMap*`、`wMap*`；没有独立的强化 DSH。`1/29/1` 的
`data1/data2` 被 `HandleItemUseAndEquip(0x01028C7C)` 写入强化界面的需求/材料数组，
它们用于预览和成功率展示，不是上述计算器读取的规则表。当前 mock 的
`(level+1)*100` 需求、玄晶强度和费用均为界面交互实现，不能反推出属性加成。

规则表位于客户端运行时的物品控制结构 `+1412`，由 `CalcEquipStatBonus` 通过
`globalItemCtrl + 0x580 + 4` 读取；现有离线反编译导出未包含该指针的初始化写入。唯一
已连接的 IDA 实例仍是 `MT6252_CH.bin`，并非 `江湖OL.CBE`，故没有误用固件实例继续
猜测该表。

为获取这一缺失的权威数据，模拟器增加了一个严格只读的 `CBE_AUTOTEST` 取证点：当
`0x01028B34` 的主属性计算器真实进入时，它读取 `R9+0x54AC` 的物品控制器、其 `+0x584` 的规则表指针，
并将 16 个 `flat_u8 / percent_i16` 条目写入 `autotest/state.txt`。取证点不写入客户机
内存、不修改寄存器、不改变调用返回值；未开启 `CBE_AUTOTEST` 时完全不执行。一次带
任意装备登录或进入装备界面即可触发该客户端原生函数，随后可把实际 16 档规则纳入
服务端装备实例汇总并建立逐级回归。

2026-07-27 的本地无输入自动测试已验证该取证点不会干预启动、网络或场景状态，但测试
停在角色选择前，故没有进入 `CalcEquipStatBonus`，也没有产生规则表记录。为避免用自动
战斗、移动或背包操作改变测试角色的持久化状态，本次没有强行推进它。检索到的公开
“江湖 OL”强化资料属于其他同名/近名产品，不能作为本客户端数值表的证据，已排除。

### 结论与后续

2026-08-05 已由真实 `CalcEquipStatBonus` 算法与五件、四个强化阶段的独立数值样例唯一
恢复完整十六档表，并已在服务端装备实例层实现，详见
[`2026-08-05-equipment-enhancement-attributes.md`](2026-08-05-equipment-enhancement-attributes.md)。
