# 装备强化主属性：原生规则表初始化取证

Date: 2026-08-14

Status: investigating

## 1. 当前卡点

- 可见现象：桃木宽剑在 `+1`、`+2`、`+5` 后，强化等级和 `+4/+8/+12/+16` 阶段词条可以显示，但基础行仍为“物攻 +34”；防具的基础护甲行也同样不变。
- 触发方式：背包装备进入客户端原生强化界面，完成 `1/29/1 -> 1/29/2 -> 1/29/3` 的正常流程。
- 本轮最小目标：定位 `CalcEquipStatBonus` 所读取的十六档主属性规则表何时、由何种原生路径初始化；在此前不伪造实例刷新或改写客户端内存。

## 2. 已确认的运行时与 IDA 证据

| binary | function/address | findings |
| --- | --- | --- |
| `江湖OL.CBE` | `CalcEquipStatBonus(0x01028B34)` | 详情页的武器物攻/防具护甲基础行按 `itemCtrl+0x584` 的十六项 `{u8 fixed, i16 percent}` 规则累计；每级为 `fixed + floor(percent * base / 100)`。 |
| `江湖OL.CBE` | `HandleItemUseAndEquip(0x01028C7C)` | `1/29/1` 先进行预览计算，之后才将 `data1/data2` 写到材料需求和玄晶能力表；二者不能充当主属性规则表。 |
| `江湖OL.CBE` | `UpdateTaskProgressEntry(0x01028726)` | `1/29/3` 成功仅更新既有物品实例的强化等级和上限。 |
| `mmGameMstarWqvga.cbm` | `sub_D04(0x00000D04)` | `1/7/7 type=1` 是新增物品行；`type=2` 不消费解析出的实例行，不能按序号覆写已有强化装备。 |

隔离运行 `equipment-enhance-rules-probe-v1` 只走到了“场景 → 已装备栏位 → 替换/卸载菜单”。在真实
`CalcEquipStatBonus` 命中时读到 `itemCtrl+0x584 == 0`，但该场景没有进入背包的强化页面、没有发出
`1/29/1`，因此不能据此认定 `29/1` 之后也不会初始化规则表。

## 3. 首个已定位的自动化偏离

现有规则探针把屏幕坐标 `(166,127)` 当作强化入口。导出的帧证明它实际选中的是**已装备武器槽**；随后
`(34,382)` 打开“替换 / 卸载”菜单。该路径没有“强化”选项，也没有 `1/29/1` 请求，所以此前的超时只说明
测试场景走错 UI 分支，不能作为服务端或客户端初始化失败的证据。

## 4. 请求/响应契约

### 已确认

```text
1/29/1  强化第一页/预览；读取当前等级、最大等级、材料需求和玄晶能力表
1/29/2  强化确认页价格/金额
1/29/3  成功或失败；成功更新既有实例的强化等级
```

### 禁止作为“刷新”补丁的对象

- `1/7/7 type=2`：没有实例覆写语义；不能携带强化主属性或阶段词条去更新旧行。
- `1/7/7 type=1`、`1/30/21`：新增背包行，给同序号装备使用会造成重复或错误生命周期。
- `1/17/1`：详情/列表数据，不能替换主背包对象。
- `29/1.data1/data2`：材料和玄晶表，不是 `CalcEquipStatBonus` 的规则表。

## 5. 下一步探针

新增一个完全隔离的自动化场景：

1. 使用临时 MySQL schema、私有端口、私有客户端缓存和测试账号；
2. 进入场景后打开背包的装备分类，选中背包中的**未穿戴**装备；
3. 通过普通触摸队列按“强化”，等待真正的 `1/29/1` 请求与其原生响应；
4. 只截屏、记录请求/响应、记录 `itemCtrl+0x584` 的只读写入和后续 `CalcEquipStatBonus` 读值；
5. 不触碰“提交”，不发送 `29/2/29/3`，不消耗玄晶、不改动任何用户账号或数据库。

通过条件不是“不闪退”，而是请求、响应、客户端 parser、强化页渲染和规则表状态构成完整证据链。

## 6. 自动化输入链路校正（2026-08-14）

首次 `equipment-enhance-stage1-probe-v1` 没有出现 `1/29/1`。运行日志表明：

```text
frame 181  30/21 背包行已由客户端 parser 提交（桃木宽剑，seq=9）
frame 186  通过真实触摸队列点击背包
frame 188  点击“装备”分类
frame 189  立即点击第一行
frame 191  立即点击“强化”
```

导出的帧仍停在“道具”分类，说明旧用例把“触摸已投递”误当成“分类已经由客户端接受并渲染”。因此这一次没有资格评价
`1/29/1` 或规则表。旧的 `equipment-enhance-bag-probe-v1` 也有同一误判：它在分类实际未切换时报告 passed。

已将 stage-1 探针改为：先记录客户端背包 screen 的当前分类字段（`R9+0x5D08 -> screen+0x11B`），投递正常按下/释放事件，
仅在该字段被客户端改写且渲染边界到达后才继续点装备行。该字段只读、仅用于判定输入是否被原生 UI 接受；它不改变
客户内存、screen 生命周期或协议数据。后续截图和 `1/29/1` 才能形成有效证据。

## 7. 人工复现日志（2026-08-14）

为避免让自动化替代人工复现，客户端现对强化规则链路保留有界的只读诊断：

- `enhance_rule_table_watch_arm`：客户端物品控制器建立后，记录其规则表指针字段的地址。
- `enhance_rule_table_pointer_write`：原生代码首次写入该指针时，记录写入 PC 与值；不改写客户内存。
- `enhance_rule_table_ready`：`CalcEquipStatBonus(0x01028B34)` 首次读取到规则表时记录表地址。
- `enhance_calc`：仅对强化等级大于 0 的装备、最多 32 次，记录基础属性、等级、固定/百分比累加值及总值；可直接区分“规则表缺失”与“规则正确但 UI 使用了另一条值”。

服务端已有 `mock_equipment_enhance phase=1/2/3` 行，包含请求的装备序号、物品 ID、当前等级、材料、成功率、消耗与结果码。
人工复现一次“查看已强化装备属性 → 打开强化界面”后，应同时保留客户端控制台和 `bin/server_out.txt` 中这些行。

## 8. 当前结论

目前没有证据证明服务端可以用某个现有背包刷新包直接改写“物攻 +34”这一静态基础行。修复必须位于
客户端原生规则表的真实来源，或证明该来源确实应由服务端下发；在取证完成前，保持强化成功包为已确认的
`1/29/3` 契约。

## 9. 构建边界发现

执行 `make -j2` 时，客户端目标可以重新编译；服务端目标却会把 `src/main.c` 中的 LCD/Unicorn
模拟器函数一并编入纯服务端目标，随后在链接期缺少 `uc_mem_read`、`Lcd_Cache_Buffer`、`UpdateLcd`
等客户端符号。该问题不是强化协议失败，也不能通过把客户端库重新链入服务端来掩盖。

正确修复是让 `jh-online-server` 使用独立的、仅聚合 `src/server/mock-server.c` 的无界面入口；它保留
现有资源根解析和服务监听参数，但不编译或链接客户端模拟器。完成后才可运行隔离强化预览探针。
