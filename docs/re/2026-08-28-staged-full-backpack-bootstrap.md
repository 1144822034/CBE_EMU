# 使用原生登录请求分阶段建立完整背包词条（2026-08-28）

状态：服务端实现与确定性线包回归已通过；真实客户端隔离复测待执行。

## 现象与首个偏离

player-1 的真实日志表明，CBE 在 `5/10 + 7/7(type=1)` 登录组请求之后，会自然发送
两个独立的 `7/7` 请求，依次携带 `type=2` 和 `type=3`。此前服务端把 `30/21`、
`7/11`、登录装备 `7/7(type=2)` 与空的 `7/7(type=3)` 一起塞进第一个组响应。

`30/21` 的 `HandleItemGridResponse`（`JianghuOL.CBE:0x01039952`）才会释放并重建当前
背包主实例；`17/1` 仅更新另一份列表／缓存，不能补写该实例的词条。因此把完整四档词条
放在 `17/1` 中虽然线包正确，player-1 已证明它不会解决当前背包详情只显示 `+4` 的问题。

完整 `30/21` 也不能继续放在第一个组响应：已记录的 48 格、31 件装备形状会令
`event_packet_init(packet, 10, 19)` 的固定解析池在业务对象之前耗尽。第一次偏离不是词条
缺失，而是把“创建完整主实例”的对象放进了共享该解析池的错误响应边界。

## 服务端修复

当前登录流程按 CBE 已发出的请求边界分为三帧：

```text
CBE -> 5/10 + 7/7(type=1)
服务端 -> 组状态与正常状态对象（不含 30/21 / 登录装备流）

CBE -> 7/7(type=2)                 # 客户端原生后续请求
服务端 -> 完整 30/21 [+ 可选 7/11] + 正常 7/20

CBE -> 7/7(type=3)                 # 客户端原生后续请求
服务端 -> 7/7(type=2) 装备行 + 空 7/7(type=3) + 正常 7/32
```

第二帧的 `30/21` 使用角色持久化的完整 common-extra：每件装备均有
`+4/+8/+12/+16` 四个稳定词条；普通物品仍无属性行。该帧用 `30/21` 重建主背包实例，因而
避免依赖 `17/1` 对主实例的未知覆盖行为。第三帧保留已有的登录装备实例流及其原生
type-3 收尾。

阶段状态仅保存为当前服务端客户端会话中的 `roleId + stage`，不会写入角色数据。重复 group
请求不会重发对象；只有匹配同一角色的真实 type-2、type-3 请求可以推进阶段。新选角会重新
建立该会话内阶段。

## 平台边界

本方案没有修改 CBE/CBM、客户机内存、寄存器或 PC，也没有在宿主侧拆 WT 包、替换 callback、
重投 event 或合成任何客户端请求。服务端只对 CBE 已实际发出的独立 WT 请求返回对象；网络
宿主仍将完整响应字节以原 callback/context 投递给固件。
