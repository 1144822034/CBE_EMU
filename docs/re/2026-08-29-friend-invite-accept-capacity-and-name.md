# 好友邀请确认的按需关系查询与名字终止符（2026-08-29）

## 触发与首次偏离

复现链路为：甲在当前场景选择乙，发送 `1/10/3 { id }`；乙在正常场景轮询中收到
`1/10/4 { id, name }`，点击“是”后发送 `1/10/5 { id, result=1 }`。甲随后却在轮询
中收到 `1/10/6 { result=2, name }`，显示“对方拒绝”。两个好友提示窗口中的名字后还会
出现一段无意义的空白字符。

启动日志已经记录权威关系表加载为恰好 `records=256`。原服务端把
`VM_MOCK_SERVICE_FRIEND_DB_MAX_RECORDS=256` 同时作为全服的进程内快照上限；它不是
客户端 `10/1` 分页协议的上限。确认接受需要在同一候选快照中写入正、反两个关系行，
因此 `256 + 2 > 256` 在 MySQL 事务前即返回失败。`10/5` builder 只会在关系提交成功后
把 `sourceResult` 设为 `1`，所以它正确地把这个服务端容量失败编码成了 `10/6.result=2`。
首次偏离是服务端把存储快照容量误当成关系总数限制，而不是客户端把“是”编码错误。

## 客户端与协议证据

`JianghuOL.CBE:0x010114FC` 分发好友 kind `10` 的 subtype `4` 与 `6`：前者读取
`id/name` 并建立 `10/5` 的确认回调，后者读取 `result/name` 显示最终结果。
`JianghuOL.CBE:0x010114A4` 发送 `10/5 { id, result }`，其中 `1` 是同意、`2` 是拒绝。

同一个客户端确认框/结果框把 `name` 交给 C 字符串显示路径。此前 `10/4.name` 与
`10/6.name` 用普通长度字段写入，不含终止 `NUL`；字符串读取越过字段末尾后便把后续
缓冲区内容画为名字尾随空白。组队邀请的同类显示路径已使用带 `NUL` 的长度字段，提供了
相同编码契约的交叉证据。

## 修复

- 删除运行时的全服好友关系快照。`10/5` 接受时先按两端账号/角色精确查询现有行，再在
  一个 MySQL 事务中 upsert 正、反两条关系；数据库表不再因全服累计条数而将有效同意改写成
  `result=2`。
- `10/1` 好友页先按当前 `(owner_account_id, owner_role_id)` 执行 `COUNT(*)`，再按客户端
  已发出的 `index/pageSize` 执行 `ORDER BY ... LIMIT ... OFFSET ...`。内存仅保留该页至多
  255 条（`pageSize:u8` 的协议上界），不再读取或缓存其他角色的关系。
- 保留旧版 256 条 `nvram/mock_service_friends.bin` 的**迁移读取格式**；只有非密封的首次
  启动且关系表为空时才导入。`256` 不再是运行时业务限制；密封部署的关系表继续是唯一权威
  来源。
- `10/4` 与 `10/6` 的 `name` 改用长度包含末尾 `NUL` 的 WT 字段。字段名、对象顺序、
  `result` 语义、场景轮询投递和客户端 callback 均不变。

没有修改 CBE/CBM、客户端内存、寄存器、PC/LR 或已登记的网络 callback；服务端仍仅在
客户端自己的场景轮询响应中投递原始 WT 对象。

## 回归

`scripts/friend-invite-capacity-and-name-regression.c` 是隔离的服务端回归：不启动监听器、
不连接 MySQL、不写入用户账号或客户端缓存。它用内存夹具模拟数据库已有 256 条关系，验证
接受仍会执行一个双向 upsert 事务，并验证好友页仅查询 `LIMIT/OFFSET` 所请求的页面；同时
构造真实轮询下行 `1/10/4`、`1/10/6`，断言 `name` 字段长度包含且仅包含一个末尾 `NUL`。

人工复测：用两个不同账号在同一场景邀请，乙点击“是”；甲应收到同意提示，双方重新打开
好友列表后均可看到对方。再分别检查邀请框与最终结果框，角色名末尾不应再显示空白字符。
