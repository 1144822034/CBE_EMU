# 背包扩容步长对齐（806 → 64 格）

## 需求

在玩家背包常满的前提下，优先寻找**背包容量增加**（含分页等）方案；
若不可行再做仓库。

## 方案一结论：可行（已有协议，修契约）

客户端硬顶是 `InitTimerControl` 逻辑 **64** 格（`JianghuOL.CBE` /
既有 `BACKPACK_CLIENT_LOGICAL_CAPACITY`），不是无限分页堆叠。
可见列表由背包 UI 在这 64 格内滚动/翻页，**没有**单独的「超 64 分页协议」。

扩容权威路径已存在：

| 路径 | 契约 |
| --- | --- |
| 商城买 `806` | `mmShop:sub_9DE`：`capacity += 4`，不入库 |
| 使用 `806` | `7/1` + 容量刷新（既有 follow-up `17/1`） |
| `item.dsh` | 「增加您背包的存储空间**4**格」 |

## 根因

服务端 `VM_NET_MOCK_BACKPACK_EXPAND_STEP` 曾为 **5**，与客户端 `adds #4`
和 DSH **4 格**不一致。多次扩容后服务端空位数大于客户端插入上限，
表现为「服务端能买进、客户端插不进 / 仍觉得满」。

价格档 `mmShop:0x7EC`：`capacity==12→20`、`16→40`、否则 `60`（与代码一致；
初始 20 时商城价通常为 60）。

## 修改

- `BACKPACK_EXPAND_STEP = 4`
- 上限仍钳在客户端逻辑 **64**（`backpack_client_capacity` / expand usable）
- 仓库仍不实现（见下）

## 方案二（仓库/钱庄）：仍 blocked

| 线索 | 状态 |
| --- | --- |
| `item.dsh` **805 钱庄扩容**「存储空间**2**格」 | 有道具文案 |
| CBE 可打印「钱庄」UI/打开串 | 本次扫描**未找到**可靠 UI 串（旧文档里部分命中为误报） |
| WT 打开/存取/分页 | **仍 unresolved** |
| 805 商城特判 | 无（对比 806） |

按 `AGENTS.md` 不能伪造钱庄 WT。解阻仍需实机打开钱庄的 `net_trace` 或 IDA parser。

## 验证

1. `make -j2`
2. 容量 20 时买/用一次 806：日志容量 `20→24`（不是 25）
3. 重复扩容直至 64：再买 806 → `result=3` 扩容上限文案
4. 扩容后商城买普通秘宝可入库；客户端格子与服务端 `capacity` 一致
