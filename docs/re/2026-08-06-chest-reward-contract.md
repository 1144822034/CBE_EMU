# 青铜、白银、黄金宝箱：奖池与概率契约

## 结论

青铜宝箱、白银宝箱、黄金宝箱的**可开出物品与概率不由客户端
`item.dsh` 控制**。客户端数据只给出物品身份、说明与钥匙配对；奖池和
概率必须由在线服务端决定。

| 宝箱 | `item.dsh` ID | 匹配钥匙 ID | DSH 说明中的证据 |
| --- | ---: | ---: | --- |
| 青铜宝箱 | 522 | 813 | “请购买青铜钥匙开启” |
| 白银宝箱 | 523 | 814 | “请购买白银钥匙开启” |
| 黄金宝箱 | 524 | 815 | “请购买黄金钥匙开启” |

33 列 `item.dsh` 行中没有奖池、奖励数量或概率字段；客户端二进制中也未
发现三类宝箱名称/权重表。因而原始官服的历史赔率不能从当前客户端资源
可靠恢复，不能凭名称或物品价值猜测后写死。

## 触发与第一次偏离

1. 客户端对普通背包使用走单对象 `WT 1/7/1`。现有通用解析器读取
   `type`、`seq` 和可选物品选择字段。
2. 旧 mock 的通用 `vm_net_mock_build_item_use_response` 把所有普通
   `1/7/1` 都当作可消耗物品处理：消耗选中的物品、回 `7/1 + 7/7 +
   7/11`，但没有服务端奖励选择或奖励入包。
3. 因此首次违反的契约不是客户端显示，而是**服务端在把宝箱作为普通
   消耗品处理前没有建立奖池选择和宝箱/钥匙/奖励的原子事务**。

## 客户端响应取证

| 客户端位置 | 已确认行为 | 本实现用途 |
| --- | --- | --- |
| `江湖OL.CBE:0x01033544` `HandleItemOperationResponse` | `1/7/1` 是挂起物品使用确认；`1/7/11` 读取 `info` 的数量行 | 确认宝箱本体消耗并同步两件被扣物品的数量 |
| `mmGameMstarWqvga.cbm:sub_11CE -> sub_D04` | `1/7/7 type=2` 更新/移除行；`type=1` 的 `iteminfo` 是一次性物品增量行 | 扣除宝箱、扣除钥匙、加入获奖物品 |
| `江湖OL.CBE:0x0101191A` `HandleItemAcquire` | `1/7/37` 可按 `msg/result/itemid/seq/itemname` 插入物品 | **不与 `7/7 type=1` 混用**；已知战斗奖励运行时会导致重复本地添加风险 |

开箱成功的复合响应顺序为：

```text
1/7/1  使用确认（仅宝箱）
1/7/7 type=2 + 1/7/11   宝箱本体更新/移除
1/7/7 type=2 + 1/7/11   匹配钥匙更新/移除
1/7/7 type=1            中奖物品增量
```

若没有配置奖池、缺钥匙、背包无法接收奖励或保存失败，服务端只返回既有
`1/16/2` 提示路径；不扣除任何物品，也不落入通用 `1/7/1` 消耗处理。

## 服务端权威配置

`server_chest_rewards` 是唯一奖池表：

```text
chest_item_id, reward_order, item_id, item_count, weight
```

- 每次开箱从该宝箱全部奖励行中**按相对权重抽取恰好一项**。
  `实际概率 = weight / 同宝箱全部权重之和`。
- 每个宝箱最多 12 个不同物品；每项数量 1–99、权重 1–1,000,000。
- 装备、神仙壶、逍遥壶是独立背包实例，单项数量强制为 1。
- 保存时先用一个 projected role 副本验证：扣宝箱、扣钥匙、奖励入包都
  成功后才生成成功包并写一次完整角色快照；MySQL 保存失败则恢复内存快照。
- 新表不插入臆造的默认奖池。管理员必须在“宝箱管理”显式配置；清空奖池
  会停用开箱而不是让宝箱被无奖励消耗。

## 管理与迁移

- 后台：`/admin-418yz6/?tab=chests` 的“宝箱管理”。物品选择复用带分类和
  搜索的统一物品选择器。
- 新安装：`server/mysql/schema.sql` 已包含该表。
- 已部署库：执行 `server/mysql/migrate_add_chest_rewards.sql`；服务启动时
  也会以 `CREATE TABLE IF NOT EXISTS` 保证表存在。

## 已知边界

当前仓库没有保存原官服在这三类宝箱上的实际响应包或服务端数据表，故不能
声称后台初始赔率等于历史官服赔率。若后续获得原始开箱请求/响应或服务端
奖池数据，应补充到本记录，并将对应配置以明确迁移方式导入；不应修改客户
端或把猜测值设为默认。
