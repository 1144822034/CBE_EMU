# SCE 场景复制与内置地点名称编辑

## 需求与字段边界

后台需要从当前选择的 SCE 创建一份新的 SCE 文件，并允许指定新文件名；同时需要编辑
SCE 的内置场景名称，且两种修改都应进入启动内容更新清单。

取证确认三个相近名称不是同一个字段：

- SCE 文件名是客户端在场景切换和 WT 18/7 请求中保留的资源键，必须保持完整的
  `.sce` 后缀；
- SCE2 头偏移 `10` 的长度字符串是 `.map` 资源引用，不能因为改场景名称而改写；
- 已发货 SCE 的地点显示名称是首个已解析具名传送点的 string field `0x16`。内容列表
  已使用它作为主标题，相关解析见 `2026-08-27-admin-sce-location-title.md`。

因此“内置场景名称”操作只改 field `0x16`，不会猜测或重建 SCE2 头、MAP 引用、NPC
或其他传送点字段。

## 实现

`src/web_admin_server.c` 的 SCE 资源管理卡提供两项操作：

- **复制并发布**：目标名称必须是一个不存在的、安全的 `.sce` 资源键。服务端读取源
  SCE 原始容器字节，确认解码 payload 含 SCE2 头后原样原子写到目标；随后比较原始
  字节、重新解码目标 payload，并只在全部一致后调用
  `vm_net_mock_content_update_publish_files()` 发布目标资源。发布失败或写后校验失败会
  删除这份尚未发布的新副本，源 SCE 始终不变。
- **保存名称并发布**：解析当前 SCE，捕获首个具名传送点 field `0x16` 的精确长度字节
  位置，并再次比对 tag、field、长度和旧字符串。仅在这个比对成功后替换字符串、按源
  容器类型重新封装、重新解码验证，再发布原 SCE 名。写后验证或发布失败会用原始容器
  原子恢复。

复制和改名使用同一个现有 MySQL 内容更新事务；它维护累积清单及 WT 18/9 → WT 18/8
→ WT 18/7 原生下载路径，具体持久化契约见
`2026-08-10-content-update-mysql-authority.md`。本次不修改 CBE/CBM、客户端内存或
客户端资源缓存。

## 回归

`scripts/admin-sce-resource-management-regression.c` 仅读取仓库内 SCE 资源夹具：它找到
一个带已定位 field `0x16` 的具名传送点，验证替换前字段、替换后仅前缀保持不变、type 1
或 type 2 容器重新编码后可解码为完全相同的新 payload，并检查复制文件名和后台表单
契约。测试不启动监听器、不连接 MySQL、不写入资源或用户数据。

完整发布事务继续由既有内容更新发布回归覆盖；实际后台保存会在资源字节验证完成后进入
该事务，事务失败时不会留下未发布修改。
