# 强化到 +12 提示「强化等级达到上限」（2026-07-31）

## 现象

装备已强化到 **+12** 后再强化，客户端提示 **强化等级达到上限**。
服务端常量 `VM_NET_MOCK_EQUIP_ENHANCE_MAX_LEVEL = 16`，按理应可继续到 +16。

## 根因

为让本地 `power×100/required` 对齐「目标级 100% / 当前级 40%」，曾把
`29/1` 的 data1/data2 改成指数强度：

```text
power(tier) = 16 * (5/2)^(tier-1)
required(L) = power(L+1)
```

样例：

| L | required(L) |
| ---: | ---: |
| 11 | ~381469 |
| 12 | ~953674 |
| 13 | ~2384185 |

客户端解析 data1 时对过大需求值不耐受，可用强化上限被截断到 **12**；
随后 `curlevel >= maxlevel`（或确认路径等价判断）触发文案
`强化等级达到上限`（`江湖OL.CBE` 字符串表，对应确认失败 `result=5` 同类提示）。

服务端 `currentLevel >= 16` 才会回 `29/3 result=5`；+12 时服务端本不会因
MAX=16 拒单——是 **29/1 表把客户端本地 max 弄成 12**。

## 修改

- `data1/data2` 恢复紧凑线性表：`power=tier×100`，`required(+0)=100`，
  `required(+N)=N×250`（数值小，本地同级约 40%）。
- 真实预览/掷骰仍用 `crystal_unit_rate()`（目标级及以上 100%，当前级及以下
  `floor(/3)` 阶梯，见 `2026-08-01-enhance-same-tier-rate-div3.md`），经
  `29/2`/`29/3` 下发。

## 验证

- [ ] 重启服务后，+12 装备再开强化：不再提示上限；`29/1 maxlevel=16`。
- [ ] +12→+13 用十三级晶预览约 100%，用十二级晶约 33%。
- [ ] 可继续强化到 +16；到 +16 后再强才提示上限。
- [ ] `make -j2` 通过。
