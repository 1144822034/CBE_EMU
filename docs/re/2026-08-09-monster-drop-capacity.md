# 怪物掉落配置容量（2026-08-09）

## 触发与首次偏离

怪物已有两条掉落时，在后台批量选择七个物品，“加入掉落（7）”按钮会被禁用。
首次偏离发生在后台批量选择器计算空槽位时：它读取
`VM_NET_MOCK_MONSTER_DROP_MAX`，旧值为 8，因此仅余六个槽位。

这不是前端点击事件或数据库写入失败。相同的 8 条限制还被用于 SQL 加载、管理员保存、
运行时投掷结果缓存，以及战后 `1/7/7 { type=1 }` 背包增量包。因此只放开按钮会造成
“可配置但不会完整掉落或刷新”的契约不一致。

## 客户端与存储契约

`server_monster_drops.drop_slot` 是 `TINYINT UNSIGNED`。客户端
`mmGameMstarWqvga.cbm:sub_D04(0x0D04)` 消费的 `1/7/7 { type=1 }` iteminfo 以 `u8`
行数开头，随后逐行读取 `i16 seq`、`u32 item_id`、`u32 count_delta` 和 common-extra。
255 行仍在该计数边界内；最坏的普通物品增量内容约 20 KB，低于服务端
`g_netMockResponse` 的 128 KB 响应缓冲。

## 修正

- 将怪物配置、数据库读取、后台表单与运行时投掷共用的
  `VM_NET_MOCK_MONSTER_DROP_MAX` 从 8 提升到 64；2026-08-21 为覆盖全部品质 1/2
  装备，再提升到协议可表达的 255。
- 将战斗已成功写入背包的结果缓存和 `1/7/7` 构造上限同步提升到 255，确保每个
  已配置且实际投中的掉落都能在同一安全的客户端增量包中刷新。

这移除了旧的 8 条编辑器限制；255 是上述 `u8` 序列化契约允许的最大非零条目，
不是未受约束的无限条目。
