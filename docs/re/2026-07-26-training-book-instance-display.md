# 修炼天书实例（921）显示与说明

## 触发与现象

角色背包中持有 `921 修炼天书实例` 时，背包列表可能出现一个可高亮但没有文字的
空行；查看说明也会得到未配置占位文案。两者不是同一条客户端路径：列表文本来自
`7/42`，说明来自 `7/38`。

本次直接复核的持久化行是账号 `21642502`、角色 `10036`、序号 `22`：
`item_id=921, item_count=1`。同一数据库还存在一条历史 `921,item_count=2`
的行，说明实例物品还被普通背包堆叠路径错误合并过。

## 客户端与资源证据

1. `bin/JHOnlineData/item.dsh` 和服务资源
   `web/fs/JHOnlineData/item.dsh` 均含相同的两条记录：
   - `920` 名称为“修炼天书”，有通用说明，堆叠上限 `99`；
   - `921` 名称为“修炼天书”，但 `形象=-1`、静态“说明”列为空、堆叠上限 `1`。
   因此 921 不能依赖普通 `item.dsh` 说明完成显示，也不能作为可堆叠物品。
2. `JianghuOL.CBE:ParseBookInfoData(0x0100FD30)` 对 `1/7/42` 读取
   `booknum` 和 `booksinfo`。每项严格为
   `seq:<00 02 BE16> + title:<BE16 len-including-NUL, GBK,NUL>`；客户端在
   主游戏对象中分配每项 18 字节，将序号放在 `+16`、标题放在前 16 字节。
   `mmGameMstarWqvga.cbm:0x00003AA8` 在绘制 ID 921 时按背包序号查找这张表，
   匹配后直接以该标题覆盖本地名称。原服务端无条件下发
   `booknum=0/booksinfo=[]`，没有履行 921 的实例标题契约。
3. `江湖OL.CBE:SendItemSeqReq38(0x010238B6)` 对 921 发
   `1/7/38 {seq}`。`mmGame:0x418C` 收到 `7/38` 时读取 `bookdes`，交给天书
   UI；`HandleShopBuyItem(0x01025AE6)` 对 `7/40` 读取 `result/bookinfo`。
   两条路径均是字符串字段，不应下发通用 `7/1`。
4. 本地实际回放 `21642502/10036/seq=22` 的当前响应为
   `WT 1/7/38 {bookdes}`，原始 GBK 字节可正确解码为
   “修炼天书资料尚未配置，未消耗。”。因此编码并未在传输层损坏；首次偏离是
   服务端没有天书实例权威数据，只能下发占位资料。
5. 修复前 MySQL 没有书本实例表，`vm_net_mock_build_unresolved_special_item_response`
   曾对所有 920/921 返回同一占位文本。这与客户端的“按背包序号读取实例说明”契约
   不符；现有实例表中 `21642502/10036/22` 的标题是 8 个 GBK 字节
   `D0DEC1B6CCECCAE9`（“修炼天书”），数据源本身并不为空。

当前 IDA 注册实例只有 `MT6252_CH.bin`；本次没有把该实例硬编码为江湖 OL。
上述客户端反编译证据来自仓库已保存的江湖 OL 反编译文件。

## 根因

服务端把 `921` 当作只有 `item_id/count/seq` 的普通背包行保存，既没有创建按
`(account_id, role_id, item_seq)` 归属的天书实例，也没有遵循 `item.dsh` 的
`stack=1`。之后虽然补上了 7/38/7/40 的实例文本，但仍把 7/42 当作所有背包都可
为空的通用伴随包，漏掉了 921 的实例标题表。客户端列表渲染对 921 有专门的
“按序号覆盖标题”分支，因而首次违反的契约是 7/42 漏发该标题，而不是 GBK、背包
行 ID 或客户端渲染本身。

实现期间还验证了一个编码边界：C 的 `\x` 转义会继续吞入紧随其后的十六进制
数字。若把 GBK 全角冒号 `\xA3\xBA` 后直接写 `1` 或 `0`，编译器会把它解释为
`\xBA1`/`\xBA0`，下行字节末尾无效，客户端会显示乱码。本次固定资料改用相邻
字符串字面量切断转义，并用 `iconv(GBK→UTF-8)` 回归验证。

## 修复设计

1. 新建 InnoDB 表 `account_role_training_books`，主键为账号、角色和背包序号；
   保存 GBK 的标题、说明和阅读内容，以及等级/经验，为未来真实消耗结算保留
   权威位置。
2. 在角色背包关系数据的同一事务中重建该角色所有 `921` 的实例行。旧背包行在
   加载/保存时按 `stack=1` 正规化为每实例一个独立序号，避免一个实例记录代表多
   本天书。
3. `7/38` 与 `7/40` 仅在请求序号确实属于当前角色的 921 行时，从实例表读取
   `bookdes/bookinfo`；找不到或不属于该角色时保持专用失败响应，不伪造成功也不
   消耗道具。
4. 新建实例使用明确、GBK 可编码的默认资料；该默认资料由服务端持久化一次，
   不是客户端资源替换或每次请求临时占位。
5. `server/mysql/schema.sql` 和
   `server/mysql/migrate_add_training_books.sql` 都声明同一张表；运行中的服务在
   首次保存含 921 的角色前也会确保表存在，已有账号无需手工重置背包。
6. `7/42` 现在只枚举客户端可见的 921 行，从同一实例表读取标题，并按
   `0x0100FD30` 的 `seq + len16 GBK title` 格式写入 `booksinfo`。下行标题最多
   15 个有效 GBK/ASCII 文本字节加终止符，匹配客户端固定 16 字节标题槽；超过
   上限只在安全的 GBK 字符边界截断并记录日志，绝不向客户端写入超过该槽的长度。

## 验证

- 回放 921 的 `1/7/38` 与 `1/7/40`，断言字段是已持久化的 GBK 天书资料；
- 重启服务后再次读取同一序号，资料不变；
- 对历史 `item_count>1` 的 921 行，验证拆分为多个 `count=1`/不同序号的背包行
  和等量实例行；
- 确认 920 继续使用其既有 `7/35` 专用路径，921 不被 `7/1` 消耗；
- `make -j2` 通过。
- 在隔离的 `127.0.0.1:19094` 服务执行
  `php tmp/special-item-use-regression.php books 19094`：通过，输出
  `training book regression passed instances=2 rows=2`。该夹具从一条
  `item_count=2` 的旧 921 行开始，验证拆分、两条实例记录、7/38、7/40、GBK
  文本一致性与不消耗行为。
- 原有完整 special-item 回归在之后的独立挑战战斗断言处失败（战斗未立即结算
  胜利）；天书阶段已全部通过，未为无关战斗路径改动行为。
- 本次同一回归已额外打开背包，断言 `7/42` 含每个 921 的序号和 GBK 标题，且每条
  标题的带 NUL 长度不超过 16；这直接覆盖背包“高亮空行”的解析契约。
