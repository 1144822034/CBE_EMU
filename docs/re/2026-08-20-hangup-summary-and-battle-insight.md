# 挂机统计面板取证（2026-08-20）

Date: 2026-08-20  
Status: reopened — native hangup-mode transition and the `combatinfo` typed
sequential wire stream are confirmed in the current player-3 runtime. The
native stop acknowledgement is implemented and awaiting one manual lifecycle
verification.

## 现象

场景挂机可以正常进入战斗并完成原生 `4/7` 结算。结算奖励窗口能显示附加文字，但场景中的挂机信息面板（战斗场次、获得经验、金钱、回魔等）不随战斗改变。

## 已确认的链路

本次 player-3 运行记录显示每次自动战斗的响应都已按客户端顺序解析：

```text
2/10 + 2/2 + 4/5 + 4/11
... 客户端动作 ...
最后 4/6 + 4/7
```

- `mmBattleMstarWqvga.cbm:HandleBattleSettleMsg(0x743C)` 正常消费 `4/7` 的经验、金钱、HP、MP 等结算字段。
- 可选的 `4/7.fdata` 仅由 `0x7B08 -> 0x4462` 渲染为结算奖励窗口的文字。
- 运行复现确认该文字不会改变挂机信息面板，所以它不是统计面板的数据源；相应的汇总格式化器和回归已删除。
- `1/25/6 { result, tagged-u16 maxnum, iteminfo }` 仍是战斗心得专用确认包；`maxnum=200` 的类型契约由已有 special-item 回归覆盖，不能借此伪造普通挂机统计。

## 已确认的解析布局（显示语义待定）

当前 player-3 正常场景挂机运行中，服务端已经在每个原生 `4/7` 结算中发送
`combatinfo`，但 `DrawBattleMain(0x5444)` 读取到 `gameState+1136=0`。而
`mmBattleMstarWqvga.cbm:sub_7794(0x78E0-0x79DA)` 只有在该字段为 `1` 时才会先
清空 `gameState+516` 起的统计块并读取 `4/7.combatinfo`。因此服务端数值已经抵达
结算包却被客户端正确地跳过，"挂机中"状态和汇总面板也不会建立；这是当前可证实的
首个状态偏离。

`src/server/mock_server_battle.c` 现仅在同一角色、同一挂机会话、同一胜利结算的 `4/7`
对象中写入 `combatinfo`。本次运行导出的泛型读取器 `0x01033A5C` 已证明其每次读取都会跳过
两字节头、读取四字节大端值、再将游标推进六字节；不根据目标槽位的 16/32 位宽度改变步长。
因此 wire 是 8 个 `00 04 + u32` 字段，随后一个 `00 01 + u8` 标志字段，总长 51 字节。
下表记录的是 `sub_7794` 的读取布局；前两个 `i16` 合为原生“战斗场次 当前/上限”显示，
其余字段的显示语义仍以实际结算值验证：

| 顺序 | 类型 | 状态来源 | 读取位置 / 当前状态 |
| --- | --- | --- | --- |
| 1 | wire u32 → i16 | 已完成场次 | `game+516`；客户端截断写入 |
| 2 | wire u32 → i16 | 战斗心得挂机上限 | `game+518`；与第一项构成“当前/上限” |
| 3 | u32 | 本场已授予经验 | `game+520` |
| 4 | u32 | 本场已授予金钱 | `game+524` |
| 5 | u32 | 本场实际 MP 恢复 | `game+532` |
| 6 | u32 | 本场实际 HP 恢复 | `game+528` |
| 7–8 | wire u32 → i16 | 0 | 固件会读取，显示语义未确认 |
| 9 | u8 | 0 | 不启用会扣减客户端金钱缓存的可选尾记录 |

HP/MP 恢复值包含自动药品和配置恢复后实际被上限裁剪并持久化的数量；经验和金钱来自同一
次奖励事务，重复投递不会二次发奖。服务端实时结算日志已证明这些源数值正确；`4/7.fdata`
仍只负责战利品文字，不参与该面板。

`combatinfo` 是挂机会话的汇总快照而非单场奖励行：场次为本场结束后的累计场数，经验、金钱、
HP 和 MP 恢复为同一会话已结算值的累计和。服务端先用本场真实结算更新该会话一次，再写入快照，
从而避免每场将面板回退为当前奖励。

### 2026-08-20 显示值复现

一次早期试验中，player-3 的面板曾显示 `26214/13107` 等不相符数字，并随后发生除零。
43 字节 tagged 候选与 25 字节纯未标记候选都曾出现异常面板值。前者错误地将 16 位目标字段
编码为 4 字节内容，后者缺少读取器始终跳过的两字节头。运行时指令确认后，唯一满足游标契约
的格式是每个数值均为 `00 04 + u32`；即使首尾目标在客户端内存中只有 16 位，也必须如此编码。

下一轮程序保留一项有上限的只读 probe：它仅在结算解析器 `0x78E0-0x79DA` 的本地 PC 范围内读取
`game+516..538` 与 `game+1205` 的实际变化，不写客户内存、寄存器、包字节、输入或状态机。
它将把每个读取操作对应的客户端槽位变化与同场服务端结算值并列，作为确定 wire 格式的依据。
若该槽位记录仍不足以判定游标推进，程序会在首次进入该范围时从已加载的 VM 模块只读导出
`0x78E0-0x7A5F` 指令到玩家隔离日志目录的
`logs/hangup-combatinfo-parser-current.bin`。该文件不含角色内存、输入或包 payload，仅用于从
本次运行的真实指令确认读取宽度；完成取证后应随试验性追踪一并删除。
解析器在 `0x7908` 已初始化读取器，且随后每个字段都经 `R5+0x20` 的同一泛型读取入口。
若仍无法仅由写入结果判定格式，可同样只读导出该入口的 256 字节到
`logs/hangup-combatinfo-reader-current.bin`，并记录其运行时地址；该函数才是长度前缀和游标
推进契约的直接拥有者。

首次读取观察未产生有效数据，原因是网络回调中的 `R9` 属于主 CBE，而 `combatinfo` 块属于随后
进入的 mmBattle 模块；该观察已删除，未写入客户状态。正式挂机确认在
`DrawBattleMain(0x5E16)` 的实际模块 `R9` 下缓存模块基址，并只在 LCD 已渲染的
`phase=7/result=1` 状态经硬件输入队列确认；不再保留终局采样日志。

挂机场次现在仅在客户端原生 `25/5` 关闭结算面板后递增，并可饱和到 `u16` 最大值；已移除
战斗心得曾触发的服务端强制终止分支。战斗心得的经验效果仍按角色效果计算，不再改变挂机
的继续资格。

## 验证边界

已完成双目标编译。下一次运行须重启使用 `bin/jh-online-server.exe` 的本地服务，使 19090
端口加载新结算构造器；客户端会通过正常网络事件解析 `4/7.combatinfo`，没有客户端内存、
寄存器、指令或回调的强制修改。末尾两个保留 `i16` 的含义仍为 `unresolved`，当前保持客户端
安全的零值并在服务端日志中明确标记。

### 2026-08-21 战斗场次上限

`item.dsh` 的战斗心得（828）经其专用 `25/6.maxnum` 以 tagged-u16 下发 `200`；主程序的
`0x01026574` 按 16 位读取它。`combatinfo` 的第二个数也写入同样的 16 位显示槽。此前服务端
在每个 `4/7` 将该数硬编码为零，首次结算便会覆盖客户端已经取得的 200，造成“当前场次/0”。

现在服务端在原生 `25/2(type=1)` 启动时，将当前场景挂机上限快照到该客户端会话：普通挂机为
64 场，当前有效战斗心得提升为 200 场；初始 `25/3` 面板和每次 `4/7.combatinfo` 均使用同一数值。
待手工验证：未使用 828 时显示 `0/64`、第一场后为 `1/64`；启用 828 后相应显示 `0/200`、`1/200`，
经验、金钱、HP/MP 累计字段保持原值。

### 2026-08-21 上限到达后仍续战

触发条件为普通挂机完成第 64 场并关闭原生结算面板。当前 player-3 运行日志先在
`mock_hangup_combatinfo_client_write` 中记录客户端槽位 `64/64`，随后下一次网络事件仍解析出
`2/2 + 4/5 + 4/11`（`mock_hangup_mmBattle_start` 的对象序列），证明首次偏离不是显示字段而是
服务端在已达上限后仍构造了下一场自动战斗。

根因是 `scene_hangup_on_scene_default_event()` 在原生 `25/5` 边界只递增
`sceneHangupCompletedBattles` 并设置 `sceneHangupRestartPending`，而场景 poll、延迟期间的
`2/10+25/3` 确认，以及原生碰怪续战路径都没有把会话上限当成续战前置条件。

现在 `sceneHangupMaxBattles` 是启用会话的必填非零快照；统一 helper 仅在
`completed < max` 时允许续战。结算关闭使计数达到上限后记录
`scene_hangup_limit_reached ... action=stop-no-next-battle` 并清理会话，不再登记场景 poll。poll
builder 另有同一检查，以防止已经排队的轮询在旧状态下再产生 `4/5`；两个原生碰怪续战 predicate
也要求仍有剩余次数。`max=0` 被视为无效会话并停止，绝不解释为无限挂机。

待手工验证：普通模式第 64 场的 `4/7` 仍显示 `64/64` 并正常结算；关闭结果面板后不再出现新的
`4/5` 或下一场战斗，服务端出现上述 limit 日志。战斗心得模式相同地在第 200 场停止。

## 2026-08-21 候选表空调用调查

用户在点击原生挂机确认后报告 `pc=0x05031848`、`r0=0`、`r3=0` 的地址零访问。
当前 mmBattle 运行时基址为 `0x0502EF40`，故首个故障指令为本地 `0x2908`；它发生在
`sub_28A4` 的候选怪物建立阶段、客户端尚未发送 `25/2` 之前，因而不可能由后续 `4/7.combatinfo`
结算包触发。最新复现仍为相同 PC，且 `R0=0`、`R2=0x0500B400`、`R4=0x054007F8`；`R4` 的内容是
有效的场景对象指针表，故不能把最终的零地址访问误判成场景对象整体缺失。

先前取证探针错误地复用了上一场战斗 callback 记录的模块基址；独立的原生确认流程会在该记录
已退出后到达 `0x2908`，所以没有留下指令快照。探针现改为在每个执行 PC 上从加载器当前记录的
模块区间反求基址，只在 `mmBattle+0x2908` 执行前读取 `0x28C0-0x293F` 代码、`R2` 参数对象和 `R4`
对象首字节。该探针不修改客户内存、寄存器、PC/LR、输入或响应，下一次复现将据此识别空槽的
真实字段归属；不得通过伪造候选数、跳过调用或写入客户内存来掩盖该错误。

## 2026-08-20 运行时除零调查

面板首次显示非零值后，用户复现了 `Arithmetic exception: Divide By Zero`。崩溃寄存器中
`r4=0`、`r5=0xffffffff`；当前 `江湖OL.CBE` 的 IDA 解析将返回地址
`0x01004CD7` 定位到 `RandRange(0x01004CC2)`：它计算 `end - begin + 1` 后调用除法。
故本次进入除法时范围为 `0..-1`，即固件试图从空集合中选取随机项。

这已经排除经验、金钱或回血数值在服务端发生算术除零。后续读到 `RandRange(0,-1)` 的调用点
为 `mmBattle:sub_716E`（经 `sub_5FA`），其从本地自动目标列表按 `0..count-1` 取随机目标；本次
终局列表为空而退出标记已在开战包生效，故范围成为 `0..-1`。因此 `25/2{result=1,type=1}` 不能
放进开战包；它会在终局前错误进入空目标选择路径。临时 `RandRange` 调用记录已删除。

### 2026-08-21 自动关闭时序取证修正

首次 `DrawBattleMain(0x5E16)` 采样记录到 `mode=2, settlement_ready=0, guard=1`，但同一响应的
解析对象为 `2/10, 2/2, 4/5, 4/11`，即下一场的**开战包**而不是 `4/7` 终局包；因此不能据此推断
`25/2` 被 `4/7` 覆盖。该错误绑定已经删除。后续确认不再依赖该采样或 `25/2`：它只会在真实的
`4/7` 已完成渲染后，经正常触摸输入触发客户端自己的 `25/5`，不写客户状态、寄存器或响应字节。

早期实验曾尝试在开战或终局响应中附加 `25/2`。当前正常路径不再携带此对象：开战为
`2/10 + 2/2 + 4/5 + 4/11`，终局为 `4/6 + 4/7 + 7/11`。已保存的逐对象追踪证明，附加
`25/2` 即使被拆成独立 FIFO 事件，也会交给当前的 `mmBattle:sub_17AC(0x17AC)`。

`sub_17AC` 的顶层对象分派只接受 `4, 30, 28, 27, 14, 20, 7, 16`，**没有 `25` 分支**。
所以独立 `25/2` 被正常接收却被忽略，`Handle25_2(0x8996)` 也不可能命中。此前“拆分后会进入
Handle25_2”的结论已被运行时和反汇编共同否定，相关传输试验已经删除。

`Handle25_2` 本身的字段契约仍已确认：仅在其专用回调上下文收到 `25/2 {result=1,type=1}` 时，
才会把 `game+1136` 设为挂机模式，并走原生十帧的 `25/5` 关闭路径。当前战斗回调不是该上下文，
不能通过伪造 FIFO 事件、改写回调或直接调用客户函数来绕过它。下一步只记录主程序写入
`business_cb` 时的真实模块调用者，以及 `game+1136` 的首次写入者；只有确认正常客户端绑定
该专用回调的请求后，才修改服务端响应阶段。

实际可验证且客户端拥有的挂机结算关闭入口是已渲染 `4/7` 奖励面板上的确认触摸：
`BattleScene_HandleInput(0x62A2)` 会自然发送 `25/5`，服务端再从该正常生命周期推进下一轮和汇总。

## 2026-08-21：原生面板启动链路复核

Status: implemented, manual validation pending — 开启顺序已按客户端状态机实现；`25/3.info`
的逐字节视觉模板仍由原服务端拥有，不能伪称已还原。

### 当前卡点与首个偏离

用户点击场景“挂机”后，临时实现把首个
`2/10(Type=2) + 25/3` 直接解释为开战请求，或在其响应中附带
`25/2 {result=1,type=1}`。后者会令客户端进入挂机模式，却没有先建立自动目标候选表；
`mmBattle:sub_716E(0x716E)` 于是调用 `RandRange(0,-1)` 并触发除零。

随后为验证 `25/3` 的字段尺寸而回复了一个手工文本 blob。它触发的是
`sub_A818(0xA818)` 的**配置/汇总容器**，因内容不是原服提供的模板而显示为自定义文字。
该英文探针已删除；它不是可接受的产品行为，也没有写入客户端状态。

### IDA 证据与正确时序

| binary | function | finding |
| --- | --- | --- |
| `mmBattleMstarWqvga.cbm` | `sub_A4BC(0xA4BC)` | 清 `module+0x4060` 后发送空 `25/3`。 |
| 同上 | `sub_8996(0x8996)` case `25/3` | 读取 `num`、`info`、`mnum/idinfo`；置 `module+0x4060=1`，由 `info[180]` 决定原生面板行高。 |
| 同上 | `sub_A778(0xA778) -> sub_A4D4(0xA4D4)` | 处理面板原生开始输入；`A4D4` 先调用 `sub_28A4`，只在候选数 `module+0x3450` 非零时才发送 `25/2(type=1)`。 |
| 同上 | `sub_4FE(0x4FE)` | 挂机 tick 从候选表选中怪物后构造正常 `WT 4/1 { id,index,posx,posy }` 碰怪请求。 |
| 同上 | `sub_716E(0x716E)` | 以候选数作为随机上界；零候选直接解释为 `RandRange(0,-1)`，不能由服务端掩盖。 |

因此正确链路为：

```text
用户点击挂机 -> 2/10 + 25/3
  -> 服务端确认 2/10 并回复 25/3（服务器所属的面板数据）
  -> 用户点击原生开始控件
  -> 客户端 sub_28A4 建立候选表 -> 25/2(type=1)
  -> 服务端确认 25/2 -> 客户端挂机 tick -> 正常 4/1 碰怪
  -> 既有 2/2 + 4/5 + 4/11 自动战斗、4/7.combatinfo 与 25/5 结算链
```

`25/2` 不能再出现在 `4/5` 开战包或结算包中；它仅能答复客户端已经完成
`sub_28A4` 后的独立 `25/2` 请求。

### 已实现范围与未决项

已实施以下协议归属调整：

1. 首个 `2/10 + 25/3` 进入原生 `25/3` 面板响应，而非直接开战；
2. 独立 `25/2` 成功后才创建服务端挂机会话；
3. 将该会话的第一份客户端原生 `4/1` 视作挂机首场，并沿用既有 scene-monster 开战 builder；
4. 只在真实 `4/7` 奖励事务完成后累计面板数值。

`info` 是 `25/3` 的服务器文本字段，不存在于本 CBM 的字符串段。它的精确色彩控制码尚未
取证；初次面板现在仅填入“本次挂机确认”、本次上限、角色背包的已用/容量/剩余格数，以及
“是否继续挂机”。不会将尚未发生的战斗场次、经验、金钱或回蓝汇总伪装成确认内容。客户端
已有的确定/取消按钮仍由原生 `sub_A4D4` 状态机处理，因此此字段不是替代 UI。该未知项只影响
排版/色彩，不影响 `sub_A4D4 -> sub_28A4 -> 25/2 -> 4/1` 的客户端状态机和除零根因。

背包数字来自当前活动角色已经持久化的 `backpackItemCount/backpackCapacity`，并按既有背包
计数 helper 限制在容量内；本次上限在启动前按普通挂机 `64` 或有效战斗心得 `200` 计算。服务端
记录 `mock_scene_hangup_panel_confirm` 日志以保留当时的上限和背包快照。待手工验证：首点挂机时
原生确认框显示 `背包：已用/容量（剩余格）` 与正确上限，确认后才建立目标候选并进入战斗；取消
则不应发送 `25/2(type=1)` 或创建挂机会话。
修复应只在已确认的 `4/5 + 4/11(type=1)` 场景挂机会话中，等待 LCD 已渲染 `phase=7/result=1` 后经
模拟器既有硬件输入队列发送一次按下与释放；不修改客户内存、寄存器、PC/LR、回调或响应字节。
读取此状态必须使用实际执行 mmBattle 渲染代码时的模块 `R9`，不能使用主 CBE 的 `Global_R9`。

## 2026-08-21：停止挂机进度层卡住

### 触发条件与首个偏离

在已进入场景挂机且至少完成一场战斗后，用户点击“停止挂机”会留下不能消失的进度层。当前
服务端日志记录到该次点击的首个未处理请求：

```text
unhandled wt=2/10 len=34 objects=1
first=1/2/10:10,1/25/2:10
```

这不是启动时的独立 `25/2(type=1)`：停止按钮提交的是一个顶层 `2/10` 的复合请求，先含
`1/2/10 {Type=2}`，再含 `1/25/2 {type=2}`。此前 detector 只接受顶层独立 `25/2`，没有响应，
因此客户端自身的等待层没有收到关闭它的确认。

### 修复与验证边界

场景挂机 mode handler 现在严格解析上述两个对象、验证当前会话确实已启用挂机，并按同一对象
顺序回复：

```text
2/10(empty acknowledgement) + 25/2 {result=1,type=2}
```

服务端只在回复已经构造完成后清除该客户端的挂机会话、累计值和下一轮调度；不会修改客户端
内存、回调或进度层。启动的独立 `25/2(type=1)` 合约不受影响。

待手工复测的断言是：点击停止后进度层消失并回到场景；服务端产生
`request=2/10+25/2(type=2) response=2/10+25/2(result-1)` 日志；之后同一会话不再安排下一场
自动战斗。若任一断言失败，应以该请求和响应的原始字节继续定位，不能通过强制关闭客户端界面
规避。
