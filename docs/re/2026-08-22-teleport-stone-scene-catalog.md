# 场景传送石全量目的地目录

> 2026-08-22 后续修订：本页记录的是当时“所有带传送石标记的 SCE”目录方案，已被
> `docs/re/2026-08-22-teleport-stone-map-anchor.md` 取代。当前场景传送石只暴露同时
> 存在精确 `sMap.dsh` 行和可定位 `n_telestone.actor` 锚点的场景；不再分配合成 ID，
> 也不再使用场景入口/中心作为该功能的落点。

## 触发与第一处偏离

场景内触碰传送石后，客户端只显示“蓬莱-铜雀台”一个地点。客户端的传送石列表请求为
空对象 WT 1/16/1；mmGameMstarWqvga 的 16/1 parser 读取 exitinfo 的格式为：

~~~
u8 count
repeat count:
  u32 exit_id
  len16 label
  u32 reserved
~~~

旧的服务端列表构建器虽然已经按该数组格式写包，却固定写入 count=1、exit_id=1 和
蓬莱标签。更早的普通传送石目标解析也忽略确认包中的 exitID，始终使用默认蓬莱场景。
这就是第一个偏离点；并非客户端列表或滚动能力限制。

## 资源证据

- 真实资源目录 web/fs/JHOnlineData 下扫描到 28 个含字面 actor 名 n_telestone 的
  SCE 场景，包含太乙峰、临安-宣阳广场、蜀山南/北门、锁妖塔一层等。
- sMap.dsh 的 13 个字段中，第 0/1/2 列依次是 ID、地图名称、地图别名。对于已登记
  场景，行 ID 可作为稳定的 exitinfo ID，别名可直接作为客户端显示文本。例如
  11终南山_02.sce 的 ID 是 90，别名是“太乙峰”。
- 两个带 n_telestone 的已发货 SCE 没有对应 sMap 行：00蓬莱仙岛_04.sce 和
  c24侠客岛_01.sce。它们仍是实际场景资源，不能因缺少世界地图节点而静默回退到蓬莱。

## 修复

传送石列表与 16/2 选择目标现在共用同一个资源驱动目录：

1. 枚举服务端真实 SCE 资源名，逐个通过正常资源加载/解压路径确认 n_telestone；
2. 优先用 sMap 的精确场景行 ID 和地图别名构造目的地；
3. 对未登记 sMap 的原生传送石场景使用确定性的高区间内部 ID，并以场景键作显示名；
4. 16/2 读取客户端回传的 exitID，并从同一目录解析精确 SCE、真实 SCE 出生点与安全
   偏移。无效 ID 明确拒绝，不再错误回到蓬莱。

16/2 和随后 16/3 的确认链、每次消耗一枚 itemId=800、以及延迟 30/1 场景进入的既有
协议均未改变。普通世界地图的 16/4 仍继续走 wMap/sMap 子场景选择契约。

## 验证

已执行 make -j2，服务端完整编译、链接通过。

新增 scripts/teleport-stone-scene-catalog-regression.c。它不启动监听器、不连接
MySQL、不写入角色数据，只读取生产资源；测试成功（退出码 0），断言：

- 目录恰好包含当前资源内的 28 个 n_telestone 场景，且没有混入无传送石 actor 的场景；
- 太乙峰保留 sMap ID 90 和“太乙峰”标签；
- 未登记 sMap 的 00蓬莱仙岛_04.sce 仍获得稳定 ID 并可回解到自身；
- 16/1 exitinfo 的 count 与完整目录一致；
- 模拟 16/2 exitID=90 后，目标解析为 11终南山_02.sce，而不是默认蓬莱。

仍应使用持有传送石的测试角色在客户端手动打开一次列表，并选择太乙峰及一个非 sMap
场景，验收长列表滚动与完整 16/2+16/3+30/1 画面流程。
