# NPC 副本服务：传送与守关挑战独立直达

## 目标

后台将“副本传送”和“守关怪挑战”作为两个独立的 NPC 对话服务。玩家选择前者即进入目标场景，
选择后者即开始当前场景的守关战斗；两条路径均不再显示第二层副本操作对话或挑战确认窗。

## 证据与根因

`task_hall_activate_selected_entry`（`江湖OL.CBE:0x010492B0`）会把传送服务的 `action=1`
发送为 `WT 26/1 {type=2,id=value}`。旧副本向导首选项使用 `EAxxxxxx`（`OPEN_INSTANCE`），
服务端据此返回另一个 `26/1` 对话，其中才提供 `EBxxxxxx`（`ENTER_INSTANCE`）；这是传送二次
对话的唯一来源。

守关挑战可使用同一函数已验证的 `action=13` 分支：客户端直接发送 `4/1 {id,index,posx,posy}`，
服务端以既有的 `4/10` 场景战斗契约应答。该分支只在当前场景已部署对应 kind-3 战斗怪节点时下发；
不走 `30/9 → 30/10`，因此不会创建原生确认窗口。

已有 `ENTER_INSTANCE` 分支会复用经过验证的场景进入构造器，返回 `30/1 {scene,posinfo}`；
客户端由 `net_handle_scene_channel_dispatch(0x01039B8A)` 与
`scene_handle_enter_with_scene_pos(0x010396D6)` 消费该包并进入目标场景。该分支仍校验最低等级、
精确 `.sce` 目标与落点，并保存正常的场景切换目标和角色位置。

## 修改

- 服务类型 `6` 为“副本传送”，首选项为 `EB000000 | actor_id`，首次 `26/1` 直接命中
  既有 `instance-enter` 分支并返回 `30/1`；
- 新服务类型 `10` 为“守关怪挑战”，首选项在首层对话编码为 `action=13` 与守关怪 ID，直接进入
  既有 `4/1 → 4/10` 战斗链；
- 后台分别显示传送目标/落点和守关怪 ID；挑战目标只允许当前场景已启用的场景战斗怪。

未改写客户端内存、回调或场景状态；仍由客户端解析服务端的场景进入响应。

## 回归

`scripts/instance-guide-direct-entry-regression.c` 验证：

1. 配置目标场景的向导首选项生成 `ENTER_INSTANCE`；
2. 直接进入构造器生成一个 `1/30/1` 场景进入对象；
3. 独立守关挑战服务被标记为首层 `action=13`，不会回退到 `OPEN_INSTANCE` 菜单。
