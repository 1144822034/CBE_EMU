# 游戏内容管理：SCE、GIF 与 DSH

## 管理边界

后台“游戏内容管理”按实际游戏资源格式划分为三类：

- **SCE 场景**：分为 NPC 管理和坐标传送管理。
- **GIF 图片**：列出现有游戏 GIF，可预览、上传、新增或替换。
- **DSH 数据**：列出现有 DSH 表格，并可按字段逐行编辑或导入完整表格。

资源目录始终由服务端配置的权威游戏数据根目录决定。后台不读取或写入任一客户端缓存目录。

## SCE 坐标传送管理

传送点不是由后台额外数据库表覆盖。管理页从已解码 SCE 的原始记录中识别边界、区域和具名传送点，并在解析时保存目标场景字符串长度字节的精确偏移。

保存目标场景时：

1. 重新加载权威 SCE，确认该偏移仍是该条记录的 `field 6` 或具名传送的 `field 0x17`，并确认旧字符串完全匹配。
2. 仅替换 `u8 长度 + 目标 .sce 文件名`；入口编号、传送范围、坐标和交互名称保持原始字节不变。
3. DSH 作为原始表格文件校验：不会额外添加 GIF/SCE 使用的 type-1/type-2 容器。
4. 原子替换后重新解码并核对新字段，再通过内容更新清单发布。

目标必须是当前权威资源目录中**严格同名**存在的 `.sce` 文件。不会去掉后缀、补前缀，也不会把 `c00蓬莱仙岛_02.sce`、`00蓬莱仙岛02.sce` 等不同资源键视为同一场景。

## 游戏 GIF

上传 PNG、JPG、BMP 或标准 GIF 后，后台使用上传文件名的主名生成目标名，并统一使用 `.gif` 后缀。例如 `新商人.png` 生成 `新商人.gif`。

输出不是标准 GIF 文件，而是客户端 `gifDecodeExt` 读取的游戏资源：

1. 外层为四字节小端声明长度、type `1` 与自定义 GIF 负载。
2. 负载包含大端字典大小、256 色 RGB565 本地调色板、带透明索引 0 的图形控制扩展，以及 GIF 图像描述和 LZW 子块。
3. 透明像素映射到索引 0；不透明像素量化为最多 255 个 RGB565 调色板颜色。
4. LZW 使用“清除码 + 单像素码”的确定性编码，避免依赖猜测式压缩器。

上传限制为 2 MiB 源文件、768×768 像素。写入后会立即由同一个 `gifDecodeExt` 再次解码校验尺寸和像素缓冲；校验失败时恢复旧资源。

## DSH 导入与编辑

现有 DSH 是原始表格文件，不是通用 type-1/type-2 资源容器。文件头依次为：总长度减四、字段数、行数、字段头字节数；字段头由 GBK 字段名组成；每一行以行长度开头，随后按字段顺序存放“一个字节长度 + 值”记录。

后台会完整校验声明长度、字段头、行边界和每个字段记录。选择一个 DSH 后可跳转到任意行、编辑该行的所有字段并保存。保存前会核对该行指纹，避免覆盖其他管理操作；写入后重新读取校验整张表，随后才发布内容更新。上传替换同样要求完整的原始 DSH 表结构。

## 发布与回滚

SCE、GIF 和 DSH 的每次成功修改都会调用既有内容更新发布接口。发布通过 WT 18/9 与 WT 18/8 更新清单，并由客户端原生 WT 18/7 下载和安装资源。

顺序是：写临时文件、原子替换、重新从权威目录解码验证、发布内容更新。任一步失败都会恢复修改前的字节；不会通过默认资源或伪造成功掩盖格式错误。

## 验证

`make -j2` 用于验证服务端编译。运行中的 `bin/jh-online-server.exe` 会阻止链接器覆盖目标文件；此时需要先由操作者正常停止该服务进程，再重新执行构建。
