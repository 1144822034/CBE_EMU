# `7/42` 背包详情响应：线包验证与显示边界（2026-08-28）

> 2026-08-28 更新：本记录关于 `17/1` 不能覆写当前主背包实例的结论保持有效；“尚未找到
> 首次完整实例化方案”的结论已由服务端按 CBE 原生 type-2/type-3 请求分阶段下发的候选
> 取代。详见 [分阶段完整背包引导](2026-08-28-staged-full-backpack-bootstrap.md)。

## 当前结论

`WT 1/7/42` 的独立请求可以由服务端正常回复 `17/1 + 7/42`，其中 `17/1.iteminfo`
能够携带背包装备完整的 `+4/+8/+12/+16` 四档词条；这个线包契约已由
`first-login-equipment-attribute-bootstrap-regression` 验证。

但这**不能**作为当前背包界面已获得完整词条的结论。player-1 的实际运行已经否定了
“独立详情响应会刷新当前背包主实例”的推断：背包界面仍只显示 `+4`。

## 首个偏离

本次 player-1 登录记录显示：场景启动复合请求中虽包含 `7/42`，服务端按既有启动契约
返回的是紧凑 `17/1`（`layout=bootstrap-compact`，`iteminfo_len=989`）；其后没有收到
唯一、空负载的裸 `1/7/42`，因此 `builtin-backpack-open` 的完整详情响应根本没有执行。

更关键的是，`30/21` 的 `HandleItemGridResponse` 会创建当前背包所使用的实时物品实例，
而 `17/1` 的 `mmGameMstarWqvga.cbm:sub_418C` 走的是独立列表／缓存解析路径，没有已知的
“按序号覆写主物品实例的强化词条”行为。因此，即使随后请求了完整 `17/1`，也不能在没有
客户端证据的前提下宣称它会补写当前装备详情。

## 不可采用的历史方案

两天前可显示完整词条的仓库版本（`04ee3ef3`）并非已证实的原生服务端流程：它在宿主
`network-client.c` 中按登录响应内容拆出背包对象，并额外排入一次 event-7 解析。该逻辑
已在 `a13d1e1` 删除；恢复它会违反当前“宿主只做透明平台投递、不得按包内容拆分／重排
callback event”的边界，不能作为修复。

## 服务端当前边界

`vm_net_mock_is_backpack_open_request()` 只匹配完整 WT 包中唯一、空负载的 `1/7/42`。
该请求由 `builtin-backpack-open` 回应完整 `17/1 + 7/42`。普通更新的 `30/21` 仍保持有界；
首次登录的完整 `30/21` 改由 CBE 已自然发出的 type-2 请求承载，不能再塞回登录组合包。
该组合包与任务、场景对象共用 `event_packet_init(packet, 10, 19)` 的固定解析池，历史取证已
观察到在该处溢出。

## 下一步取证

候选已改为在登录 CBE 的独立 type-2 请求中下发完整 `30/21`，以其自身的响应边界创建主
实例；下一步是用隔离自动化完整记录该 callback 的 parser 路径和 LCD 帧。`17/1` 仍不作为
主实例词条修复手段。

## 回归的含义与限制

`first-login-equipment-attribute-bootstrap-regression` 仅构造真实裸 `WT 1/7/42`，经真实
dispatcher 校验严格有序的 `17/1 + 7/42` 及四项阶段属性。它不启动客户端，因而只证明
服务端响应字节的契约，不证明当前背包 screen 已消费或显示这些词条。
