# NPC 专属库存的批量编辑与默认价格

状态：已实现；包含隔离后台自动化回归。

## 原有行为与首个偏离

原后台把 `server_npc_shop_inventory` 逐条渲染为编辑行，新增入口也只能提交一个
`item_id`。库存展示缓冲区上限是 64 条；库存超过该数量时，后续记录不能在页面中
查看或删除。单价字段是必填项，后端也将 `unit_price == 0` 视为无效。

这不是客户端商店协议的缺口：客户端 `26/1` 商品条目需要正的 `u32` 单价。首个不
满足用户需求的层是后台配置模型——它没有“已选商品集合”或“目录默认单价”的语义。

后续在真实后台复现了“选中 84 件武器后保存失败”。请求本身没有超过 1 MiB 表单上限，
也没有到达 CSV 或商品分类校验。MySQL 中同一 Actor 30093 有两条父记录：旧键
`c04临安府_01` 的服务类型是修理、精确键 `c04临安府_01.sce` 的服务类型才是武器商人。
后台列表以宽松场景比较展示后者，提交处理却按数据库排序先解析前者，因此在库存写入前
错误地拒绝为“服务类型无效”。这不是 84 项的数量限制问题，而是旧的裸场景键破坏了动态
NPC 的精确资源键唯一性。

## 正确契约

商品的权威来源仍是当前服务端商品目录：`item.dsh/equip.dsh` 加上
`server_shop_items` 覆盖。商人和商品分类必须与客户端菜单契约一致：

| 服务类型 | 可配置商品 |
| --- | --- |
| 武器商人 | 装备分类 7–9（剑、匕首、杖） |
| 防具商人 | 装备分类 0–6 |
| 药品商人 | 非装备分类 10 |

后台的“留空单价”表示保存时使用该商品当前的目录有效价
`vm_net_mock_shop_effective_unit_price()`；该正价写入专属库存表。这样下次下发商店包
仍是客户端可解析的显式单价，而不是依赖客户端猜测默认值。之后若改变全局目录价格，
已配置的专属库存不会被悄悄重写；管理员可再次留空批量保存以采纳新目录价格。

`server_shop_items.enabled` 只控制全局商城页面是否列出商品；它不是物品
资源是否存在的开关。NPC 专属库存的上架状态完全由
`server_npc_shop_inventory.enabled` 决定。因此商城中下架的装备，只要该 NPC
库存行已上架且单价为正，仍必须出现在该 NPC 的购买分类中。此前商人选项统计
错误复用了商城开关，会把一整个已保存的专属库存过滤成“暂无可购买商品”。

库存的持久化键、客户端进入场景后用于 `26/1` 的 NPC 服务会话键以及动态 NPC 父记录，
都必须是同一个完整 `*.sce` 资源名。库存查找使用字节级 `strcmp()`；任何无后缀形式都
不是合法别名，因此 `c00蓬莱仙岛_02.sce` 与 `00蓬莱仙岛_02.sce` 严格属于两张不同地图。

武器与防具另使用 `equip.dsh` 的第 6 列“品质”进行二次筛选。它只是目录中的原始
装备品质；不是角色装备实例的强化等级，也没有被猜测映射为颜色或稀有度名称。因此后台
按资源中的实际数值显示为“品质 0”、“品质 1”等。药品没有该目录字段，品质筛选不显示。

## 修改点

1. `src/web_admin_server.c` 将库存改为完整列表，并提供独立的多选商品弹窗：按当前
   NPC 服务类型过滤、名称/ID 搜索、按分类筛选；武器/防具再按 `equip.dsh` 品质筛选，
   并可对当前筛选全选、移除暂存选择。已有库存也可按分类和品质筛选后批量移除。
2. POST 新增 `save-npc-inventory-bulk` 与 `delete-npc-inventory-bulk`。CSV 选择集合在
   解析时限制为商品目录容量、禁止 0 和重复 ID。
3. `src/server/mock_server_scene_task.c` 在数据库写入前重新验证场景、NPC、服务类型、
   商品目录存在性和分类边界。批量新增/更新与批量删除均在一个 MySQL 事务中提交；
   仅 `COMMIT` 成功后更新内存缓存。
4. 仍保留逐条编辑和删除，便于调整单个价格/上下架状态；其空单价也会按相同契约解析。
5. Windows 后台的 SCE 枚举也改为优先使用已生效的服务资源根目录。此前它只扫描相对
   `web/fs/JHOnlineData`，而预览/加载已经使用 `--resource-root`；运行目录变化时，页面
   能预览场景却会在提交时以“场景无效”拒绝自身表单。现在枚举和提交验证使用同一资源根。
6. 启动加载动态 NPC 时先扫描旧的裸场景键，并且只在 `<旧键>.sce` 确实存在时开启事务迁移。
   迁移会保留精确键的冲突配置、搬运没有冲突的任务/副本/专属库存行，然后删除旧父行；删除
   前在同一事务内再次读取并要求精确 `.sce` 父记录恰好存在。若该前提不成立会回滚并保留
   旧记录，而不会把一个可编辑 NPC 变成孤儿。迁移完成后再建立运行时目录，故后台和场景
   运行期都不会看到宽松键的双记录。`c00` 与 `00` 等不同资源前缀不会合并，只有缺失
   `.sce` 后缀的同一资源键可以迁移。
7. 后台 Actor 编辑和库存 POST 按精确场景资源键查询动态 NPC，不使用运行期的宽松 `.sce`
   后缀比较。库存 POST 的动态父记录直接从 MySQL 精确查询；场景投递使用的长生命周期
   内存目录不能再决定持久化写入是否有父对象。找不到父 NPC、服务类型不支持库存、单项
   物品缺失三种拒绝分别记录并向页面说明；不再把它们混成“NPC、服务类型或物品参数无效”。
8. 动态 Actor 编辑卡片按“身份与位置”“脚本/任务/副本设置”“保存与危险操作”“专属库存”
   分区；宽屏使用紧凑网格，小屏自动改为一列，避免库存按钮挤入 Actor 基础字段区域。库存
   工具栏也保留“添加商品”和“管理已有库存”两块及响应式布局。
9. 批量“加入库存”表单的 `actor_id` 必须由当前 Actor 的 `actorId` 直接渲染，绝不能借用
   服务类型。一次格式化调用遗漏该参数会触发 C 可变参数未定义行为；实际页面把武器商人的
   服务类型 `1` 输出为 `actor_id=1`，使服务端正确地找不到该 NPC。已将参数补齐，并把新建
   武器商人页面的隐藏字段精确等于其 Actor ID 加入自动化断言。
10. `src/server/mock_server_scene_task.c` 中服务期库存查找以“场景规范化后的资源身份 +
    Actor ID + 物品 ID”为键；此前该路径把会话无 `.sce` 键与库存 `.sce` 键直接 `strcmp()`，
    造成库存已经提交却在触碰 NPC 时统计为零。持久化与后台父记录检查仍保留精确 `.sce`
    资源键，只有服务期读取采用上述受限的后缀规范化。

## 自动化回归

`scripts/run-npc-stock-automation.ps1` 的场景 ID 是 `npc-stock-bulk-v1`。它创建唯一的
`jh_online_autotest_*` schema、独占端口、资源副本和服务 PID，准备一个动态武器商人，
并经实际后台 HTTP 路径验证：

1. 登录后服务端渲染多选器、`equip.dsh` 品质元数据与分类/品质筛选、批量移除控件；
2. 构造同 Actor 的旧裸场景键（非商人）与精确 `.sce` 键（武器商人），确认启动迁移后
   旧键不存在且精确键仍拥有武器商人服务类型；
3. 84 件武器以空单价批量保存，数据库中的单价等于页面商品目录默认价且均上架；
4. 通过后台新增商人后可立即配置库存；另模拟另一服务实例在缓存建立后写入父 NPC，
   后台仍能按 MySQL 中的精确父记录保存库存；
5. 药品不能被伪造请求写入武器商人库存；
6. 所有库存可以一个事务地批量移除；
7. 从服务端读取的 `admin.js` 通过 `node --check` 语法检查。
8. 使用正常 CBMS/WT 服务端点完成 `1/12` 登录、`1/6` 选角和三次 `26/1` NPC
   对话（触碰商人、选择武器、选择剑类），断言商城全局下架的 1001 仍作为该 NPC
   已上架库存出现在剑类响应中。该步骤同时覆盖库存、动态 NPC 与实时服务上下文都使用
   同一个严格 `.sce` 场景键。

运行前必须显式提供自动化 MySQL 密码；运行器不接触 `jh_online`：

```powershell
$env:CBE_AUTOMATION_MYSQL_PASSWORD = '***'
.\scripts\run-npc-stock-automation.ps1
```

证据写入 `artifacts/automation/npc-stock-bulk-v1-*/`，包括运行上下文、服务端输出、HTTP
回归日志和所下发的 JavaScript。场景还保存真实服务端 `26/1` 对话链的响应断言；客户端
实际渲染与购买手感仍由人工验收覆盖。
