# 怪物管理目录覆盖核对（2026-07-24）

## 触发条件

后台“怪物管理”的左侧目录看起来没有列出全部可作为任务击杀目标的怪物。

## 数据链路与证据

后台页面调用 `vm_net_mock_monster_admin_list()`，它只枚举
`g_vm_net_mock_monster_entries[]`；MySQL 的 `server_monsters` 只是该目录中
已有 ID 的属性覆盖，不能补出目录外的怪物。

对服务端资源 `web/fs/JHOnlineData` 交叉读取后得到：

| 来源 | 结构化字段 | 唯一非零 ID | 与原目录的差异 |
| --- | --- | ---: | --- |
| `automonster.dsh` | `怪物id1..3` | 73 | 无差异 |
| `task.dsh` | `任务要求类型=2`、`任务要求ID` | 51 | 原目录遗漏 `23`、`38`、`44` |

`task.dsh` 中三条可复核记录为：

| 怪物 ID | 任务 ID | 任务目标中的名称 | 任务等级 |
| ---: | ---: | --- | ---: |
| 23 | 5004 | 冥火麒麟【燎天】 | 40 |
| 38 | 112 | 火凤凰 | 30 |
| 44 | 407 | 火蝮蛇 | 40 |

此前目录共 77 项：自动刷怪 73 项，另有任务专属的 `15`、`63`、`65`、`300`。
因此“自动刷怪 ∪ 结构化任务击杀目标”应为 80 项，第一次偏离就在静态目录没有加入
上表三项，而不是后台 HTML 筛选、分页或 MySQL 查询丢失了行。

## 修复

- 将 `23`、`38`、`44` 加入统一怪物目录，使属性、掉落、MySQL 覆盖和后台列表使用
  同一个合法 ID 集合。
- 三项的初始等级采用对应任务等级；没有恢复到原始服务端战斗属性表，初始类型按其
  已知名称作服务端建模：冥火麒麟为首领、火凤凰为飞行、火蝮蛇为爬行。它们仍可在
  后台编辑，不把这些推断描述为已恢复的原始数值。
- 为所有任务专属目标补充 GBK 名称和 `task.dsh#任务ID` 来源标签。SCE 自动出生扫描
  仍会为普通怪物提供真实场景名；任务专属目标没有自动出生记录，页面因此使用
  “出现位置／来源”而不是错误地称作“首次场景”。

## 验证结果

1. 静态目录复核为 80 个唯一 ID；全部 73 个 `automonster.dsh` ID 均在目录中，任务
   专属集合为 `15,23,38,44,63,65,300`。
2. `make -j2` 已重新编译服务端对象；正式 `bin/jh-online-server.exe` 正被运行中的
   服务占用，Windows 拒绝覆盖该文件。随后使用同一组对象执行
   `make -j2 server SERVER_TARGET=bin/jh-online-server-monster-catalog-check.exe`，完整链接通过。
3. 用独立校验服务（19190/19191）登录后台并请求
   `/admin-418yz6/?tab=monsters&monster=23`：HTTP 200，页面显示“怪物目录（80）”、
   `#23 冥火麒麟 / task.dsh#5004`、`#38 火凤凰 / task.dsh#112`、
   `#44 火蝮蛇 / task.dsh#407`，并显示“出现位置／来源”。校验服务已停止。
4. 校验过程还暴露原 `-fwhole-program` 与分开编译服务端对象不兼容：重新编译
   `mystd.c` 后，GBK/UTF-8 辅助符号会被错误内部化而无法链接。已从服务端编译选项
   移除该标志；后续用全新对象目录完整编译，以保证“火蝮蛇”等 GBK 名称由当前源码的
   iconv 路径转换，而非复用旧对象。
