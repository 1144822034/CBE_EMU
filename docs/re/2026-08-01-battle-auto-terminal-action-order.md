# 自动战斗：多目标动作队列与终局结算的事件顺序

## 新的手工复现证据

在上一轮修复后，首个死亡动画不再重复，但用户观察到“剩余怪物攻击玩家后没有后续推进”。本次只读取用户运行后的 `bin/server_out.txt`，关键链路为：

```text
tick 102: 4/6 actionnum=3
          玩家攻击 -> 第一只怪物 type-3 死亡 -> 存活怪物反击
          next_tick=132
tick 132: 4/6 actionnum=2 + 4/7 + 4/9
          玩家攻击 -> 最后一只怪物 type-3 死亡 -> 立即结算/关闭
```

服务端在 tick 132 已经把第二份响应（`resp=307`）发出，因此“尚未有下一步”不是怪物 HP 槽未被扣减，也不是服务端未调度第二次攻击。

## 客户端契约

- `mmBattleMstarWqvga.cbm:HandleBattleActionMsg(0x6EB0)` 为 `4/6.actionnum` 的每一条记录分配一个动作槽。
- `DrawBattleSceneBg(0x4BE8)` 和 `sub_4B38(0x4B38)` 异步逐条完成普通攻击、type-3 死亡等槽位。
- `HandleServerBattleCmd(0x7BD0)` case 6 只入队 `4/6`，case 7 会立刻调用 `HandleBattleSettleMsg`，而 case 9 会立刻切换至终局 phase 8。

因此最终响应中的 `4/7` 不是可任意挪后的“结束通知”：它必须和最后的 `4/6` 一起建立 type-3 死亡回调所需的结果缓存。真正不能与该动作队列同事件发送的是 `4/9`；即使对象顺序是 `4/6 -> 4/7 -> 4/9`，case 9 仍可能在最终攻击/死亡动作完成前切换战斗 phase。这是本次的第一个协议顺序违反。

另一个相邻的时间边界问题是：旧逻辑以 `actionnum * 10` tick 作为下一个 `4/6` 的到期时间。上例的首轮 `actionnum=3` 恰在 tick 132 交付下一包，和第三个（怪物反击）动作的完成帧重合；网络事件可以先于该帧的完成回调进入 parser。

## 修复（第一次修正后的反证与最终边界）

第一次修正把 `4/7` 与 `4/9` 一起延后，实际双怪终局仍复现“最后一只死亡动作循环”。运行记录已排除槽位映射问题：首只死亡为 `target=0`，最后一只为 `target=2`，终局 `4/6` 的三个敌人 HP 槽均为 `0`；同时记录到延后包在 `actionnum=2` 的 21 tick 边界后发送。

客户端代码给出了更早的契约：

- `HandleBattleActionMsg(0x6EB0)` 先登记最终的 `4/6` 动作队列；
- `sub_4B38(0x4B38)` 在 type-3 死亡动作完成时调用 `Callback_Unknown1(0x30D4)`，由该回调建立自动战斗的终局状态；
- `HandleBattleSettleMsg(0x743C)` 必须在这个回调之前已经获得本场的奖励/结果缓存。既有运行反证也确认，把 `4/7` 推迟到下一请求会使结算缓存为零。

因此正确边界不是延迟结算，而是只延迟关闭：

1. 自动行动间隔仍按每条 `actioninfo` 一个 1000 ms 原生动作阶段计算，并在末尾加一个调度帧（100 ms）；`actionnum=3` 从 30 tick 改为 31 tick。
2. 最终战斗响应保持 `4/6 -> 4/7 [-> 7/7]` 同一网络事件，确保 type-3 死亡回调读取到本场终局缓存。
3. `4/9`（普通自动路径前置的 `4/11(type=0)` 也同属关闭组）独立留到动作队列越过该边界后的 scene poll 投递；不再与 `4/7` 同包。
4. 八秒奖励窗口中的无奖励终局虽不生成 `4/7`，仍使用同一个最终动作到关闭的边界；不会在 type-3 死亡动作期间提前发 `4/9`。
5. 关闭等待状态纳入按账号捕获/恢复的 battle state，避免并发请求切换活动账号时把一个角色的终局关闭投递给另一个角色。

该变更不更改 `actioninfo` 的怪物槽位、死亡 type 或反击顺序；它只将“结果可用”和“关闭战斗画面”恢复为客户端的两个不同生命周期点。

## 可观察日志与手工验证

终局自动攻击时应出现：

```text
mock_battle_terminal_close_deferred ... actionnum=2 delay_ticks=21 not_before_tick=...
mock_battle_terminal_close_deliver ... tick=<不早于 not_before_tick> response=close
```

验证场景：三怪挂机中击杀第一只后，应先完整播放两只存活怪物反击；下一次玩家攻击只在下一帧边界后开始。最后一只死亡后，`4/7` 应随最终 `4/6` 到达，随后才在动作边界后的轮询中发送关闭组；不得卡在最后一个怪物攻击动画，也不得重新出现死亡动画循环。

未解决的字段语义：真实线上服务对“动作完成”没有可见客户端 ACK。本实现仅使用已验证的客户端动作阶段和严格下一帧边界；若某特定资源仍超过该阶段，必须保留其原始 tick、`actionnum` 和响应包，再针对资源播放回调取证，不能继续任意增加全局等待时间。
