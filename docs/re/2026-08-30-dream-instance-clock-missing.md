# 梦境副本右上角时间未显示

Date: 2026-08-30

Status: original timed-instance contract unresolved; UI-asset hypothesis narrowed; no behavior change

## 当前结论

- 用户提供的 `梦境空间三层` 截图证明这串数字位于地图画面层（约
  `x=250..335, y=116..136`），不在顶部固定 HUD 的框体内；其红黄像素字形与资源槽 73 的
  `-num.gif` 一致。数字的四个主字形起点约为 `x=273/291/319/337`，中间有一枚细小分隔
  像素；结合画面，最合理的读法是 `08:05` 的 `mm:ss` 形式。这是基于截图布局的推断，
  不是已证实的协议字段。截图顶部 HUD 在工具栏之后没有常驻时钟、分隔符或固定计时背景。
  这排除了“普通状态栏计时器”的解释，但尚不能仅凭图集颜色断言它一定是伤害飘字：原版也
  可能将计时器作为地图叠层并复用这个数字图集。必须由实际绘制坐标随帧的变化和调用者 PC
  决定其语义。
- 数字左侧的绿色标记对 17×17 静态资源做了全像素模板比对，首选为资源槽 21 的
  `map_kuang.gif`，最佳位置约为截图 `(240,113)`，与次优候选有显著差距。它是目前最强的
  资源归属线索，但还不是运行时证明：截图缩放、背景色和透明像素均可能造成假匹配；而
  `map_kuang` 这个名称本身也不能说明它是计时器图标。
- `time_number.gif`、`ui_timer.gif` 与 `addtime.gif` 均是客户端资源目录中的真实 UI
  资源；但它们不能再被当作“梦境限时副本”的直接证据。静态追踪已证明 `addtime.gif`
  的一个使用点属于帮派申请审批 `1/10/33` 的通用列表界面，`ui_timer.gif` 也由邻近的
  通用界面绘制函数使用。资源名称或画面相似不等于梦境场景右上角控件的协议来源。
- “扩充装备副本”文案同样只证明原版有独立副本状态分支；其附近的对象处理函数尚未与
  场景 UI、`29梦境空间_03.sce` 或计时资源建立调用链。因此，右上角显示的精确含义、
  初始数值、扣减规则与补时机制目前都仍是 unresolved，不能据此实现猜测性的限时副本。
- 当前 dynamic NPC 副本只有目标 SCE、落点、最低等级和可选场景战斗怪；没有时限、
  剩余时间、补时物品或对应客户端会话状态。已观察到的
  `30/1 -> WT2/3 -> WT6/1 + 30/2(no-posinfo)` 也只建立通用场景进入链，不能启动该 UI。
- player-1 已正确加载 `29梦境空间_03.sce` 及其关联的
  `b_29梦境空间.sce`。后者是随场景加载的关联/背景资源，不是应替换成的副本入口，
  也不携带可用的通用倒计时配置。

## 客户端 UI 资源与已排除关联

`江湖OL.CBE` 的场景 UI 静态资源目录包含下列槽位：

| 槽位 | 资源 | 画面/文字 | 已证实范围 |
| --- | --- | --- | --- |
| 21 | `map_kuang.gif` | 青绿色 17×17 地图框 | 与截图中数字左侧标记的静态模板最接近；尚未取得运行时绘制调用者。 |
| 24 | `time_number.gif` | 绿色数字图集 | 资源已登记；尚未找到与梦境进入相连的使用点。 |
| 73 | `-num.gif` | 红黄数字图集 | 与用户截图中地图层的红色数字逐像素样式一致；可用于伤害飘字，也不能排除被地图叠层计时器复用。 |
| 85 | `ui_timer.gif` | 沙漏 | 在 `0x010225F2` 中作为资源槽 85 传给 UI 绘制 helper。 |
| 93 | `addtime.gif` | `补充时间` | 在 `0x01040176`、`0x01040808` 等处作为资源槽 93 绘制可点击列表项。 |

资源槽由 `scene_ui_tile_catalog_build_filename_table`（`0x01043B84`）建立。普通状态栏的
`UpdateSceneMenuState`（`0x0100E3E2`）只选择 `ep_icon`、`ruffian`、`training`、`muse`
等资源，不引用槽位 24、85 或 93；不能把它们误判为普通的战斗状态提示。

`HandleRankingEvents(0x01040AA8)` 对 `10/33` 调用
`HandleRankingResponse(0x0104094A)`；已有运行验证表明该包是帮派申请批准/拒绝，
不是梦境副本。该响应路径可达绘制槽位 93 的列表 UI，故“补充时间”贴图不是限时副本协议的
充分证据。

### 本轮：固定 HUD 与地图叠层数字的绘制链

资源尺寸只能限定可复用的图集，不能单独决定“伤害”还是“时钟”语义：

| 资源 | 图集尺寸（客户端像素） | 与截图的关系 |
| --- | --- | --- |
| `time_number.gif` | `77 x 7` | 细小的绿色数字图集；若绘制到截图位置，字高应约为 7 个客户端像素。 |
| `ui_timer.gif` | `13 x 16` | 只有沙漏图标，不含数字。 |
| `-num.gif` | `110 x 16` | 红黄数字图集；其 16 像素字高、颜色和截图中地图层数字一致，但图集自身不携带“伤害”或“时间”语义。 |
| `map_kuang.gif` | `17 x 17` | 截图左侧绿色标记的当前静态匹配候选；等待运行时图像指针确认。 |

场景每帧入口 `scene_runtime_tick(0x01015212)` 会先调用
`UpdateSceneMenuState(0x0100E3E2)`，再进入场景既有的菜单／布局更新调用；已证实的
`UpdateSceneMenuState` 仅消费 `training.gif`、`ep_icon.gif`、`ruffian.gif`、`muse.gif`
等状态栏资源，不消费槽位 24（`time_number`）或槽位 85（`ui_timer`）。所以普通场景的
固定 HUD 链不会仅因进入 `29梦境空间_03.sce` 就产生计时数字。

此前唯一的槽位 85 静态命中也已追到真实调用点：`0x01040786` 只在上层 UI 的
`entry->type == 2` 分支调用 `0x010225F2`。后者按列表滚动位置遍历最多 20 个条目，调用
通用布局 helper `0x0101A020`，并将 `85` 作为其中一个图块编号传入；坐标随条目和屏幕尺寸
计算，且这条调用链不从 `scene_runtime_tick` 进入。它是页面内的列表／选择控件，不是固定在
场景右上角的计时 HUD。

这还没有把 `-num.gif` 的最终动画绘制函数命名出来：该图集通过运行时资源表按索引取得，
静态代码不会在每次调用处保留文件名。画面层级可以排除固定状态栏，但不能区分“跟随地图
实体的伤害飘字”与“固定于地图右上角的限时副本叠层”。若之后需继续精确命名该函数，应只读
记录 LCD 图像 API 的源图像指针、裁剪坐标、目标坐标和 CBE 调用 PC；这样可以直接把
`-num.gif` 的某一次绘制回溯到它的客户端调用者，而不改写游戏状态或画面。

该取证现已作为默认关闭的宿主日志实现：设置 `CBE_TRACE_SCENE_NUMBERS=1` 后，
`src/vmFunc.c` 会先记录**应用主数据包**中 `+num/-num`、`map_kuang2/map_kuang`、
`time_number`、`ui_timer` 创建出的图像对象地址（避免将其他数据包的同编号资源误标）；随后对 `110x16`（`-num/+num`）、`77x7`
（`time_number`）、`13x16`（`ui_timer`），以及已确认指针的 `map_kuang`，记录一行到
`logs/scene-number-draw.log`。每行保留资源归属、透明绘制标记、源裁剪格、目标坐标和 CBE
的 `LR` 返回地址；最多记录 2048 行，之后写一次 suppression 标记。该日志不写入客户内存、
不调整图像参数、不影响 LCD 复制或网络／输入事件顺序。

客户端还含有“重置扩充装备副本失败！”及“存在扩充装备副本挑战机会，不需要重置！”
文案。相关分支位于 `0x0103838A`：对象 reader 的选择值为 `0x1B`，变体为
`2 / 4 / 13`，并按结果值显示这些文案。该分支与场景 UI、梦境 SCE 和 `10/33` 没有
已证实的调用关系。

## 截图状态的可重复观察基线

本轮重新比对了截图前后 player-1 的实际资源版本，发现“进入梦境三层”必须进一步拆分：

| 资源来源 | 压缩文件字节数 | 解压 SCE payload | 实体差异 |
| --- | ---: | ---: | --- |
| `web/fs/JHOnlineData/29梦境空间_03.sce` 原始副本 | 278 | 320 | 13 个装饰 + 1 个回临安 portal；无场景战斗实体。 |
| `bin/JHOnlineData/29梦境空间_03.sce`（player-1 的已安装缓存） | 411 | 394 | 新增动态 kind-3 场景战斗怪 `3001`，主体 `e_fire.actor`、效果 `e_ghostfireR.actor`。 |

缓存版的 SHA-256 是
`682ACD48190B5796A306FF8E7F0329F80E72DF62B03234107C3E7FE2BF57D81F`。最近的服务端记录也将
`3001` 作为 NPC `30406` 进入三层后的 `spawn_enemy`，并在客户端实体列表中报告
`runtime_index=14`。截图中的“梦境—炽热精灵”和火焰正与这个新增实体的名称、`e_fire` 图像
相符；它们不是原始三层的静态装饰。故以后不能将使用 278 字节原始 SCE 的进入测试，当作截图
状态的对照。

## NPC 入口对照场景

直接从三层登录只能验证“同资源 + 原生 `25/5` 场景加载”是否足以出现该图层数字；它不能证明
NPC 副本入口没有额外影响。因此另建 `dream-npc-entry-clock-probe-v1`，其隔离夹具严格使用：

1. `c04临安府_06.sce` 的 player-1 记录落点 `(137,321)`；
2. 唯一一个 fixture-owned 动态 NPC `30406`，放在同一落点，类型为副本向导，目标仍是
   `29梦境空间_03.sce@(120,120)`，场景战斗怪为 `3001`；
3. 已固定 SHA-256 的 411 字节三层资源副本。

客户端不会被直接发送 `26/1` 或 `30/1`。它先在 `JianghuOL.CBE+0x015154` 的
`FindNearestNPCWrapper → ShowConfirmOrMessage` 提示创建边界，向普通硬件输入队列发送一次
确认键；随后仅在 `ParseNPCDialogData(0x010380E8)` 首次处理该 NPC 的 `26/1` 对话时再发送一次
确认键，选择客户端首项“进入副本”。服务端和客户端必须自然完成：

```text
26/1 {type=1,id=30406}
→ 26/1 对话（action=1，“进入副本”）
→ 26/1 {type=2,id=0xEB0076C6}
→ 30/1
→ 场景跟随请求及目标场景 25/5
→ 右上地图区域的真实数字绘制（若有）
```

其中 `0xEB0076C6 = 0xEB000000 | 30406`；它是现有服务端实例入口操作值，不是计时器字段。
自动化会保留每个 PC 触发、`30/1`、后续 `25/5`、服务端两次 `26/1` 边界、内部 LCD 帧和数字
atlas 的真实 caller。若 75 秒内未有绘制，结果是确定的负观察而非“制造倒计时”。

2026-08-30 的首次真实运行证明，单独把 411 字节文件覆盖为服务端基础资源并不构成已发布内容：
服务端会因没有同一场景的已启用草稿、部署指纹、捕获基础和私有 overlay 而正确禁用 `30406`，客户端
遂在等待原生 NPC 提示时超时。随后确认当前 `jh_online` 已不再保存该发布版本的 3001 草稿、捕获基础
或部署账本；因此夹具不再读取或复制主库的任何内容。它只将已安装 411 字节 SCE 中可由客户端 parser
验证的 kind-3 记录还原为**隔离库草稿**：`3001@(180,141)`、数量 1、field16=5、名称 GBK 原始字节、
`e_fire.actor` 与 `e_ghostfireR.actor`。

隔离服务启动后，运行器向本机隔离管理端口提交正式的 `deploy-scene-battle-monsters` 动作。服务自身负责：
捕获 278 字节基础 SCE、生成私有 overlay、发布 WT18 内容清单并写入部署账本。随后运行器必须验证生成的
overlay 为 411 字节，且 SHA-256 等于 player-1 缓存快照
`682ACD48190B5796A306FF8E7F0329F80E72DF62B03234107C3E7FE2BF57D81F`；不一致即在客户端启动前失败。
这既避免伪造部署账本，也不写入用户内容。

两次隔离试跑还给出一个更早的失败边界：运行器曾把 POST 发往 `/login` 和 `/action`，而后台的公开路由实际是
`/admin-418yz6/login` 与 `/admin-418yz6/action`（由 `web_admin_server.c` 的
`VM_MOCK_ADMIN_BASE_PATH` 声明）。前者会得到普通页面的 `404`，不会创建 `cbe_admin` 进程内会话；因此服务端
没有收到发布动作，也不会有 overlay 或客户端进程。这不是网络、资源或 CBE 问题。运行器现仅在唯一测试库创建
显式命名的 `dream_probe_admin` 操作员，通过这两个真实后台 HTTP 表单路由获得私有 Cookie 并提交发布；Cookie
不写入产物。发布事务提交后，运行器停止并重新启动**自己创建的隔离服务**，使启动期动态 NPC 校验读取已落库的
overlay 与部署账本。它同时保留 `server-predeploy.stdout.log`（认证／发布）和新服务日志（NPC 装载／游戏协议）。
没有恢复默认管理员，也没有访问用户的后台账号。

随后两次启动仅生成 `fixture.log`，没有服务端或客户端 PID：夹具把 `CREATE TABLE IF NOT EXISTS
server_admin_users` 放在角色／草稿事务内部。MySQL 对 DDL 会隐式提交，因此之后的显式 `commit()` 与
异常分支的 `rollBack()` 都报“没有活动事务”，后一个错误还掩盖了第一个错误。建表现已移到事务开始之前，
且清理仅在 `inTransaction()` 时回滚；这属于隔离测试准备修复，不涉及客户端、资源或协议行为。

新增隔离自动化场景 `dream-clock-probe-v1`。它创建唯一的
`jh_online_autotest_<hex>` 数据库和独立的客户端目录，以 278 字节原始场景作为客户端起始缓存，
并要求正式隔离发布生成上述 **411 字节、哈希固定** 的服务端覆盖资源。测试角色在 `(120,120)` 正常登录进入
`29梦境空间_03.sce`；若客户端没有按内容更新协议取得发布资源，后续场景解析和探针都会留下对应的首次失败证据。
标题阶段仍只使用既有的一次性硬件队列按键；在客户端实际收到 `25/5`
并完成两帧 LCD 渲染后，场景内不发送点击、移动、攻击、请求或回调。

随后探针仅观察截图换算得到的地图矩形（客户端坐标 `x=160..232, y=62..105`）：

- 若 `-num/+num` 图集在该区域产生连续的三个裁剪 blit，或一个宽度至少 24 的完整 blit，保存
  `dream-map-number-observed` LCD 帧、源裁剪/目标坐标和 CBE `LR` 返回地址，并通过；
- 若 75 秒观察窗口内没有这个真实绘制事件，保存 `dream-map-number-not-observed` 帧和资源快照，
  以明确失败退出；失败只说明“固定资源 + 正常场景进入”不是充分条件，不能否定截图；
- `CBE_TRACE_SCENE_NUMBERS=1` 仅启用既有的只读 LCD 日志。它不写 CBE 内存、寄存器、包、
  callback 或渲染参数。

运行前提是本机可连接隔离数据库。可直接双击专用 BAT 启动器；若当前进程没有
`CBE_AUTOMATION_MYSQL_PASSWORD`，它会显示 PowerShell 的隐藏密码输入提示，并只在该次子进程中
保存口令。也可由命令行显式提供口令：

```bat
set "CBE_AUTOMATION_MYSQL_PASSWORD=<本机隔离测试库口令>"
scripts\run-dream-npc-entry-clock-probe.bat
```

BAT 只固定调用 `dream-npc-entry-clock-probe-v1`，并将底层运行器的退出码原样返回；失败时会保留
错误提示窗口，避免双击时看起来像客户端闪退。

```powershell
$env:CBE_AUTOMATION_MYSQL_PASSWORD = '<测试 MySQL 口令>'
make -j2
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/run-shop-return-hangup-automation.ps1 -Scenario dream-clock-probe-v1
```

运行产物位于 `artifacts/automation/dream-clock-probe-v1-*/`，包含 `result.json`、LCD PNG/JSON、
`scene-number-draw.log`、服务端日志、夹具日志及资源哈希。运行器拒绝端口占用、非
`jh_online_autotest_*` 数据库和任何不等于上述哈希的梦境缓存；它只停止自己记录的进程。

这是“同一资源状态下，进入本身是否足以画出数字”的稳定对照，**不是** NPC `30406` 的完整
`30/1` 进入回放。若该基线稳定失败，下一轮才应在同一资源夹具内补齐经过实测的 NPC 对话和
选项硬件输入，比较 `30/1` 进入与普通登录进入的首次绘制差异；不能用服务端直接补数字或
人为设置客户端倒计时替代这条输入链。

## 未决项与下一步

目前不存在足以实现的“原版限时副本完整协议”。当前通用 NPC 传送也没有任何可证明的
限时状态。要继续实现，必须先以一份会显示时间的原版进入记录为对照，捕获：

1. 进入前后的请求序列，以及首次出现 `-num/map_kuang/time_number/ui_timer/addtime` 时紧随的响应对象；
2. 初始数值、倒计时变化和点击“补充时间”后的请求/响应；
3. 到时、离开和重新进入时客户端如何清理或恢复该状态。

确认后才能定义实现范围：服务器是否需要持久化剩余时间/次数、哪个原生包创建客户端会话
状态、是否存在补时请求、以及到期如何处理。届时再把梦境 NPC 绑定到已证实的新服务；
不能更改 CBE/CBM、客户端内存或在宿主侧伪造 UI 状态。
