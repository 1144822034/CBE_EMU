# 怪物管理：智能装备掉落分配

状态：已实现；纯内存回归已通过。

后台“怪物管理”新增“智能分配装备掉落”操作。管理员可以分别设置品质 `0`、`1`、`2` 的每件装备掉落概率，提交前会显示覆盖范围和保留任务材料的确认说明。

智能分配的边界包含 `server_scene_battle_monsters`：只要怪物 ID 已在场景战斗怪配置中出现（包括已禁用的配置行），就不会进入装备候选，也不会被事务更新、清空或重建 `server_monster_drops`，其场景战斗配置和现有掉落保持不变。

## 数据边界

- 只读取 `equip.dsh` 所定义的八个真实装备槽位：主武器及七个穿戴部位；只处理品质 `0`、`1`、`2`。每件候选装备最多分给一个怪物；没有合法承接怪时跳过并在后台结果中报告，不会强行分配给低等级怪物。
- 品质 `0` 只分给非首领怪物；品质 `1`、`2` 只分给 `family=首领` 的怪物。普通怪不会因该操作获得品质 `1` 或 `2`。
- 每个怪物资源目录自带的单条任务材料掉落是保护项。若已有覆盖行保留该材料，则保留其已调概率；否则恢复资源目录定义的概率。此前手动添加的其他材料和全部装备掉落都会被覆盖。
- 装备必须与怪物处于同一个十级阶段（`1–10`、`11–20`、……、`61–70`）才具备承接资格；这同时拒绝低等级装备向高等级首领上溢，以及高等级装备向低等级怪物下压。满足阶段资格后，同一怪物的每个穿戴部位最多承接一件装备，避免堆叠几十条同部位掉落。候选先按等级差最小匹配，再按同品质已分配数均分；名称连续匹配至少两个中文字符时仅作为同等级、同分配数候选的稳定优先级，最后按怪物 ID 决策。

首领数量较少，而品质 `1`、`2` 装备较多；原来的每怪 64 条上限会静默截断尾部装备。因此 `VM_NET_MOCK_MONSTER_DROP_MAX` 改为协议和 MySQL `TINYINT UNSIGNED` 都可表达的 255 条。若合格怪物的剩余容量仍不足，操作会在写库前失败，不会丢弃任何装备。

## 持久化与运行时

分配器先完整构造所有怪物的新掉落表，再开启一个 MySQL 事务：逐怪物写入当前有效属性、删除旧掉落并插入“任务材料 + 新装备”。任何 SQL 失败都会回滚；只有提交成功后才替换内存覆盖表。因此普通场景战斗、副本和挂机都从同一 `server_monster_drops` 契约读取结果，未修改客户端、网络响应或角色状态。

服务日志记录普通怪/首领数、各品质装备数、保留任务材料数、强名称关联数、三种概率和事务状态，事件名为 `monster_equipment_drop_assign`。

## 后台提交失败提示的根因

一次分配日志已经显示 `transaction=committed`，但页面仍提示“怪物操作提交失败”。首个偏离不在 MySQL，而在提交后的 303 重定向：成功摘要包含中文，URL 编码后长度明显增加；原先重定向构造缓冲、`Location` 额外头和最终 HTTP 头缓冲分别只有 768/1100/1024 字节，`snprintf` 截断后浏览器无法解析完整的怪物管理页面，前端找不到 `#monster-list` 和 `[data-admin-detail]`，于是显示通用失败。

现已将怪物重定向消息/Location 扩至 2048/2304 字节，并将重定向额外头和最终 HTTP 头扩至 4096/8192 字节。事务提交后页面刷新不再因成功提示被截断而误报失败；该修复不改变分配事务或掉落规则。

## 回归

`scripts/monster-equipment-drop-assignment-regression.c` 只为内存目录准备五只怪物、八件装备与一条任务材料，调用规划层而不启动监听器或连接 MySQL。它验证：

- 任务材料及其已调概率保留；
- 品质限制正确，七件合法装备恰好各分配一次，额外的一件跨阶段低级装备被跳过；
- 装备十级阶段和穿戴部位资格正确，低等级怪物不会接收高等级装备，高等级首领也不会吸收低等级装备，同一怪物不会重复占用同一穿戴部位；
- 三个普通怪的品质 `0` 均分，两个首领的品质 `1`、`2` 均分；
- 两个中文字符以上的名称关联和相应等级落到预期怪物。

构建与运行：先执行 `make -j2`，再用与 `admin-request-length-regression.c` 相同的 MinGW 链接命令构建该测试；运行时将仓库 `bin/` 和 `Lib/sdl2-2.0.10/bin/` 加入该测试进程的 `PATH`。本次本地结果为通过。
