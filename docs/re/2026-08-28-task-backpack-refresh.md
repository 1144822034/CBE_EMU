# 任务接取与提交后的背包刷新

## 现象

接取一个配置了 `givenItemId/givenItemCount` 的任务后，服务端背包数据已经
增加了该物品，但客户端背包没有立即显示；随后提交该任务时，服务端已扣除
物品，客户端原有画面也没有同步删除该物品。

## 可重复链路与证据

`bin/server_out.txt` 的同一真实客户端会话（角色 `10093`、任务 `2000`）记录了：

1. NPC 对话发出 `26/1 action=4`，客户端请求任务详情 `6/10`，随后请求接取
   `6/11`。
2. 服务端以 `backpack-add-item` 成功保存了任务给予物品，紧接着的接取回包为
   `mock_task action=accept ... response_objects=4 ... request=6/11 response=6/11`。
   这四个对象是 `6/11`、请求携带的 `25/5` 确认、以及任务列表/提示刷新
   `6/1 + 6/14`；其中没有能向物品管理器新增背包行的 `7/15`，也没有按序号刷新
   总数的 `7/11`。
3. 玩家到交付 NPC 后，服务端成功保存 `task-commit`，并记录
   `mock_task_submit_iteminfo ... seqnum=1 iteminfo_len=7` 与
   `mock_task action=commit ... request=6/4 response=6/4`。这证明提交的任务回调
   已取得要扣除的服务端序号；但这个序号此前从未被接取回包交给客户端，故客户端
   没有可被 case-4 行更新命中的背包行。

当前没有 `bin/logs/net_trace.log` 或 `bin/logs/net_packets.log`；上述服务端运行日志
保留了请求类型、回包对象数、持久化原因和提交 iteminfo 长度，足以定位第一次偏离在
接取回包的物品同步缺失，而不是任务状态或数据库写入。

## 客户端与协议契约

- `JianghuOL.CBE:net_handle_task_response_dispatch(0x0104726C)` case 11 解析
  `6/11` 接取结果；case 4 解析 `6/4` 的 `seqnum` 和每个
  `(i16 sequence, u8 remaining)` 的 `iteminfo`，再处理奖励。
- `JianghuOL.CBE:0x01033544` 是通用 `7/11` 的按序号数量同步路径；数量为零时
  由客户端执行删除。
- 现有、已使用的 `7/15` 增量奖励对象是客户端物品管理器的新物品/堆叠入口；与随后
  的 `7/11` 绝对数量同步组合，可同时覆盖新建背包行与已有堆叠行。其序号和总数必须
  来自同一次 `vm_net_mock_role_add_backpack_item` 的成功结果。

因此不能以登录后的 `17/1` 全量背包重建掩盖问题，也不能在宿主侧直接更新客户端。
修复应当在 `6/11` 正常回包内追加服务端已验证的 `7/15 + 7/11` 对象；提交仍由原有
`6/4` case-4 iteminfo 使用同一序号执行扣除。

## 计划修改和验证

1. 接取给予物品时保留实际背包序号，验证持久化后的行和总数。
2. 仅在 `6/11 result=0` 且确实给予物品时追加一条 `7/15` 增量和一条同序号 `7/11`
   总数同步；不为没有给予物品的任务增加对象。
3. 增加确定性回归：解析任务接取回包，断言成功给予物品时含有上述两种对象和一致
   序号；再覆盖随后的 `6/4` 提交 iteminfo。构建后运行 `make -j2` 和该回归。

## 验证结果

2026-08-28 已执行：

- `mingw32-make -j2`：通过。
- `obj/server/task-delivery-item-consumption-regression.exe`：通过。该隔离夹具先
  断言接取差分生成一条 `7/15` 和一条 `7/11`，再断言物流货物以相同序号编码进
  `6/4 seqnum/iteminfo` 的零余量删除流。
- `obj/server/task-logistics-delivery-readiness-regression.exe`：通过，确认物流任务
  仍只有在持有给予物品时才可交付。

## 风险与边界

本修复不改变 CBE 回调、网络投递、任务状态机或回包字节之外的宿主逻辑。所有物品变更
仍由服务端的角色持久化函数完成，客户端只通过其已注册的 WT 回调解析原样响应字节。
